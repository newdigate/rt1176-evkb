# RT1176 → RK055HDMIPI4MA0 capacitive touch (v2: "a finger on real glass") — Design

**Date:** 2026-07-28
**Status:** validated design, ready for an implementation plan
**Fulfils:** the "**v2** — capacitive touch (controller on `J48` pins 26–29 via LPI2C5/Wire2)"
roadmap entry of `2026-07-27-rt1176-rk055-display-design.md` (§2).

---

## 1. Goal

Read **capacitive touch** from the RK055HDMIPI4MA0's **GT911** controller over LPI2C5 (`Wire2`),
and prove it twice: in QEMU against a virtual GT911, and on real silicon against a real finger.

The display half is done and hardware-verified ([[rt1176-rk055-display]]), so the hard SoC work
is behind us. What is genuinely hard here is *verification*: a gate that prints `TOUCH_OK`
because a register read succeeded proves nothing. §7 is the substance of this design.

**Controller identity (verified).** The RK055 uses a **GT911**, not the FT5406.
`mcuxsdk/examples/lvgl_examples/lvgl_sdk/lvgl_support/rt11xx/lvgl_support.c` selects
`FT5406_RT_Init()` only for `DEMO_PANEL_RASPI_7INCH` and `GT911_Init()` for every other panel.
Driver reference: `mcuxsdk/components/touch/gt911/fsl_gt911.{c,h}`, **BSD-3-Clause** — the licence
firewall is a non-issue, exactly as it was for the HX8394.

**Precondition, confirmed not assumed (2026-07-28):** the RK055 is on `J48` and the Raspberry Pi
7" panel is **disconnected**. LPI2C5 therefore carries exactly two devices: the GT911 at 0x5D and
the WM8962 codec at 0x1A. §9.4 records what changes if both panels are ever plugged in at once.

## 2. Scope

**In scope (v2):**

- A new **`TouchPanel`** sibling library containing a `GT911` driver (reset + I²C-address latch,
  ID check, config read, polled multi-touch coordinate read, diagnostics).
- A **virtual GT911** in the `mimxrt1170-evk` QEMU machine, including the INT-level address latch.
- `examples/display/rk055_touch_test/` — a three-phase gate (targets, swipe, two-finger) with
  `run_qemu.sh` and a hardware transcript.
- An `attachInterrupt` **edge counter** on the INT line, as a corroborating token only.
- Documenting the new **D6/D9 board trap** (§4.2).

**Out of scope — named follow-ons, not silently dropped:**

- **v3** — the LVGL `lv_indev` binding on top of v2, joining the existing `lvgl_rpi_panel_test`
  shape. The LVGL port already exists (`~/Development/LVGL/port/lvgl_mipi_panel.*`).
- **The FT5406** (the RPi panel's controller). It is the natural second implementation and §3
  leaves a seam for it, but the RPi panel remains hardware-blocked on the `J84` lane-order
  mismatch and nothing here changes that.
- **Gestures, filtering, debouncing, calibration storage.**
- **Any write to the touch IC's configuration space.** See §5.3 — this is a deliberate safety
  decision, not an omission.
- **Interrupt-driven coordinate reads.** The INT line is proven, but the read path stays polled.

## 3. Architecture

### 3.1 A new sibling library, not a `MipiDisplay` subdirectory

`MipiDisplay` is split `soc/` + `panels/<name>/` with the panel selected at **compile time**,
because the RT1176 has exactly one MIPI-DSI host. **Touch does not share that constraint** — it is
an I²C device, and two controllers could in principle coexist on the same bus. Putting the GT911
under `panels/rk055/` would inherit a restriction it does not have, force `MipiDisplay` to depend
on `Wire` (it has no such dependency today), and strand the FT5406 in `panels/rpi7/`.

So: a new repo, following the established peripheral-library convention.

```
~/Development/TouchPanel   →  github.com/newdigate/TouchPanel
  LICENSE                  MIT (matching the tree; the tree is deliberately MIT/BSD-only)
  library.properties
  README.md
  TouchPanel.h             shared vocabulary
  gt911/
    gt911.h
    gt911.cpp
```

Imported by an example as:

```cmake
import_evkb_library(TouchPanel gt911)
```

— the same `NAME + subdirs` form `MipiDisplay` uses. `evkb.cmake` gains a manifest line:

```cmake
_evkb_lib(TouchPanel ${_dev}/TouchPanel https://github.com/newdigate/TouchPanel <sha> .)
```

Local-first resolution applies as usual; the pin is filled in once the repo is pushed.

### 3.2 No abstract base class yet

`TouchPanel.h` defines the shared vocabulary only:

```cpp
struct TouchPoint { uint8_t id; uint16_t x, y; };
```

`GT911` is a **concrete class with no virtuals**. With exactly one implementation, an abstract
base is speculative: the seam that matters is the library boundary and the shared `TouchPoint`
type, not a vtable. When the FT5406 arrives, extract the base then — with two real implementations
to generalise from rather than one imagined one.

### 3.3 Public surface

```cpp
class GT911 {
public:
    GT911(TwoWire &wire, uint8_t rstPin, uint8_t intPin);

    bool     begin();                                   // reset, address latch, ID, config read
    uint8_t  read(TouchPoint *points, uint8_t maxPoints);  // 0 = no touch; caller sizes the array

    uint16_t resolutionX() const;                       // as REPORTED by the IC (§5.4)
    uint16_t resolutionY() const;
    uint8_t  configuredPoints() const;                  // stored touchPointNum, read never written
    uint8_t  address() const;                           // 0x5D or 0x14 — which one answered

    enum class Error : uint8_t {
        None, NoAck, BadId, ConfigRead, ConfigChecksum, StatusRead, PointRead, StatusClear
    };
    Error    lastError() const;
    uint32_t lastDeviceId() const;                      // the raw 4 bytes read from 0x8140
    uint8_t  lastI2cStatus() const;                     // Wire endTransmission() code
};
```

**Diagnostics are a requirement, not a nicety.** [[rt1176-rk055-display]] records that
`hx8394Init()` having only a `bool` return was what made the panel-ordering bug expensive, and
that the RPi bring-up lost two sessions to the same deficiency. `begin()` returning `false` must
always be accompanied by a machine-readable reason.

## 4. Board facts

### 4.1 Pins — netlist-verified

| Signal | `J48` | Board net | Series | SoC pad | Ball | Fast alias | **Normal port (ALT5)** | **Core digital pin** |
|---|---|---|---|---|---|---|---|---|
| Touch RST | 28 | `CTP_RST_B_C` → `CTP_RST_B` | R2031 (0 Ω) | `GPIO_AD_01` | R14 | `GPIO9_IO00` | GPIO3 bit 0 | **D9** |
| Touch INT | 29 | `CTP_INT_C` → `CTP_INT` | R2032 (0 Ω) | `GPIO_AD_00` | N12 | `GPIO8_IO31` | GPIO2 bit 31 | **D6** |
| I²C SCL | 26 | LPI2C5 SCL | — | `GPIO_LPSR_05` | — | — | GPIO6 bit 5 | D15 |
| I²C SDA | 27 | LPI2C5 SDA | — | `GPIO_LPSR_04` | — | — | GPIO6 bit 4 | D14 |

Sources: `MIMXRT1170-EVKB-DESIGNFILES_RevC3/pst2kicad/board.net` (nets `CTP_RST_B_C` code 763,
`CTP_INT_C` code 768, `GPIO_AD_00` code 880, `GPIO_AD_01` code 946); SDK
`examples/_boards/evkbmimxrt1170/board.h:168–176`; core `cores/imxrt1176/digital.c:76,79`.

**★ The `GPIO8`/`GPIO9` CM7 interrupt trap does not apply here.** Those are the *fast aliases*.
Per [[rt1176-gpio-irq-cm7-trap]] the fast ports `GPIO7..GPIO12` are `NotAvail_IRQn` on the CM7 —
but this core's pin table already drives both pads through the **normal** ports at ALT5
(`IOMUXC_GPIO_AD_00_GPIO_MUX2_IO31`, `IOMUXC_GPIO_AD_01_GPIO_MUX3_IO00`), and GPIO2's combined
IRQs are 102/103. The three aliases share bit positions, so this costs nothing. The driver can use
plain `pinMode` / `digitalWrite` / `digitalRead` / `attachInterrupt`; there is no raw register work
in this design at all.

### 4.2 ★ New board trap to document

**Touch INT and RST *are* Arduino digital pins D6 and D9.** Three consequences:

1. **`irq_attach_test` uses a D13→D9 jumper** — D9 is the touch reset line. Running that gate with
   the RK055 attached drives the panel's touch reset. Not a firmware conflict (different
   binaries), but a real bench trap.
2. Per [[rt1176-arduino-header-audit]], `GPIO_AD_00`/`GPIO_AD_01` also appear **raw on `J25` odd
   pins 15 and 13** (no series resistor), and fan out through populated 0 Ω (R1811/R1813,
   R1906/R1907, R6/R10) into the SIM circuit (RevC3 sheet 22) and the motor-control column.
3. **This matters more than usual because the I²C address is latched from the INT pin level**
   (§5.2). Anything loading `GPIO_AD_00` during the ~55 ms reset window can change which address
   the device answers at — a silent failure that looks like "the device isn't there".

This belongs in `docs/arduino-header-revc3.md` alongside the existing A5/`USB_OTG2_ID` entry.

### 4.3 Bus configuration

LPI2C5 = `Wire2`. **No change to the `Wire` library is needed** — the hard-won settings are
already in place ([[rt1176-rpi-display-hw-bringup]], [[rt1176-wire-library-move]]):

- Pad **`0x20` (ODE, open-drain)** on the LPSR pads. Not `0x0A` — push-pull gives arbitration-lost
  on every address on this shared bus. Do not "improve" this.
- `CCM_CLOCK_ROOT41` mux 1 (OSC24M) ÷ 1 = **24 MHz** functional clock, which is what `setClock()`'s
  prescale arithmetic assumes.

The example calls `Wire2.setClock(400000)`. Note this **diverges from NXP**, which runs the LPI2C5
root at OSC24M ÷ 12 = 2 MHz (`board.h:171`) and divides down from there; we reach a comparable SCL
rate through the LPI2C divider from a 24 MHz root instead, because that root is already
hardware-proven on this bus. 400 kHz is the GT911's rated maximum and is **unproven here** — if
silicon is marginal, fall back to 100 kHz and record it (§9.2).

## 5. The GT911 driver

### 5.1 Register facts

Transcribed as facts from `fsl_gt911.c` (BSD-3-Clause, NXP, 2019–2020,2024). Values and addresses
are recorded with citation; **no code structure is copied**, per the licence firewall.

| Address | Meaning |
|---|---|
| `0x8047` | config base / config version (a value of 0 means the blob is invalid) |
| `0x8048`–`0x804B` | X resolution low/high, Y resolution low/high |
| `0x804C` | touch point count (low nibble) |
| `0x804D` | module switch 1 — bits [1:0] = INT trigger mode, bit 3 = X2Y swap |
| `0x80FF` | config checksum (index 184 of the blob) |
| `0x8100` | config "fresh/valid" flag (index 185) |
| `0x8140` | product ID, 4 bytes — must read `'9','1','1','\0'` = `0x00313139` little-endian |
| `0x814E` | status — bit 7 = buffer ready, bits [3:0] = number of points |
| `0x814F` | first point; **8 bytes per point**: `id, xL, xH, yL, yH, sizeL, sizeH, reserved` |

Config blob length **186 bytes** (`0x8047`–`0x8100` inclusive). Checksum = `(~sum + 1)` over the
**first 184** bytes, compared against byte 184.

I²C addresses: **0x5D** (mode 0) or **0x14** (mode 1), 7-bit.

Sub-addresses are **16-bit, big-endian (high byte first)**. The driver issues them explicitly —
`beginTransmission(addr); write(hi); write(lo); endTransmission(false); requestFrom(addr, n);` —
rather than using `Wire`'s `iaddr` `requestFrom` overload, so the driver does not depend on that
overload's 16-bit byte order. The repeated-START read path is already hardware-proven
([[rt1176-wire-library-move]]: `requestFrom` TX→repeated-start→RX byte-exact).

### 5.2 ★ The reset sequence and the I²C address latch

**This is the single subtlest fact in the whole task.** The GT911 latches its I²C address from the
INT pin level at the moment reset is released. INT is therefore **bidirectional in time**: an
output during reset, an input forever after.

Address-mode-0 sequence (targeting 0x5D), with NXP's delays:

| Step | Action | Delay after |
|---|---|---|
| 1 | INT → output, drive **LOW** | — |
| 2 | RST → output, drive **LOW** | 20 ms (spec ≥ 10 ms) |
| 3 | — | 1 ms (spec ≥ 100 µs) |
| 4 | RST → **HIGH** (release reset — the level on INT is latched here) | 5 ms |
| 5 | INT → drive **LOW** (still an output) | 50 ms |
| 6 | INT → **input** | — |
| 7 | Read 4 bytes at `0x8140`; require `0x00313139` | — |

Steps 3 and 5 look redundant for mode 0 (INT is already low), but they are the reference's timing
and are transcribed faithfully. Mode 1 differs only in driving INT **high** before step 4.

Consequence for the API: the INT pin cannot be configured once and forgotten. `begin()` owns the
direction changes; `attachInterrupt` (§6.3) is only attached **after** step 6.

### 5.3 ★ The config blob is read-only. We never write it.

`GT911_Init` rewrites all 186 bytes whenever the stored `touchPointNum` or `intTrigMode` differ
from what the caller asked for — recomputing the checksum and setting the valid flag. NXP's own
comment warns that "setting wrong firmware to the touch IC will break it."

**Decision: we read, verify, and adapt. We never write.**

- The stored point count only **caps** how many points the IC reports. `read()` works regardless,
  as long as the stored value is ≥ the number of points we want.
- If the panel ships with `touchPointNum < 2`, the driver reports that through
  `configuredPoints()` and the two-finger phase fails **loudly**. It does not rewrite NVM to fix
  itself.
- `intTrigMode` only matters for interrupt-driven reads, and §6.3 uses the INT line as a counter,
  not as the read trigger — so we do not need to change it.

The blob's checksum **is** verified on read (`ConfigChecksum` error), because a bad checksum means
we cannot trust the resolution fields we are about to scale by.

This eliminates all brick risk on a panel that cannot be replaced. §8 T2 records the escalation
path if a hardware finding ever forces a write: it becomes its own spec, with its own gate.

### 5.4 Resolution: scale by it, never assert it

The GT911 reports its own resolution, which is not guaranteed to equal 720×1280. The driver
exposes it; the example **scales by it** and **prints it** (`RES=`), and asserts nothing about its
value.

This is deliberate. A brittle `assert(resX == 720)` would fail on a legitimate panel variant, while
a wrong resolution already has a natural detector: the drawn targets become unhittable and the
phase-1 assertion fails on its own. The transcript records the truth either way.

### 5.5 The mandatory status clear

After reading points, the firmware **must** write 0 to `0x814E`. A driver that forgets it sees the
same buffer forever — a stuck-value failure that looks like a working touchscreen holding still.
`read()` performs the clear and reports `StatusClear` if it fails; §7.2 makes the QEMU model
*enforce* it.

## 6. The example and the gate

`examples/display/rk055_touch_test/`, imports:

```cmake
import_evkb_library(MipiDisplay soc panels/rk055)
import_evkb_library(PXP)
import_evkb_library(TouchPanel gt911)
import_evkb_library(Wire)

teensy_target_link_libraries(rk055_touch_test cores MipiDisplay PXP TouchPanel Wire)
```

The panel comes up first (targets have to be visible), honouring
`PANEL_INIT_BEFORE_SCANOUT = 1` — panel init before the LCDIFv2 scans out, which
[[rt1176-rk055-display]] established is a **panel property**, not a general rule.

### 6.1 Tokens

```
I2C_OK  ADDR=0x5D
GT911_OK  ID=911
CFG_OK  RES=<x>x<y>  POINTS=<n>
TARGET 1/5 HIT x=.. y=..     ... TARGET 5/5 HIT ...   TARGETS_OK
SWIPE_OK dir=+x span=<pct>% samples=<n>
MULTI_OK ids=<a>,<b> sep=<px>
INT_EDGES=<n>
TOUCH_OK
```

Every failure names the phase, the reason, and the last coordinate seen — e.g.
`TARGET_FAIL phase=1 target=3 reason=timeout last=(412,918)`. Bare booleans are banned (§3.3).

### 6.2 The three phases

**Phase 1 — five targets, in order.** The example draws one filled target at a time at known
framebuffer coordinates (four corners inset from the edge, then centre) and advances only when a
reported touch falls inside the **current** target's bounds. A stuck or fabricated coordinate can
satisfy at most one target.

This phase is the only thing in the entire design that proves the **coordinate ↔ display mapping
and orientation**: a flipped, swapped, mirrored or mis-scaled axis makes the sequence impossible
to complete, because the operator is touching where the graphic *is*.

**Phase 2 — a directional swipe.** Requires monotonic movement in a stated direction across ≥ 60 %
of the axis over ≥ 8 samples. Proves live streaming and catches a mirrored axis independently of
phase 1.

**Phase 3 — a two-finger hold.** Requires two simultaneously valid points with **distinct touch
IDs** and at least a minimum separation. Proves the point-array decode and the count field — the
parts phases 1 and 2 exercise only for `points[0]`.

### 6.3 The INT edge counter

After `begin()` releases INT to an input, the example `attachInterrupt`s it (D6, GPIO2 bit 31,
CM7 IRQ 103) and counts edges, reporting `INT_EDGES=`. **The interrupt never drives the read
path** — coordinates are polled — so this adds no failure domain to the critical path.

Two reasons it earns its place: it is an independent hardware signal that a polled read cannot
give (the line physically toggled when a finger landed), and it de-risks v3's LVGL binding, which
will want it.

It is also, incidentally, the **first silicon verification of GPIO2 interrupts** —
`irq_attach_test` only ever proved GPIO3.

## 7. Verification

### 7.1 The two-gate rule, and what each gate is allowed to prove

| Token | QEMU proves | Hardware proves |
|---|---|---|
| `I2C_OK` / `ADDR` | the address-**latch logic**: a driver that gets the INT sequence wrong finds no device | the real IC answers at 0x5D over the real bus |
| `GT911_OK` / `ID` | the read path and the 16-bit sub-address encoding | the real silicon's product ID |
| `CFG_OK` / `RES` | the checksum arithmetic and blob parsing | **the only true source of the resolution** — QEMU's blob is fiction |
| `TARGETS_OK` | coordinate decode + the phase state machine, against a model-owned path | **a finger**, and the coordinate↔display **mapping** |
| `SWIPE_OK` | monotonicity logic | real streaming through the analog front end |
| `MULTI_OK` | the point-array decode | the real IC genuinely tracking two contacts |
| `INT_EDGES` | the INT wiring and `attachInterrupt` plumbing | the real line toggles; **GPIO2 CM7 IRQ on silicon** |

**★ Orientation is hardware-only by construction.** The QEMU model and the example share our
assumption about which corner is (0,0), so QEMU can never catch a flipped axis. Only a finger
settles it. This is the same *documented asymmetry* pattern the display gate already uses
(`PANEL_SUM` QEMU-only, `UNDERRUN` hardware-only) — stated, not papered over.

### 7.2 The QEMU model

New `hw/i2c/imxrt_gt911.{c,h}` in `~/Development/qemu2`, instantiated on `lpi2c[4].bus` in
`hw/arm/mimxrt1170-evk.c` alongside the RPi ATtiny (0x45) and the WM8962 stub (0x1A).

GPIO wiring:

- inputs: `gpio[2]` output 0 (RST) and `gpio[1]` output 31 (INT, while firmware drives it)
- output: → `qdev_get_gpio_in(gpio[1], 31)` (INT, once the model drives it)

*Note on the shared pin:* the existing `irq_attach` fixture connects `gpio[2]` **output 27** to
`gpio[2]` **input 0**. The GT911 consumes `gpio[2]` **output 0**. Same pin, opposite direction —
no contended connection, but the machine file gets a comment saying so, because it is exactly the
kind of thing that looks like a bug six months later.

Three properties make it an oracle rather than a mirror of our driver:

1. **It has no I²C address until the first RST rising edge**, at which point it latches 0x5D or
   0x14 from the INT level. A driver that never toggles RST, or that gets the INT level wrong,
   finds nothing on the bus and the gate goes **red**. This puts the subtlest fact in the task
   under automated regression. *(Implementation note: QEMU's `I2CSlave` wants an address at
   realize; park the model at a reserved address until the latch fires, then
   `i2c_slave_set_address` — the same mechanism the `Wire` slave gate's `SAMR` handling already
   uses.)*
2. **It refuses to advance its touch script until the firmware writes 0 to `0x814E`.** Forgetting
   the mandatory status clear (§5.5) stalls the gate.
3. **The touch path is timer-driven and owned by the model.** A `QEMUTimer` replays a deterministic
   sequence — five discrete taps, then a left-to-right drag, then a two-point hold — expressed in
   *touch-resolution* space as fractions of the reported resolution. The firmware cannot influence
   it. Contrast with a firmware-writable injection tap, which would be circular by construction:
   [[rt1176-gpio-irq-cm7-trap]] records a gate that passed falsely for exactly that reason, and
   "a gate you built to match your firmware proves consistency, not silicon correctness."

A write into the config space (`0x8047`–`0x8100`) logs `LOG_GUEST_ERROR`. The gate greps the
existing `-d guest_errors -D <name>.dbg` dump for it, so §5.3's read-only decision is **enforced**,
not merely intended.

The model serves a **checksum-valid** 186-byte blob so the firmware's verify path is exercised
positively; a negative test (deliberately corrupt the checksum, expect `ConfigChecksum`) is a
build-time unit concern, not a machine-model one.

### 7.3 Hardware ritual

Per CLAUDE.md and [[rt1170-evkb-flashing]] — do **not** hold the VCOM while programming:

```
flash … load   →   flash … verify   →   attach tools/rt1170-console.py   →   reset via a
backgrounded LinkServer run
```

`pkill LinkServer` also needs `redlinkserv` and `crt_emu_cm_redlink`. A stuck LPI2C BBF needs a
**physical power cycle** — a debugger reset does not clear it.

Evidence lands in `transcript_qemu.txt` and `transcript_hw_evkb.txt`, matching the display gate.

## 9. Risks

### 9.1 The INT-pin address latch (highest)

Covered by §5.2, §4.2 and §7.2. The QEMU model puts it under regression; the board loading on
`GPIO_AD_00` is the part QEMU cannot see. **If T1 fails on hardware with "no device", scope
`GPIO_AD_00` during the reset window before touching the firmware** — the failure mode of a wrong
latch is that the device answers at 0x14 instead, which a bus scan across both addresses will show
immediately. The driver's `address()` accessor exists partly so that this is one print away.

### 9.2 400 kHz on a shared bus (medium)

Unproven at this rate on LPI2C5. Mitigation: fall back to 100 kHz, record the finding. A 2-point
read is ~20 bytes per poll, so 100 kHz costs ~2 ms — livable for a polled loop.

### 9.3 Stuck BBF (medium, well understood)

A stuck bus-busy latch needs a **physical power cycle**; soft reset, master reset and a GPIO bus
clear all fail. Symptom: every address NACKs. Known from [[rt1176-rpi-display-hw-bringup]].

### 9.4 Both panels connected (deferred, not ignored)

`J48` pins 26/27 and `J84` pins 11/12 are the **same nets**. With both panels physically attached,
the GT911 (0x5D) shares LPI2C5 with the RPi ATtiny (0x45), FT5406 (0x38) and the unidentified 0x4A
— no address collision, but doubled pull-up loading, and the RPi board needs its own 5 V to be
alive at all. **This design assumes one panel at a time (§1), confirmed for the RK055.** If that
ever changes, it is a new variable to introduce deliberately, not to discover mid-bring-up.

### 9.5 Resolution surprise (low)

Handled by construction (§5.4): scale, print, never assert.

## 11. Open questions for the plan stage

# RT1176 → XRGB8888 through the RK055 LVGL stack (v7) — Design

**Date:** 2026-07-31
**Status:** validated design, ready for an implementation plan
**Fulfils:** the "XRGB8888 (re-records every golden)" roadmap item, open since the v4
scope split (`2026-07-30-rt1176-lvgl-double-buffer-design.md` §2) and carried through
every roadmap note since. Builds on v3–v6, all complete, hardware-verified and merged.

---

## 1. Goal

True 8-bit-per-channel color from LVGL to the glass. **The DSI wire is already 24-bit**
(`DSI_DPI_COLOR_CODING_24BIT`, `mipi_dsi.cpp:227`): today RGB565 framebuffers quantize
to 5/6/5 and the LCDIFv2 expands on scanout, so the missing depth lives entirely in the
framebuffer and the renderer. After v7, all three RK055 LVGL examples
(`lvgl_rk055_panel_test`, `lvgl_rk055_touch_test`, `lvgl_rk055_flip_test`) render
XRGB8888 into 32-bpp framebuffers, the LCDIFv2 scans them out natively, and a grey
gradient that visibly bands today is visibly smooth — certified by a build-variant
"before" (the tearing-demo discipline: the eye sees the defect, then its absence).

**No DSI, D-PHY, or panel-init work.** `mipi_dsi.cpp` is untouched.

**Facts this design stands on, verified in source:**

1. RGB565 is baked in at exactly seven places: `PANEL_BYTES_PER_PIXEL = 2`
   (`panel_config.h:69`, pitch/size derive from it), the hardcoded
   `BPP_RGB565` descriptor field (`lcdifv2.cpp:212`), `LV_COLOR_DEPTH 16` in the
   shared `lv_conf.h:60`, static asserts in both LVGL bindings
   (`lvgl_mipi_panel.cpp:14`, `lvgl_ili9341.cpp:9`), the PXP copy handler's
   RGB565-only shape (`lvgl_pxp_copy.cpp`), `Display::fillScreen`'s `PXP_RGB565`
   surface (`Display.cpp:259`), and the QEMU model's RGB565-only paint path
   (`imxrt_lcdifv2.c:273`) — whose `bpp_bytes` helper already knows ARGB8888.
2. The ili9341 SPI binding genuinely requires RGB565 (its wire format); its assert is
   honest. Color depth must therefore be **per-example**, never a global flip.
3. Both LVGL and MipiDisplay compile from source per example
   (`import_evkb_library`), so per-example compile definitions select depth cleanly.
4. The PXP library already has `PXP_XRGB8888` (`PXP.h:31`).
5. Budget: 64 MB SDRAM on a 32-bit SEMC port (`semc.c:33`). Double buffers grow
   3.7 → 7.4 MB (fine). Scanout fetch doubles per line — the underrun-risk axis §10.1.
6. At 4 B/px the derived constants pass every existing static assert: pitch 2880 is
   32-byte aligned and ≤ 0xFFFF (`panel_config.h:76,94`).

## 2. Scope

**In scope (v7):**

- The per-example depth-selection mechanism (§3) — defaults unchanged, so every
  non-migrating example builds byte-identically.
- MipiDisplay: descriptor derivation + format-aware `fillScreen` (§4).
- The PXP copy handler's dual-format accelerated shape (§5), earned by the bench.
- The bench's dual-format matrix — 14 geometries × 2 formats, `CASES=28` (§6).
- Migration of all three RK055 LVGL examples + the gradient strip in the panel test +
  the `DEPTH_DEMO_565` before-variant (§7).
- QEMU LCDIFv2 model: the 32-bpp draw line (§8) — closing a stated model gap.
- Golden re-records for all three examples (same-commit, stable ×2 + eye).

**Out of scope — named, not silently dropped:**

- **RGB888 (24-bpp packed)** — a third format with worse alignment properties and no
  consumer; the LCDIFv2 supports it, nothing here needs it.
- **ili9341 at 32 bpp** — the SPI wire is RGB565; conversion-on-flush is a different
  milestone with its own measurement.
- **Alpha/blending in the LCDIFv2** (the X byte stays ignored; single layer as ever).
- **LVGL draw-unit PXP, async copies, `flush_ready`-from-ISR** — unclaimed roadmap
  items, unchanged.
- **Underrun *remediation*** (burst/QoS tuning): v7 watches (`UNDERRUNS=0` on
  silicon); if it ever fires, that finding is documented and fixed in its own
  milestone, never hidden by a quiet revert.

## 3. Depth selection: compile-time, statically cross-checked

`LV_COLOR_DEPTH` (`lv_conf.h`) and `PANEL_BYTES_PER_PIXEL` (`panel_config.h`) each
become `#ifndef`-guarded with unchanged defaults (16 / 2). A migrating example opts in
with two cmake compile definitions:

```cmake
target_compile_definitions(<example> PUBLIC LV_COLOR_DEPTH=32 PANEL_BYTES_PER_PIXEL=4)
```

(spelled once via the examples' shared cmake idiom; the definitions must reach the
LVGL and MipiDisplay objects too, which `PUBLIC` on the importing target achieves —
the plan verifies propagation with a compile-time probe before relying on it).

Everything downstream **derives**:

- `PANEL_PITCH_BYTES` / `PANEL_FB_BYTES` already compute from `PANEL_BYTES_PER_PIXEL`;
  both framebuffer allocators already size by `PANEL_FB_BYTES` — they scale for free.
- `panel_config.h` statically asserts `PANEL_BYTES_PER_PIXEL == 2 ||
  PANEL_BYTES_PER_PIXEL == 4`.
- The LVGL binding (`lvgl_mipi_panel.cpp`) replaces `LV_COLOR_DEPTH == 16` with the
  **consistency assert** `(LV_COLOR_DEPTH == 16) == (PANEL_BYTES_PER_PIXEL == 2u)` and
  generalizes the pitch assert to
  `PANEL_PITCH_BYTES == PANEL_WIDTH * (LV_COLOR_DEPTH / 8)`.
  A half-migrated example cannot compile.
- `lvgl_ili9341.cpp` keeps its `LV_COLOR_DEPTH == 16` assert verbatim.

Two live configurations total, each frozen per example at compile time — the same
philosophy as "one panel can ever be live".

## 4. MipiDisplay: descriptor + fillScreen

- **`lcdifv2.cpp`**: the descriptor BPP field becomes a constexpr derivation —
  `PANEL_BYTES_PER_PIXEL == 2 ? BPP_RGB565 : BPP_ARGB8888` — used in `descl5_cfg` and
  its post-write readback check. No other register changes (pitch/size already derive).
- **`Display::fillScreen(uint16_t rgb565)`** keeps its Teensy-compatible signature and
  becomes format-aware: at 4 B/px the PXP surface is `PXP_XRGB8888` and the fill color
  is `displayRgb565To888(rgb565)` — the helper already exists (`Display.h`), and at
  16 bpp the PXP already converts through 888 internally, so the painted color is
  identical at both depths. Same API, same visual result.

## 5. PXP copy handler: dual-format shape

`lvgl_pxp_copy.cpp`'s accelerated shape generalizes to: **both buffers the same
format ∈ {RGB565, XRGB8888}**, with `bpp` derived from the format and threaded through
the offset-base arithmetic (`data + y*stride + x*bpp`) and the stride-sanity check
(`stride >= w * bpp`). PXP surface format maps `LV_COLOR_FORMAT_RGB565 → PXP_RGB565`,
`LV_COLOR_FORMAT_XRGB8888 → PXP_XRGB8888`. Unchanged: height ≥ 2, `threshold_px`,
chain-to-default for every other shape, PXP errors counted apart from shape fallbacks
(`PXP_ERRORS=0` stays pinned by the adopting gates), full-area default copy on error.

The height≥2 rule for 8888 must cite the v7 bench table (§6), not the v6 565
transcript. Expectation: the PXP's advantage widens (CPU bytes double, PXP per-op cost
is near-flat) — but the table decides. **If the 8888 numbers contradict the height≥2
rule, that surfaces to the user before the handler adopts the format**; otherwise P3
proceeds without a stop (the adoption decision for 8888 was taken in this design,
conditional on the numbers holding).

## 6. Bench: dual-format matrix

`lvgl_pxp_copy_bench` runs the same 14 geometry cases at both formats — outer loop
over format, token grows a field:

```
CASE i=<n> f=<565|8888> r=<w>x<h>+<x>+<y> CPU=0x… PXP=0x… MATCH cpu_us=<t> pxp_us=<t>
```

`CASES=28` re-pinned; the gate's per-case greps stay anchored (`^CASE i=$i f=$f `).
Pattern fills stay position-dependent **and become format-dependent** (a different
seed per format) so a copy routed at the wrong bpp cannot checksum clean. Timings stay
hardware-only (`(QEMU: vacuous)` stated, as today). The existing negative test
(skipped `wait()` → per-case divergence goes red) covers both formats because it
drives the same runner over the same matrix.

The 8888 half of the hardware table is the P3 input named in §5. The bench buffers at
4 B/px are ~3.7 MB each — comfortably inside the extmem allocator's budget alongside
nothing else (the bench owns the board).

> **AS SHIPPED (Task-4 re-sync): silicon refuted byte-identity at 32 bpp.** The
> bench's first hardware run failed all 14 XRGB8888 cases while QEMU passed 28/28.
> A DIAG dump proved the PXP writes the X byte as the pipeline's **computed alpha
> (0)** — RGB bytes exact, both 32-bit OUT encodings (RM 52.3.1.22,
> `OUT_CTRL[ALPHA_OUTPUT]=0`; alpha engine unconfigured). The correctness claim
> this section originally stated ("byte-identical destination") was therefore
> false on silicon for 8888 and was hidden by a less-faithful QEMU raw copy.
> Resolution, silicon-wins both ways: the QEMU PXP model now writes X=0 for
> 32-bit RGB outputs (qemu2 `0df62eb15a`), and the bench oracle asserts exactly
> the measured contract — 565 byte-identity; 8888 RGB-identity with in-rect
> X:=0, whole-max-extent checksums intact, so a model OR silicon that *preserved*
> X goes red. The handler (§3/§5) documents the same contract and why ARGB8888
> (where that byte means something) must never join the accelerated shape without
> its own alpha-engine design. Functionally invisible to every consumer (LVGL
> X-byte, LCDIFv2 scanout, 24-bit DSI wire); QEMU and silicon byte-agree, and the
> three migrated examples' goldens verified identical on both. Full record:
> `examples/display/lvgl_pxp_copy_bench/transcript_hw_evkb.txt` (2026-07-31).

## 7. The migrated examples + the banding demo

All three examples gain the two compile definitions. Their gates' *meanings* are
unchanged — every existing pin (drag moves=9, REFRESHES=FLIPS=VSYNCS=120,
VSYNC_TIMEOUTS=0, PXP_ERRORS=0, BUFFERS, DISTINCT=OK, …) carries over; only the
golden checksums change value (same pixels semantically, different bytes), re-recorded
same-commit under the standard ritual (stable ×2 in QEMU + human eye on glass).

**Scene change — panel test only:** a full-width dark-to-light grey horizontal
gradient strip joins the static scene. Grey is the harshest banding case: 5-bit
channels give ~31 visible steps across 720 px at RGB565, and a smooth ramp at 8888.
Touch and flip scenes are unchanged.

**`DEPTH_DEMO_565`** — a cmake variant of the panel test (the `FLIP_DEMO_SINGLE`
pattern): the identical scene built at the default depth, for the before-eye. It is a
demo variant, not a gate, and owns no golden. Ritual: flash the 565 variant → user
reports the banded steps; flash the 8888 build → user reports the smooth ramp; both
recorded in `transcript_hw_evkb.txt` in the same commit as the re-recorded goldens.

**`UNDERRUNS=0`** joins all three examples' printed counters: read from the LCDIFv2
`INT_STATUS_D0` UNDERRUN bit (W1C-read pattern, touching only that bit — the v5 W1C
discipline), printed at end-of-run. In QEMU it is vacuous and stated (the v1
`UNDERRUN` asymmetry pattern); on silicon it is the bandwidth watchdog and the
transcripts must show 0.

## 8. QEMU model: the 32-bpp draw line

`imxrt_lcdifv2.c` gains `lcdifv2_draw_line_argb8888` (X/alpha byte ignored — matches
the single-layer, no-blend hardware config), selected by the descriptor's BPP field
where the paint path today refuses everything but RGB565. `bpp_bytes` already handles
ARGB8888; pitch/size math is already field-driven. The unmodelled-BPP guest-error
stays loud for every other format. This closes a gap the model itself documents —
stricter/more-faithful, the only permitted direction. Without it the re-recorded
goldens cannot gate in QEMU at all.

vmstate: no new fields (the BPP field already lives in the descriptor registers) — no
version bump expected; the plan confirms.

## 10. Risks

1. **Underrun at doubled scanout fetch** (highest silicon risk). The LCDIFv2 reads
   2× the bytes per line from SDRAM contended by LVGL rendering and PXP copies.
   `UNDERRUNS=0` on silicon is the honest watchdog. If it fires: document, and fix in
   its own milestone (§2) — never a quiet revert, never a weakened assertion.
2. **Frame budget pressure**: LVGL writes 2× the bytes into non-cacheable SDRAM; the
   PXP sync copy moves 2×. The flip test's existing pins
   (REFRESHES=FLIPS=VSYNCS=120, VSYNC_TIMEOUTS=0) fail loudly if rendering blows the
   33 ms budget — the correct failure mode, and the P3 table quantifies the copy half
   before adoption.
3. **The QEMU 8888 draw line could mask a silicon format mismatch** (model paints
   what the descriptor claims). Standard mitigation: silicon rituals + the banding eye
   are the authority; QEMU is necessary, never sufficient.
4. **`lv_color_t` widens** at depth 32; any 16-bit color assumption in port code
   fails at compile (the asserts), not subtly at runtime.
5. **Definition propagation**: if a cmake definition failed to reach one library's
   objects, structs would disagree across translation units. Mitigated by the
   consistency asserts living in headers compiled into *every* affected unit, and the
   plan's propagation probe (§3).

## 12. Open questions for the plan stage

1. The exact cmake spelling that guarantees the two definitions propagate to the
   LVGL and MipiDisplay object files (PUBLIC on which target; whether the import
   macros need a knob) — settle with a compile-time probe before P1 lands.
2. Whether the LCDIFv2 `BPP_ARGB8888` field value in `soc/lcdifv2.h` is already
   defined or needs adding beside `BPP_RGB565` (the QEMU header has it; the
   MipiDisplay header may not).
3. The gradient's exact widget form (canvas vs. styled `lv_obj` with a horizontal
   gradient style) — whichever renders deterministically for the golden; the plan
   picks after reading LVGL's gradient dithering behavior (`LV_GRADIENT_MAX_STOPS`,
   dither config) since dithering would *reduce* visible banding at 565 and must be
   configured identically in both variants for an honest before/after.
4. Where `UNDERRUNS` is read/cleared without disturbing the v5 vsync ISR's W1C
   discipline (shared `INT_STATUS_D0` — read-only sample vs. W1C-on-read policy).

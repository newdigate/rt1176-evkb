# W14: a QEMU IW416 SDIO card model — design

Date: 2026-08-19. Follows W13 (Wi-Fi data path stable, no open defect).
Work lands in the **qemu2 tree** (`~/Development/qemu2`,
gitlab.com/Newdigate/qemu-rt1170), NOT in this repo — qemu2 is GPL and the
licence firewall keeps it out of firmware. This repo only gains gate
assertions.

## Why

The M.2 Wi-Fi driver is ~2000 lines of intricate SDIO ring and interrupt
logic with **zero automated coverage**. Every `m2_*` QEMU gate asserts the
CARD-ABSENT fallback, because QEMU's SD model is a memory card that ignores
CMD5. Both serious bugs this subsystem has produced would sail through a
fully green 97-gate sweep:

* **W8's 32-port ring bug** — host read 16-bit bitmaps against a 32-port
  ring; every managed-mode upload landed on a port it never looked at.
* **W12's stranded uploads** — a clear-on-read interrupt bit consumed by a
  non-draining path left frames stranded forever; RX dead until reflash.

Both took days of hand-run silicon soaks to find. A model that implements
the ring and interrupt semantics would have caught both in seconds, on
every sweep, for free.

## Feasibility (checked, not assumed)

* QEMU's `SDCardClass` (`include/hw/sd/sd.h:93`) exposes `do_command`,
  `write_data`, `read_data`. A new SD-bus device can implement the SDIO
  protocol subset our driver uses.
* `hw/sd/sd.c` marks CMD5 `IO_SEND_OP_COND` and CMD52 `IO_RW_DIRECT` as
  `sd_cmd_optional` — i.e. deliberately unimplemented. That is exactly the
  `cmd5-no-response` the gates currently assert, and it is why a separate
  device (not a patch to `sd.c`) is the right shape: memory-card behaviour
  stays untouched.
* `hw/arm/mimxrt1170-evk.c:265-277` attaches `TYPE_SD_CARD` to each USDHC's
  `sd-bus`. The model attaches the same way, selected by a machine property
  so existing gates are unaffected by default.

## Scope — Phase 1 only

**Phase 1 delivers enumeration + firmware download**, i.e. the probe reaches
`iw416_begin=ok` with a real ioport and a firmware-ready handshake, instead
of falling to the card-absent path. That is a self-contained deliverable
and it already covers a large slice of driver code that is untested today.

Phase 1 models:

1. **CMD5 `IO_SEND_OP_COND`** — R4 with the SDIO OCR and function count.
   The driver re-issues with a voltage window until ready
   (`SdioHost.cpp:210-213`), so the model must clear/set the ready bit
   across those calls exactly as a real card does.
2. **CMD52 `IO_RW_DIRECT`** — a register file with per-function address
   spaces. Function 0: the CCCR bits the driver touches (I/O enable, I/O
   ready, bus width, block size). Function 1: the SD8978 registers named in
   `Iw416.h` — `CARD_STATUS_REG 0x5C` (`DN_LD_CARD_RDY|CARD_IO_READY`),
   `HOST_INT_MASK/STATUS`, `IO_PORT_0..2` (yielding ioport `0x10000`),
   `CARD_FW_STATUS0/1`, `READ_BASE_0/1`, and the "new mode" config
   registers the driver writes in `begin()`
   (`HOST_INT_RSR`, `CARD_CONFIG_2_1`, `CMD_CONFIG_0/1`, `CARD_MISC_CFG`).
3. **CMD53 `IO_RW_EXTENDED`** — block-mode transfers against the ioport,
   routed by address so the firmware-download port and the command port are
   distinguishable.
4. **The firmware download handshake** — the bootloader publishes the next
   chunk length in `READ_BASE_0/1`, consumes exactly that many bytes, and
   after the image reports `FIRMWARE_READY` (0xFEDC) in
   `CARD_FW_STATUS0/1`. The model does not interpret the blob; it counts it.

**Explicitly NOT in Phase 1** (they are Phase 2, where the real value is):
the command/event port's request-response semantics, the 32-slot data
rings, `HOST_INT_STATUS` clear-on-read behaviour, and frame injection.
Phase 1 exists to make Phase 2 possible.

## Correctness rule this model must obey

**The model encodes the firmware's documented contract, never our driver's
assumptions.** Where the two differ, silicon decides and the model follows
silicon. Two facts already measured on hardware that the model must respect
when Phase 2 arrives:

* A set bit in the RD bitmap does **not** imply a packet is waiting — stale
  bits linger (W12: ~6100 resyncs found no data).
* The firmware does **not** always raise `HOST_INT_UP_LD` for an upload it
  has queued (W13: three host-side explanations refuted; `stranded`
  survives with all readers verified accumulating).

A model that "helpfully" always raises the interrupt would make the gate
pass while silicon still failed — the exact inversion of this repo's
"silicon wins" rule. These behaviours must be modelled as *options* so a
test can select the hostile case deliberately.

## Gate strategy

* Existing gates keep asserting the card-absent fallback **unchanged** —
  the model is opt-in via a machine property / `-global`, so a default
  sweep is byte-identical. This protects the current 97/0/0 baseline.
* Phase 1 adds ONE new gate asserting real enumeration + firmware-ready on
  `m2_sdio_probe`. That is the first automated proof that any of this
  driver's SDIO path works.
* Sweep target becomes 98.

## Risks

* **QEMU's USDHC controller model may not drive CMD52/53 faithfully.** If
  the controller drops them before the card sees them, Phase 1 stops and
  the controller gets fixed first — that is a legitimate outcome, not a
  failure, and it must be reported rather than worked around in the card.
* Modelling effort is easy to underestimate; Phase 1 is deliberately
  bounded to enumeration + download so there is a landing point.

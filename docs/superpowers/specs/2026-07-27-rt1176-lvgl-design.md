# RT1176 → LVGL 9.4 (v1: "widgets rendered, both panels") — Design

**Date:** 2026-07-27
**Status:** design approved, pending user spec review
**Target board:** MIMXRT1170-EVKB (i.MX RT1176), CM7 only
**Predecessor:** builds on [RPiDisplay](2026-07-23-rt1176-rpi-display-design.md) (800×480 LCDIFv2 framebuffer), [PXP](2026-07-22-rt1176-pxp-design.md), and the ILI9341/SPI display path.
**Fulfils:** the "v5 — LVGL (or a minimal graphics API) on top" roadmap entry of the RPi display spec (§10).

---

## 1. Goal

Render real LVGL widgets on **both** existing displays — the Raspberry Pi 7"
panel (800×480, LCDIFv2) and the ILI9341 (320×240, SPI) — from one shared port
layer, verified in QEMU **and** on silicon.

"Rendered" for v1 means: build an LVGL scene (labels, buttons, a bar), call
`lv_timer_handler()` from `loop()`, and see those widgets on the glass — with a
deterministic checksum of the rendered pixels asserted by a QEMU gate.

This is a **render-only** milestone. The widgets are drawn, not interactive.

## 2. Scope

**In scope (v1)**
- Vendored LVGL 9.4.0 (MIT) as a new sibling library `newdigate/LVGL`.
- An `import_evkb_lvgl()` build macro, modelled on `import_evkb_cmsis_dsp()`.
- An RT1176 port: `lv_conf.h`, a `millis()` tick source, and two `lv_display_t`
  bindings (RPi panel direct-render, ILI9341 partial + `writeRect`).
- One example per panel, each with a QEMU gate and hardware verification.
- `license-audit.sh` extended to cover the new repo.

**Out of scope (deferred, each its own milestone — §9)**
- Touch / any `lv_indev` input. The panel's touch is relayed by the ATtiny88
  (0x45 on LPI2C5/`Wire2`), so it is tractable — but it is a separate register
  map with no QEMU oracle, and it would double this milestone.
- The PXP draw backend (`LV_USE_DRAW_PXP`). v1 is software rendering: correct
  and deterministic first, accelerated second, with a measurement to justify it.
- Filesystem / image decoding / ThorVG / VGLite, an RTOS, animation beyond what
  a static scene needs, and any second framebuffer or tear-free page flipping.

## 3. Facts established during design (all verified, not assumed)

**License — the gating question for this tree.**
- LVGL 9.4.0 core is **MIT** (`middleware/lvgl/LICENCE.txt`). Bundled ThorVG and
  the builtin sprintf are MIT too.
- Running `license-audit.sh`'s own Part-1 regex over the full LVGL tree flags
  **exactly 5 files**, all under `src/libs/vg_lite_driver/VGLiteKernel/`
  (dual-licensed VeriSilicon kernel: `vg_lite_kernel.[ch]`, `vg_lite_hal.h`,
  `vg_lite_hw.h`, `vg_lite_option.h`).
- `src/libs/frogfs/` is **MPL-2.0**. It does *not* trip the Part-1 regex (which
  matches only GNU GPL/LGPL), but it is weak copyleft and unused here.
- RT1176 has no VGLite GPU and `LV_USE_DRAW_VG_LITE` defaults to 0, so **pruning
  `vg_lite_driver/` and `frogfs/` costs nothing and keeps the firewall pristine
  with zero additions to the audit's `ALLOW` list.** Pruning is strictly better
  than allowlisting: it removes the code rather than excusing it.

**Build integration — why the normal Arduino import will not work.**
- `import_arduino_library` globs `${LIB_ROOT}/*.c` and one level per extra
  subdir argument. It is **not recursive**.
- LVGL has **459 `.c` files across 145 directories**, nested up to 14 deep.
  Listing 145 subdir arguments is not a design.
- Precedent exists: **CMSIS-DSP** already bypasses the Arduino glob with a
  dedicated `import_evkb_cmsis_dsp()` macro in `evkb.cmake` (it builds a STATIC
  target, links `teensy_flags` PRIVATE, exposes includes PUBLIC). LVGL follows
  that established pattern rather than inventing a new one.

**Displays available.**
- RPi 7" panel: 800×480 RGB565, `PANEL_FB_BYTES` = 768,000, framebuffer in
  SDRAM, LCDIFv2 scans it out continuously; `Display::framebuffer()` already
  exposes it. HW-verified.
- ILI9341: 320×240, SPI, `writeRect()` blit. **Unmodelled in QEMU.**
- SDRAM is 64 MB (`ERAM` @ 0x80000000), so LVGL's heap is not constrained.

**NXP ships an LVGL PXP draw backend** (`src/draw/nxp/pxp/`, `LV_USE_DRAW_PXP`),
which pairs with this repo's HW-verified `newdigate/PXP` library. Deferred to
v2 (§9) but explicitly not designed out.

## 4. Data path

```
  LVGL widget tree
        |  lv_timer_handler()  (software renderer, CPU, deterministic)
        v
  render buffer (RGB565)
        |
        +-- RPi panel:  buffer IS Display::framebuffer() in SDRAM
        |               flush_cb marks ready; LCDIFv2 scans out. No copy.
        |
        +-- ILI9341:    small partial buffers (OCRAM/DMAMEM)
                        flush_cb -> tft.writeRect(area, buf) over SPI
```

The split matters: on the RPi panel LVGL renders **into the live scanout
buffer** (`LV_DISPLAY_RENDER_MODE_DIRECT`), so there is no per-frame blit at
all. On the ILI9341 the transport is SPI, so partial rendering + `writeRect` is
the only sane mode.

## 5. Component decomposition

### 5.1 New library `newdigate/LVGL` (MIT)

```
LVGL/
  lvgl/                    vendored LVGL 9.4.0, with src/libs/vg_lite_driver/
                           and src/libs/frogfs/ REMOVED (§3)
  port/
    lv_conf.h              RT1176 configuration
    lvgl_rt1176.h/.cpp     begin()/tick wiring, shared entry point
    lvgl_ili9341.h/.cpp    lv_display_t binding for ILI9341_t3
    lvgl_rpi_panel.h/.cpp  lv_display_t binding for RPiDisplay
  LICENSE  README.md  library.properties  VENDORING.md
```

`VENDORING.md` records the upstream version, the exact pruned paths, and the
re-vendoring procedure — so the next bump is mechanical and the pruning is not
folklore.

### 5.2 `import_evkb_lvgl()` in `evkb.cmake`

Mirrors `import_evkb_cmsis_dsp()`:

```cmake
macro(import_evkb_lvgl)
    if(NOT TARGET LVGL)
        evkb_library_dir(LVGL _evkb_lvgl_dir)
        file(GLOB_RECURSE _evkb_lvgl_srcs CONFIGURE_DEPENDS
             "${_evkb_lvgl_dir}/lvgl/src/*.c")
        add_library(LVGL STATIC ${_evkb_lvgl_srcs}
                    ${_evkb_lvgl_dir}/port/lvgl_rt1176.cpp)
        target_include_directories(LVGL
            PUBLIC "${_evkb_lvgl_dir}/lvgl" "${_evkb_lvgl_dir}/port")
        target_compile_definitions(LVGL PUBLIC LV_CONF_INCLUDE_SIMPLE=1)
        target_link_libraries(LVGL PRIVATE teensy_flags)
    endif()
endmacro()
```

Pinned via `_evkb_lib(LVGL ${_dev}/LVGL https://github.com/newdigate/LVGL <SHA> .)`,
where `<SHA>` is filled in after the library's first push — the repo's standard
"push the library, paste its new SHA here, commit" flow (`evkb.cmake` header).
Local-first resolution means development proceeds against `~/Development/LVGL`
before any SHA exists.
The display bindings are compiled by the *example* (not the LVGL target) so that
an example pulling in only ILI9341 never drags in RPiDisplay, and vice versa.

### 5.3 `lv_conf.h` (the decisions that matter)

| Setting | Value | Why |
|---|---|---|
| `LV_COLOR_DEPTH` | 16 | both panels are RGB565 |
| `LV_USE_OS` | 0 | bare-metal `loop()`, no RTOS in this core |
| `LV_USE_DRAW_PXP` / `LV_USE_DRAW_VG_LITE` | 0 | v1 is software render; VGLite absent on RT1176 |
| `LV_USE_STDLIB_MALLOC` | builtin | self-contained pool, no libc heap interaction |
| `LV_MEM_SIZE` | 1 MB, in SDRAM | 64 MB available; generous but bounded |
| tick source | `lv_tick_set_cb(millis)` | reuses the core's existing tick. (`LV_TICK_CUSTOM` was **removed** in LVGL 9 — verified 0 hits in 9.4's `lv_conf_template.h`; the callback is the only mechanism.) |
| fonts | Montserrat 14 + 28 | enough for a real scene; bitmap ⇒ deterministic |
| filesystem / ThorVG / frogfs | off | pruned or unused (§3) |

### 5.4 Display bindings

Both are thin and independently testable — each answers "what does it do, how do
you use it, what does it depend on" on its own.

- **`lvgl_rpi_panel`** — depends on `RPiDisplay`. Creates an `lv_display_t` of
  800×480, `LV_DISPLAY_RENDER_MODE_DIRECT`, buffer = `Display.framebuffer()`.
  `flush_cb` calls `lv_display_flush_ready()` (optionally after a vsync wait).
- **`lvgl_ili9341`** — depends on `ILI9341_t3`. Creates an `lv_display_t` of
  320×240, `LV_DISPLAY_RENDER_MODE_PARTIAL`, two ~320×40 RGB565 buffers.
  `flush_cb` calls `tft.writeRect(x, y, w, h, buf)` then `lv_display_flush_ready()`.

## 6. Public API (v1 — minimal, YAGNI)

```cpp
// port/lvgl_rt1176.h
void lvgl_rt1176_begin();          // lv_init() + lv_tick_set_cb(millis)
void lvgl_rt1176_loop();           // lv_timer_handler(), call from loop()
uint32_t lvgl_render_checksum(const uint16_t *buf, size_t px);  // FNV-1a, gate oracle

// port/lvgl_rpi_panel.h
lv_display_t *lvgl_rpi_panel_create(DisplayClass &display);

// port/lvgl_ili9341.h
lv_display_t *lvgl_ili9341_create(ILI9341_t3 &tft, uint16_t *buf1, uint16_t *buf2, size_t px);
```

Everything else is stock LVGL API — we deliberately wrap nothing that LVGL
already exposes well.

## 7. Verification (two-gate)

**QEMU gate — checksum the render, not the panel.**
LVGL's software renderer is pure CPU work into a RAM buffer, so its output is
**bit-deterministic and independent of whether the panel is modelled**. Each
example builds a fixed scene (no animation, no time-varying text, bitmap fonts),
renders one frame, FNV-1a's the resulting pixels, and prints
`LVGL_SUM=0x……  PASS/FAIL`. The gate asserts it.

This is what makes the **ILI9341 gateable at all** — its panel is unmodelled in
QEMU, so without this the SPI path would be hardware-only. Only the *transport*
(SPI blit, DSI scanout) still needs silicon.

The RPi example additionally reuses the existing `FB_SUM` / `PANEL_SUM`
machinery from `rpi_panel_test`, which proves the pixels actually reach the
virtual bridge.

**Hardware verification.** Both panels show the widget scene, confirmed by eye
(the ILI9341 is QEMU-blind for transport; the RPi panel was HW-verified in its
own milestone). Silicon remains the oracle for anything the model stubs.

**Expected-checksum handling.** The expected value is a *recorded artifact*,
regenerated whenever the LVGL pin, `lv_conf.h`, or the scene changes — never a
hand-derived constant. A checksum mismatch after a pin bump is expected churn,
not necessarily a regression; the gate comment must say so, or someone will
"fix" a real failure by pasting in whatever the board printed.

## 8. Risks / unknowns

- **Flash/RAM footprint.** LVGL 9.4 with two fonts is a meaningful text/rodata
  addition to a 16 MB XIP image. Measure at first link; trim fonts/widgets via
  `lv_conf.h` if it surprises us.
- **Render-buffer determinism.** Anti-aliased font rendering is deterministic,
  but any use of time, RNG, or uninitialised memory in the scene would break the
  checksum. The scene must be explicitly static — this is a gate design
  constraint, not a style preference.
- **Direct-render tearing on the RPi panel.** Rendering into the live scanout
  buffer can tear. v1 accepts it (static scene); double-buffered page flipping
  is a v2 concern.
- **`lv_conf.h` discovery.** LVGL's include mechanism is fussy;
  `LV_CONF_INCLUDE_SIMPLE` + include order is the intended approach and is
  asserted by the build, not assumed.
- **ARM GCC 10 vs LVGL 9.4 C standard.** LVGL expects C99+; confirm no C11-only
  constructs trip the toolchain at first build.

## 9. Roadmap (later specs)

- **v2 — PXP draw backend.** Enable `LV_USE_DRAW_PXP` against `newdigate/PXP`;
  justify with a measured frame-time delta, not vibes.
- **v3 — touch input.** `lv_indev` fed by the ATtiny88 touch relay (0x45,
  LPI2C5/`Wire2`). Hardware-only verification.
- **v4 — tear-free RPi output.** Double buffer + page flip on vsync.
- **v5 — an actual application UI** (camera viewfinder controls, audio surface).

## 10. License firewall (standing constraint)

LVGL enters the tree as **MIT**, pruned of `vg_lite_driver/` (dual-licensed) and
`frogfs/` (MPL-2.0). `~/Development/LVGL` is added to `REPOS` in
`license-audit.sh`, so the new third-party code is genuinely swept rather than
sitting in a blind spot — the whole point of the audit. **No `ALLOW` entry is
added.** If a future LVGL bump reintroduces copyleft-flagged files, the audit
fails loudly and the correct fix is to prune again, not to allowlist.

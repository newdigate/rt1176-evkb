# M2-MAYA-W161 (IW416) bring-up on the MIMXRT1170-EVKB — design

**Date:** 2026-08-17
**Hardware:** u-blox `M2-MAYA-W161-00C` M.2 Key-E card in EVKB socket J54
**Module:** NXP **IW416** — Wi-Fi 4 (802.11a/b/g/n, dual-band 1×1) + Bluetooth/LE 5.2.
WLAN over SDIO, Bluetooth over UART.

## Goal

Both radios, eventually. Wi-Fi station reaching lwIP, and Bluetooth reaching
BLE advertise/scan. Structured as two parallel tracks that converge on a shared
module layer.

---

## 1. Board facts (RevC3, extracted from the design files)

Extracted programmatically from `MIMXRT1170-EVKB-DESIGNFILES_RevC3` —
`pst2kicad/board.net` for connectivity, `BOM/SCH-55139_C3.xlsx` for
populate/DNP. Not taken from any datasheet or SDK board file.

### J54 (M.2 Key-E) to MCU

| M.2 function | J54 pins | MCU pad | Notes |
|---|---|---|---|
| SDIO CLK/CMD/D0–D3 | 9,11,13,15,17,19 | `GPIO_SD_B1_00..05` | uSDHC1 — **shared with microSD J15** |
| BT UART TXD/RXD/CTS/RTS | 32,22,34,36 | `GPIO_DISP_B2_10/11/12/13` | **LPUART2**; ALT2/ALT2/ALT3/ALT3; 1V8 via U354/U355 |
| BT_DISABLE# | 54 | `GPIO_AD_15` (ball M14, "SPDIF_IN" pad) | 10K pull-up R832, 27Ω series R833 |
| WIFI_RST_B | 23 | `GPIO_AD_16` (ball N17, "SPDIF_OUT" pad) | level-shifted to 1V8 through U354 |
| W_DISABLE1# (WL_RST) | 56 | **not connected** | R404 is **DNP** — permanently pulled up to WL_3V3 via R829 |
| WL_DEV_WAKE | 66 | `GPIO_AD_07` (Arduino D8) | via U354 |
| BT_DEV_WAKE | 42 | `GPIO_AD_28` (Arduino D13) | via U354 |
| WIFI_WAKE → host | 21 | `GPIO_AD_29` (Arduino D10) | **via J104, open by default** |
| I²C | 58,60 | `GPIO_LPSR_04/05` | LPI2C5 = `Wire2`, shared with the WM8962 codec |
| BT PCM | 8,10,12,14 | SAI via U354/U355 | J81/J82 open by default |

### Two consequences that constrain everything downstream

**uSDHC1 carries two card slots.** R369–R372/R366/R367 (MCU→M.2) *and*
R1890–R1895 (MCU→J15) are all **fitted**, no DNP on either side. One SD bus,
two sockets. Wi-Fi and the microSD card are mutually exclusive, and with the
M.2 card fitted the existing `storage-memory/sd_test` and
`audio/sd_wav_play_test` hardware runs may misbehave, because an SDIO card
answers CMD3 during SD initialisation.

**The BT UART pads are the Arduino D0/D1/D2 pads** (R2/R3/R8 fitted). Anything
using header D0–D2 collides with Bluetooth — and conversely, a D0↔D1 jumper is
a real loopback for testing LPUART2, provided `BT_DISABLE#` is asserted so the
module is not driving the same wires.

## 2. Architecture

### New sibling library

Per the tree's rule that nothing but examples lives in this repo, one new
sibling repo, using the `MipiDisplay` pattern of selectively-imported
subdirectories:

```
~/Development/M2Radio/
  sdio/         generic uSDHC SDIO host — CMD52/CMD53, CCCR/CIS, DAT1 card IRQ
  iw416/        module: firmware download (UART + SDIO), chip control lines
  wlan/         Wi-Fi driver — contents decided at the W3 fork
  hci/          BT HCI transport over Serial2
  VENDORING.md  provenance for anything vendored
```

Imported as `import_evkb_library(M2Radio sdio iw416 hci)`, so the Bluetooth
track never compiles the SDIO layer and vice versa.

### Core changes (`teensy-cores/imxrt1176`)

Minimal and separately gated:

- `HardwareSerial2.cpp` — LPUART2 on `GPIO_DISP_B2_10/11`, `IRQ_LPUART2`, RX
  daisy-chain select. The core currently implements **only `Serial1`**; there
  is a generic `HardwareSerial` plus a 57-line per-instance table file, so this
  follows an existing shape.
- Hardware CTS/RTS via LPUART `MODIR` (pads `DISP_B2_12/13`). New API surface —
  `HardwareSerial` has no flow-control support today, and BT HCI wants it at
  3 Mbaud.

Nothing else. The SDIO layer uses the USDHC register definitions already added
for the SdFat port.

### Explicitly not doing

Refactoring SdFat's `SdioTeensy` into a shared USDHC primitive. It is a
working, gated driver. The new SDIO layer **copies** the clock/pinmux/reset
sequence it already proved on this silicon rather than restructuring it. Two
drivers, one peripheral, mutually exclusive in hardware anyway.

### uSDHC1 ownership

Documented rule plus a runtime guard: whichever library claims uSDHC1 first
owns it; the second asserts loudly rather than quietly corrupting the bus.

## 3. Phase map

### Phase 0 — board facts, no hardware

`docs/m2-evkb-revc3.md`: the table above, the DNP findings, the uSDHC1 sharing
landmine. Costs no board time and is what a second session working on SD needs.

### Track B — Bluetooth

| | Deliverable | Un-fakeable assertion |
|---|---|---|
| **B1** | Core: `Serial2` on LPUART2 + hardware CTS/RTS | Physical loopback jumper J9 pin 2 ↔ pin 4, with `BT_DISABLE#` asserted so the module is not fighting the jumper |
| **B2** | `GPIO_AD_15` out of reset → NXP UART firmware download → HCI Reset → Read Local Version | The controller's own company identifier and LMP subversion |
| **B3** | BLE advertise + scan | Real advertising reports from real devices nearby |

**B3 needs no host stack.** LE advertising and scanning are pure HCI commands
(`LE Set Advertising Data` / `Advertising Enable` / `Set Scan Enable`), so the
track reaches a beacon and a working scanner without importing an Apache-2.0
BLE host. A GATT host stays a separate, later, optional decision.

### Track W — Wi-Fi

| | Deliverable | Un-fakeable assertion |
|---|---|---|
| **W1** | `sdio/`: uSDHC1 in SDIO mode, CMD5 → OCR, CMD3 → RCA, CMD7, CMD52 → CCCR, CIS tuple walk | Manufacturer code (expect `0x02DF`, Marvell/NXP) and device ID read off the wire |
| **W2** | CMD53 block transfers, DAT1 card interrupt, firmware download over SDIO | Firmware-ready handshake after the image lands |
| **W3** | **Fork:** MLAN + bare-metal MOAL / FreeRTOS / thin clean-room | decision, not code |
| **W4** | Driver as far as `scan` | Actual SSIDs in the room |
| **W5** | Associate to a WPA2-PSK AP | Association state + BSSID from a real AP |
| **W6** | lwIP netif, DHCP, TCP echo | Reuses `networking/lwip_test`'s existing peer scripts |

lwIP is already a sibling repo at `NO_SYS=1` with a working `networking/lwip_test`,
so W6 inherits both the stack and its test peers.

### Convergence

B2 and W2 share the firmware blob and the chip-control lines — that is what
makes running the tracks in parallel cheap rather than duplicative. Both live
in `iw416/`.

### Plan granularity

This spec covers the whole programme; implementation plans are written **per
phase group**, not for the whole thing at once. The first plan covers
**Phase 0 + B1 + W1** — the board-facts doc, `Serial2`, and the SDIO probe.
Later plans are written after their predecessor's hardware result is in, since
each one's shape depends on what the silicon said.

### The W3 fork (deferred by decision)

Options, to be judged once W2 shows how the chip behaves:

1. **Vendor MLAN + write a bare-metal MOAL** — the VGLite pattern (vendor
   verbatim, own `port/baremetal/`). Battle-tested driver, no RTOS. MOAL
   assumes threads with blocking waits on command responses, so the shim means
   restructuring those into a cooperative state machine.
2. **Bring FreeRTOS in** (MIT, licence-clean) and use NXP's existing FreeRTOS
   MOAL as-is. Fastest to working Wi-Fi. Changes the character of the tree —
   everything else is bare-metal Arduino-style and lwIP is `NO_SYS=1`.
3. **Thin clean-room driver** — only the IW416 host command interface needed for
   STA + WPA2-PSK. The firmware performs the 4-way handshake, so no supplicant
   is required. Smallest code, cleanest licence story, most protocol archaeology.

NXP's driver splits as MLAN (the bulk, portable, used as-is) + MOAL (OS
abstraction, must be ported); NXP ships MOAL for FreeRTOS and Zephyr, neither of
which this tree has. The licence is advertised as BSD-3-Clause but gets a
per-file survey before we believe it — the VGLite lesson.

## 4. Verification

### Gate strategy: absent-fallback now, model later

| Phase | QEMU gate | What it proves |
|---|---|---|
| B1 | **Real.** Console on `-serial` slot 0, LPUART2 capture on slot 1 | LPUART2 genuinely transmits and receives |
| B2 | Absent-fallback | The ELF reaches the download attempt and times out cleanly instead of hanging |
| W1 | **Meaningfully negative.** QEMU attaches an SD *memory* card, which by spec ignores CMD5 | The enumerate path concludes "no IO function" rather than mis-parsing |
| W2+ | Absent-fallback | Same shape |

QEMU models all 12 LPUARTs (`imxrt_lpuart`) and both USDHCs (`imx-usdhc` +
`sd-card`), and binds the Nth `-serial` to LPUART(N+1). Adding an SDIO-function
or IW416 model to qemu2 is deferred until silicon behaviour is known and there
is something concrete to model against.

### Two disciplines that bite harder here than usual

**Absent-fallback gates are the vacuity-prone kind.** "No device found" is also
what a dead ELF produces. Every fallback gate emits a *positive* token proving
it arrived there deliberately — a reason code plus a subsequent heartbeat, not
an absence — and each goes into `tools/gate-vacuity.test.sh` coverage.

**A green `m2_sdio_probe` does not mean the module works.** It asserts the
module-absent fallback. Every claim about the IW416 itself lives in
`transcript_hw_evkb.txt` and nowhere else. Same relationship
`display/vglite_probe` has to the GC355.

The sweep target moves from 94 to 94 + N, **re-measured by running the sweep**,
never by counting files.

### Hardware etiquette (another session shares the board)

1. The M.2 card is fitted and shares uSDHC1 with J15, so the other session's SD
   hardware runs may fail for reasons unrelated to their changes. Phase 0's doc
   is the fix.
2. The documented flash recipe begins `pkill LinkServer; pkill redlinkserv;
   pkill crt_emu_cm_redlink`, which yanks the board out from under an active
   debug session. Coordinate before running it.
3. Wi-Fi work needs the microSD slot empty — a bus constraint, not a preference.
4. Do not hold the VCOM while programming (existing `CLAUDE.md` rule).

Phase 0 and all QEMU work need no board, so the programme front-loads into the
part that cannot collide. Hardware access is batched: build everything, then one
flash-and-read window.

## 5. Risks and open questions

**Both radios may share one firmware image.** `sdiouartiw416_combo_v0.bin`
serves both, and on NXP combo parts the image is downloaded once, not once per
interface. Downloading over UART and then over SDIO may need a chip reset, or
make the second download a no-op. B2 and W2 are therefore designed to tolerate
an already-initialised chip rather than assuming a cold one.

**Firmware provenance.** The blob is redistributable NXP binary, not open
source. It is not copyleft, so `license-audit.sh`'s grep passes — but that is
the VGLite trap: green answers *is there copyleft here*, not *may we ship this*.
**Decision: fetch at configure time rather than vendor**, reusing the local-first
/ `EVKB_FORCE_FETCH` machinery in `evkb.cmake`. This sidesteps the
redistribution question instead of answering it.

**Silicon-only surfaces.** QEMU cannot catch any of these:

- the DAT1 async card interrupt — SdFat's driver never configures it, no model exists;
- LPUART2 at 3 Mbaud — the core's baud divisor arithmetic may not reach it cleanly;
- whether `GPIO_AD_15` and `GPIO_AD_16` need a particular assertion order. The
  u-blox pinout PDF is image-only, so pin 23's exact module-side meaning is
  unconfirmed. Driving both high is very likely right but is a guess until the
  board says otherwise. **Resolve empirically in the first hardware session.**

**Largest single unknown: W3.** See the fork options above. Deferring it is the
mitigation — W2 reveals the chip's behaviour before the commitment is made.

**Less risky here than on rt1062:** the `imxrt1176` core never writes `SCB_CCR`,
so OCRAM is coherent for free and the D-cache DMA trap that cost a full debug
session on the RT1060 does not apply. To be verified rather than assumed, since
the firmware download path rests on it.

### Open before W2

- Exact firmware variant for MAYA-W161 — u-blox may ship its own rather than NXP's stock image.
- Redistribution terms of that image, if fetch-at-configure turns out not to be possible.
- Whether combo firmware download must happen exactly once, via one interface.
- Per-file licence survey of MLAN, if the W3 fork goes that way.

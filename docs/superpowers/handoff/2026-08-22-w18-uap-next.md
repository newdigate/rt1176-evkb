# W18 handoff: the uAP works — what is left, and what will bite

u-blox **M2-MAYA-W161** (IW416/SD8978) on **MIMXRT1170-EVKB RevC3**, branch
`claude/wifi-host-mode-m2-ap-b2f304`. M2Radio at **`300d32b`**, pushed, and `evkb.cmake` pins it. Sweep is **116 gates**.
★ **qemu2 `c3b816be51` or later is required** — five `m2_uap_*` gates go RED (not
SKIP) without it; `docs/KNOWN-BROKEN-GATES.md` has the diagnosis.

**Read before forming any theory:**
`examples/networking/m2_uap_probe/transcript_hw_evkb.txt` (Phase 0 + FAULT 1)
and `examples/networking/m2_uap_lwip/transcript_hw_evkb.txt` (everything
since). Both are written to be read by someone who was not there.

## What W17 settled, and how solidly

The card **hosts a WPA2-secured access point**. A client joins, is handed an
address by our DHCP server, and moves traffic both ways. Every claim below has
an oracle that is not our own print:

| claim | oracle |
|---|---|
| the AP is on air | a foreign radio (this Mac) sees the SSID appear between START and STOP, on the configured channel, with the configured security |
| a client joined | the card's own `STA_LIST` names the client's MAC; the client names the card's |
| RX works, tagged | 99/99 frames `bss_type=1`; first frame decoded as the client's gratuitous ARP carrying its MAC and IP |
| TX works | an ARP **reply** whose target fields existed only in the request we built |
| the upstack works | a UDP payload string absent from our image arriving at a bound socket |
| DHCP works | the client takes `192.168.44.100` — an address absent from its sketch |
| WPA2 works | the client associated, impossible without the 4-way handshake |

## The things that will bite, in rough order of likelihood

1. ★ **There is no harmless `SYS_CONFIGURE`.** A *minimal* one kills the
   command port outright — no reply, nothing again for the rest of the firmware
   life. Reproduced 5/5 across three shapes (bare action; action+CHAN_BAND GET;
   action+MAX_STA_CNT SET). A **populated** configuration is accepted. So never
   "just query" the uAP config: a GET is exactly the shape that wedges.
   Recovery is a **card reset** (M.2 reset GPIO + blob re-download, no MCU
   reboot); nothing shorter works — 30 retries over ~90 s never recovered, and
   the data port had nothing to drain.
2. ★ **The join event id depends on the security mode.** Open →
   `EVENT_MICRO_AP_STA_ASSOC` (0x2D); WPA2 → `EVENT_MICRO_AP_RSN_CONNECT`
   (0x51), which follows the handshake. A gate asserting 0x2D passes on an open
   AP and fails on a WPA2 one for a link that works. Assert on `STA_LIST`'s
   count instead — and note the event word carries the BSS in bits 31:24
   (`EVENT_GET_BSS_TYPE`).
3. ★ **Broadcast from an AP is lossy and that is not a bug.** 802.11 ACKs and
   retries unicast and does neither for broadcast: measured 34/40 broadcast vs
   **40/40 unicast**, same client and channel. Consequences: any protocol that
   depends on broadcast reaching a uAP client must tolerate ~15% loss (our DHCP
   replies did, and that was a real defect — now unicast per RFC 2131 §4.1), and
   **a gate asserting "N sent, N received" over a broadcast path is flaky by
   construction** and will look like a firmware regression.
4. **Membership must be polled, not accumulated.** `sta_count` comes from
   `STA_LIST`; events only say *when*. A missed event makes a delta-tracked
   count drift permanently. `sta=?` (not 0) is the no-card value — "never
   read" and "read as empty" are different claims.
5. **The uAP interface reports the same MAC as the STA interface.** No separate
   address is provisioned; do not assume one.

## The soak (criterion 5) — done

**28.8 min, 46 join/leave cycles.** One distinct health signature across every
2 s sample (`sort -u` on the health line), so no counter was ever non-zero — not
merely zero at the end. The frame accounting closes **exactly**:
`rx_bss1 1353 = 1214 UDP + 47 DISCOVER + 46 REQUEST + 46 rejoin ARPs`,
`rx_bss0=0`, `unrouted=0`.

`dhcp_disc` runs exactly **one** ahead of `dhcp_req` — and it is a constant, not
a rate: the delta appears at the first exchange and never moves across 46 joins.
A first-exchange race with the netif coming up; ongoing loss is ruled out. (An
interim ratio taken at one moment read this as "~3% loss"; a ratio cannot tell a
constant from a rate, and it took a second point to separate them.)

## What is left

* **Routing/NAT between STA and uAP** — the W17 handoff deferred this until
  everything else soaked. It now has. This is the natural next feature, and it
  is where **STA+uAP concurrency** first has to actually work.
* ~~QEMU: a uAP surface / a station / a station that sends~~ — **all done.**
  Sweep is **115**. `inject-bss=` lets the model tag an injected frame, so
  `m2_uap_lwip[data]` gates the uAP RX path and `[mistag]` gates the handoff's
  named hazard — STA-tagged frames arriving at a uAP-only guest must be refused
  and counted, not delivered. **Only `[mistag]` can catch a tag-ignoring
  demux**; `[data]` passes on one, measured.
  ~~What is left in QEMU: TX~~ — also done (qemu2 `c3b816be51`). The model reads the
  TxPD's `bss_type` and `tx-loopback` echoes each frame back on the interface it
  was sent on, so `m2_uap_lwip[tx]` gates `sendDataFrameBss()`. **Sweep 116.**
  Every part of the uAP driver now has a gate; what is left is FEATURES, not
  coverage.
* ~~QEMU: a uAP surface~~ — done. The command surface now exists
  (qemu2 `5ac785cf09`, `-global iw416-sdio.uap=on`) and two gates ride it —
  `m2_uap_probe[uap]` (the FAULT 1 regression) and `m2_uap_lwip[uap]` (the
  bring-up sequence, order asserted). Sweep is now **113**. What is still
  missing is a modelled client that associates: without one `STA_LIST` reports
  zero, no MICRO_AP events fire, and **join/leave/data gates still cannot
  exist**. Criterion 4 is therefore PART met — configure/start/stop are gated,
  join/leave/data are not.
  ★ When you add the station, note what the events must do: the join event id
  DEPENDS ON THE SECURITY MODE (open 0x2D vs WPA2 0x51), and the event word
  carries bss_type in bits 31:24. A model that always emits 0x2D would let a
  gate assert something silicon does not do.
* **DHCP hardening** — leases never expire, a full pool is counted
  (`dhcp_full`) but nothing is reclaimed, and RENEW is answered as a fresh
  REQUEST. The server lives in the example, not the library, deliberately:
  promote it once it has faced those.
* **TX aggregation with a mixed-BSS batch** is untested. `iw416NetifInitUap`
  deliberately does not enable aggregation; the STA init does, and it is a
  driver-wide setting.
* **The full 111-gate sweep** and a **real-AP `m2_lwip_test` session** — the
  two halves of criterion 3 not done here. The 14-gate regression subset that
  covers the driver changes is green (all seven `m2_rx_demo` gates included).

## Bench notes

* **ESP8266** at `/dev/cu.usbserial-0001` is the station:
  `tools/esp8266-uapclient`. It disables its own SoftAP on boot, cycles
  join/leave on a timer (`CLIENT_NO_CYCLE` to stop that), and takes its
  passphrase from a generated `client_creds.h`.
* **Credentials are mechanical, not careful.** `-DM2_UAP_PSK` at configure
  time → `uap_creds.h` in the build dir, which CMake **checks is gitignored**
  and refuses to write to otherwise → copied file-to-file to the client by
  `make-creds.sh`. Outside 8..63 chars is a FATAL_ERROR, because WPA2 rejects
  a short one and the AP would come up **open while the log said WPA2**. Never
  printed. W6 leaked live passwords into *pushed* history; redacting at HEAD did
  not undo it.
* ★ **The MCU-Link debug port drops** after repeated `LinkServer run` +
  `pkill` cycles: `Wire not connected`, `Unable to retrieve DAPInfo`. The
  board stays alive and heartbeating — **check VCOM first**, a live board with a
  dead probe is this and not a firmware fault. Only a physical repower fixes it;
  it happened twice.
* ★ **Scans: presence is reliable, ABSENCE IS NOT.** Two invocations disagreed
  (each triggers its own scan and macOS ages cached entries between them), and
  separately a single scan reported the SSID absent while the AP was
  demonstrably up with a client on it. So: capture one scan to a file and query
  that file, and never treat a single "absent" as a negative control — repeat it
  until it is stable.
* `m2_uap_lwip` hosts **indefinitely** — no `BSS_STOP`. The board beacons
  until reset or reflashed.

## Method notes worth keeping

* The FAULT 1 hypothesis came from asking the **reference** what a real
  bring-up sends, not from guessing at shapes — `wlan_uap_cmd_sys_configure`
  refuses to build without a configuration, which is what made "populated vs
  minimal" the axis to test.
* When several explanations compete, **eliminate the one under your own control
  first** — it is free. The uAP-events question had three candidates; inspecting
  our own demux killed one before any bench time was spent.
* **A missing field looks nothing like a field reading 0.** An `arduino-cli
  upload` silently did not take, and it was caught only because the client's
  `sent=` counter was *absent* rather than zero. Print counters at both ends
  of a link test.
* **Writing down what a thing does not do** is a good way to notice that it does
  something worse: documenting the DHCP server's limits is what surfaced its pcb
  answering on any netif.

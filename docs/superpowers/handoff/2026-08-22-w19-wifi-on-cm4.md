# W19 handoff: run the Wi-Fi stack (uAP **and** STA) from the CM4 core

**Start by brainstorming, not by coding.** This is a design question with at
least three viable shapes and one measured constraint that kills the obvious
one. Nothing below is a plan — it is the evidence a plan should be argued
from.

> ★ **Use the `cm4-bringup` skill.** It is mandatory for any dual-core work in
> this tree and it is not optional here: this task touches core-release
> sequencing, peripheral-to-core assignment, the TCM/backdoor windows and the
> qemu2 machine model — **four separate entries on that skill's risk-trigger
> table, every one of which MANDATES an EVKB probe before the code is
> trusted.** Read `.claude/skills/cm4-bringup/SKILL.md` and its
> `references/cm4-roadmap.md` first; the roadmap is a LIVING document and this
> work becomes **Phase 8**.

## Where things stand

The Wi-Fi stack works and is fully gated **on the CM7** (sweep 119). The card
hosts a WPA2 AP with DHCP, joins as a station, and moves traffic both ways —
see `docs/superpowers/handoff/2026-08-22-w18-uap-next.md` for what that
covers and what it does not.

★ **Phase 7.4 is still ★HW-UNVERIFIED** (`dualcore/cm4_graph_usb_capstone`:
QEMU-green, never run on the board). The roadmap calls running it "the whole
point of the phase". **Decide deliberately whether Phase 8 starts before that
is closed** — Phase 7 is the precedent for "the CM4 owns a complex peripheral
and services it fast enough", which is exactly the claim Phase 8 rests on.
Starting Phase 8 on top of an unverified Phase 7 is a choice, not an oversight;
make it consciously.

## Measured constraints — start here, they rule out the obvious design

Everything in this section was measured in this repo on 2026-08-22, not
recalled. Re-measure anything you intend to lean on.

| fact | value | why it matters |
|---|---|---|
| **SDIO data path is PIO** | `DATPORT` (USDHC 0x20), word loop on BREN/BWEN; no ADMA, no descriptors | ★ The big enabler. "DMA cannot reach CM4 private TCM" — the constraint CLAUDE.md warns about — **does not bite this data path at all**. Buffers may live in CM4 TCM. The cost is that the CORE does every copy. |
| **USDHC1 IRQ** | **133** (RM interrupt table) | The CM4 already dispatches external NVIC IRQs (Phase 2C, MU IRQ 118), so the mechanism exists. Whether IRQ 133 can be *routed* to the CM4 is unverified. |
| **CM4 TCMs** | fixed **128K ITCM + 128K DTCM** | Not the CM7's FlexRAM; a separate fixed pair. This is the skill's own silicon-truth note. |
| `m2_uap_lwip` code, **no blob** | text **52,296** / data **16,310** / **bss 148,032** | ★★ **bss alone exceeds the 128K DTCM.** The full uAP+lwip+DHCP build does not fit CM4 DTCM as it stands. |
| IW416 firmware blob | ~**400 KB** binary (2.4 MB as the `.inc` hex array) | ★★ **15× the largest CM4 image ever built here** (`cm4_graph_usb_capstone` is 27,468 bytes). The blob cannot live in a CM4 image. |

### What those two ★★ rows mean

**The obvious design — "move the whole stack to the CM4" — does not fit.** Not
marginally: the blob alone is larger than both CM4 TCMs combined, and the
lwip build's bss alone is larger than DTCM. Any workable shape has to answer
*where the blob lives* and *where the RAM comes from* before anything else.

## Three shapes worth arguing about

Brainstorm these against each other; do not assume the first is best.

1. **CM7 brings the card up, CM4 owns it thereafter.** The CM7 does the reset
   sequence and the 400 KB blob download from its XIP flash, then hands over —
   the CM4 takes USDHC1, the driver and the netifs. Fewest new unknowns about
   the blob; the handover instant is the whole risk (who owns the registers,
   what happens to an in-flight interrupt, how the CM4 learns `ioport`).
2. **CM4 owns everything, blob read from shared memory.** The CM7 stages the
   blob into OCRAM and the CM4 downloads it. Cleaner ownership, but adds an
   address-map question the risk-trigger table says must be probed, and the
   CM4 must reach ~400 KB of OCRAM at SDIO speed.
3. **Split by role: CM4 runs the driver, CM7 keeps lwip.** Frames cross the MU
   or a shared ring. Keeps the 148 KB bss on the CM7 side, but puts an IPC hop
   in the data path that W11/W16 spent a lot of effort removing from it.

★ Whatever you pick, **say which core owns USDHC1 and never let both touch
it.** CLAUDE.md's rule is that each peripheral instance is assigned to one
core, and the failure mode if that slips is not a clean error.

## Open questions, roughly in the order they should be answered

1. **Can USDHC1's IRQ 133 be routed to the CM4 at all?** Triangulate the RM
   interrupt table against the SDK, then probe. Phase 7 answered the same
   question for USB and is the template.
2. **Where does the blob live, and who pushes it?** See the three shapes.
3. **Where does the RAM come from?** 148 KB bss vs 128 KB DTCM. Options: place
   bss in OCRAM (the linker can), shrink lwip pools, or split the stack.
   Measure the real lwip footprint rather than trusting the current pool sizes
   — they were never tuned.
4. **Is the CM4 fast enough for a PIO data path?** W11 measured the CM7 link as
   sensitive to bus and CPU cost, and PIO means the core copies every byte.
   The CM4 is slower and has no D-cache benefit here. **This is a throughput
   question, and QEMU cannot answer it** — the same reason Phase 7.4's number
   cannot be measured in emulation.
5. **Does the W15 interrupt-driven service still work?** The DAT1 card
   interrupt is the mechanism; it is gated by CCCR 0x04 on the card side and
   the SDHCI plumbing on the host side. Both are CM7-verified only.
6. **Simultaneous STA + uAP from the CM4** — the datasheet supports it, this
   repo has never run it on either core, and it multiplies every ring and
   event question. Treat as a later phase, not part of Phase 8.

## What NOT to assume

* **Do not assume the CM7 driver works unchanged.** It is written against
  CM7 assumptions that were never questioned because there was one core.
* **Do not assume QEMU proves it.** The uAP surface is modelled
  (`iw416-sdio.uap=on`, qemu2 `c3b816be51`) and 119 gates cover the CM7 path,
  but qemu2 models no M4 pipeline. Every timing claim needs the board.
* **Do not weaken a gate to make a dual-core variant pass.** If a gate cannot
  express the CM4 case, write a new one and demonstrate it RED first.
* **Do not touch the ring/interrupt contracts casually.** W8, W12, W15 and W16
  were each dug out of that hot path; `m2_rx_demo`'s seven gates exist because
  of it and must stay green.

## Practical notes

* **The main checkout has no `build/` for `m2_uap_probe` or `m2_uap_lwip`**, so
  a sweep there reports **SKIP** for their eight gates until they are built.
  Build them before trusting a count — a SKIP hides in a total.
* Sweep is **119**; five `m2_uap_*` gates need qemu2 ≥ `c3b816be51` and go RED
  (not SKIP) without it. `docs/KNOWN-BROKEN-GATES.md` has the diagnosis.
* Run long gate sets **in batches**. A gate that "fails" inside a long loop may
  simply have been in flight when the outer command's own timeout fired; that
  cost time twice this session.
* Bench: ESP8266 station on `/dev/cu.usbserial-0001`
  (`tools/esp8266-uapclient`, credentials via `make-creds.sh`, never inline).
  The MCU-Link debug port drops after repeated `LinkServer run` + `pkill`
  cycles and needs a physical repower — the board stays alive and
  heartbeating, so **check VCOM before blaming firmware**.

================================================================================
THE BUG THIS TRANSCRIPT EXISTS FOR: 16-PIXEL BLIT ALIGNMENT
================================================================================

FIRST GPU RUN, sum=0xB1A12E39. Every token said success -- INIT=OK,
FLUSHED=PASS, LVGL_BYTES=3686400 (a full 720x1280x4 paint), and a stable
checksum that was neither blank nor equal to the software one. On glass:

  - knob GEOMETRY was correct. Crescents were crescents (NOT full rings, so
    the arc-clamp failure did not return under LV_USE_FLOAT), faces, rings,
    detent ticks and all four states rendered right.
  - the TITLE TEXT was mangled: glyphs fragmented and overlapping.
  - TICK MARKS smeared, each trailing repeated horizontal streaks rightward.

Vector paths clean, small BLITS corrupt. A per-row smear is the signature of a
stride mismatch on a blit source.

DIAGNOSIS came from dumping all 65 v7 feature bits (see vglite_probe's
transcript): gcFEATURE_BIT_VG_16PIXELS_ALIGN = 1. The GC355 requires
16-pixel-aligned blit sources. Phase 2a's compat shim had ANSWERED 0 for that
bit -- an invented value, and the wrong one -- and even after the re-vendor
made the real value visible, LVGL was still allocating glyph and layer buffers
with the SOFTWARE renderer's defaults from port/lv_conf.h:
LV_DRAW_BUF_STRIDE_ALIGN 1 and LV_DRAW_BUF_ALIGN 4.

FIX: the VGLITE build sets both to 64 (16 px x 4 B at LV_COLOR_DEPTH 32).
Measured after: sum changed to 0x15F05E35, and text and ticks are clean.

★ ONE ASSERTION HAD TO BE RELAXED, and it was too strict rather than wrong.
port/lvgl_mipi_panel.cpp asserted LV_DRAW_BUF_STRIDE_ALIGN == 1 because DIRECT
mode makes LVGL write the scanout buffer at its own stride, so padding would
skew every line. But the real invariant is that the panel pitch not get padded,
and 720 x 4 = 2880 = 45 x 64 -- so a 64-byte alignment pads nothing here. The
assertion is now PANEL_PITCH_BYTES % LV_DRAW_BUF_STRIDE_ALIGN == 0, which is
the property actually required. Keeping == 1 would have forced a false choice
between a correct GPU blit path and a correct direct-render panel when the
arithmetic says both hold.

Verified the software path is untouched: its golden is still 0x513C4DB8 and its
QEMU gate still passes.

★ WHAT CAUGHT THIS, because it is the reusable part. The checksum was stable,
non-blank, and different from software -- everything a gate looks for. Two more
checks passed too: LVGL_FLUSHED=PASS and a full-screen LVGL_BYTES. All of that
is consistent with a corrupted frame. Only a human looking at the panel found
it. Same lesson as the knob pilot's arc clamp: a determinism check certifies
reproducibility, never correctness.

METHOD: flashed VCOM-free (load -> verify -> attach reader -> reset).
Note an M.2 MAYA-W161 card is fitted to this board; two SWD connect failures
earlier in the session were cleared by resetting the debugger port.


================================================================================
OPEN: RESIDUAL GPU-ONLY ARTIFACTS (2026-08-17)
================================================================================

The 16-pixel alignment fix cleared the mangled text and the smeared ticks. It
did NOT clear everything. Still present on the GPU path:

  - some glitching artifacts
  - the LOWER PART of each knob face is a slightly different colour, a band
    rather than a smooth transition

★ ESTABLISHED BY A/B ON THE SAME PANEL, which is what makes this a GPU finding
rather than a widget one: the SOFTWARE build of the IDENTICAL scene, from
identical SynthUI widget code, renders CLEAN -- no glitches, no colour band.
Confirmed by eye, both builds, same session, same board. So the artifacts are
in the VG_LITE draw path, not in synthui_knob's drawing.

That A/B was worth doing rather than assuming. The colour band sits at roughly
the same height within every knob, which superficially looks like a per-widget
effect -- exactly the reading that would have sent the next person to debug the
widget. The software render refutes it.

LEADING HYPOTHESES, in the order worth testing, NEITHER TESTED:

1. ALPHA / PREMULTIPLY on the shading overlay. gcFEATURE_BIT_VG_LVGL_SUPPORT
   reads 0 on this silicon, so LVGL premultiplies in SOFTWARE
   (lv_draw_vg_lite_img.c:66). The knob's face shading is drawn as a
   semi-transparent overlay -- "lighter and darker depending on the angle" --
   and a blend or premultiply mismatch there would tint exactly one region of
   the face while leaving opaque geometry correct. This matches the symptom
   most closely: it is a COLOUR error confined to a blended area, with every
   opaque path right.

2. TESSELLATION TILING. The buffer is 256x256 over a 720x1280 screen, so the
   GPU renders in bands with boundaries at y=256, 512, 768, 1024. Knob rows sit
   at y=120, 295, 470, 645 with height 150, so rows 0, 2 and 3 STRADDLE a
   boundary and row 1 does not. If the band edge is the cause, row 1 should be
   clean and the others not -- a cheap discriminating observation to make on
   glass before changing anything.

3. SCISSOR. gcFEATURE_BIT_VG_SCISSOR reads 1, so lv_draw_vg_lite.c:141 now
   takes a path that was dead under the old driver. Newly-live code is worth
   suspecting on principle.

Hypothesis 2 is the cheapest to test and needs no rebuild: look at whether row 1
(the second row down) is clean while rows 0, 2 and 3 band.

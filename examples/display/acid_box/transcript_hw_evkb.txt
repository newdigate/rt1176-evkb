★ THE "LOCKUP" WAS THE DEBUGGER. HOW THE FIRST SESSION WAS FOOLED.
================================================================================

The first session recorded: systick frozen at 1739 across 20 s of wall time,
PC=0xFFFFFFFE, $lr=$sp=0, s_sum holding its correct final value, touch never
begun, and no fault handler ever reached. Every one of those is explainable
without any firmware defect, and three of them were reproduced deliberately
this session on a board proven to be healthy.

★ ARTEFACT 1 -- REGISTER READS ON A RUNNING CORE RETURN ZEROS.
  LinkServer's gdbserver in --attach mode reports a FAKE STOP to gdb and hands
  back 0 for every core register while the target runs on. Demonstrated on the
  HEALTHY control, synthui_step_test: `info registers` gave r0-r15 = 0, sp = 0,
  lr = 0, pc = 0 -- while systick_millis_count advanced 2 ms between two reads
  in the same session. So `$lr=0, $sp=0` was never data. (Memory reads in this
  mode are live and non-invasive, which is why every symbol read stayed
  trustworthy. Writes are silently dropped: `set var transport.playing_ = 1`
  read back false.)

★ ARTEFACT 2 -- A DEBUGGER-HALTED CORE LOOKS EXACTLY LIKE A FROZEN ONE, AND
  THE FROZEN NUMBER SURVIVES RESETS.
  Once a probe session latches C_HALT, the core stays halted after gdb
  detaches. `wiretimedreset` does NOT clear it -- so the firmware never
  re-runs startup, systick_millis_count keeps its old DTCM value, and every
  later read returns the SAME number. This session read 16390 identically
  across two resets and 35 s of wall time and very nearly concluded "dead at
  16.39 s". It is the same shape as "1739, FROZEN across 20 s".
  THE ONLY HONEST LIVENESS TEST IS DHCSR: bit 17 S_HALT and bit 24
  S_RETIRE_ST say whether the core is halted or retiring instructions.
  A frozen counter says nothing until you have read them.

★ ARTEFACT 3 -- "NO FAULT HANDLER RAN" IS THE EXPECTED RESULT UNDER A DEBUG
  CONNECT, EVEN WITH NO FAULT.
  LinkServer's connect script sets DEMCR = 0x010007F1/0x010007F0, arming
  VC_HARDERR, VC_BUSERR, VC_MMERR, VC_INTERR, VC_STATERR, VC_CHKERR and
  VC_NOCPERR. Vector catch halts the core INSTEAD OF running the handler, so a
  breakpoint on fault_isr can never be hit whether or not a fault occurred.
  It was never evidence of an unstackable fault. And in fact CFSR and HFSR
  read 0 at every reading this session: no fault ever happened at all.

★ AND THE BRACKET WAS A BASE RATE, NOT A CLUE.
  The first session bracketed the death between acid_box.cpp:591 and :603 and
  read the tightness as strong evidence. The setup() timeline, measured on
  silicon (below), shows why that bracket is simply where the firmware
  usually IS: it is 55% of setup()'s wall-clock time. A debugger halt landing
  during boot is MORE LIKELY to land there than anywhere else.

  setup() checkpoint timeline, silicon, milliseconds (g_diag_t):

      204  after CONSOLE.begin + delay(200)
      204  after AudioMemory(24)

BENCH PROTOCOL NOTES EARNED THIS SESSION
  - Never SIGKILL a LinkServer session mid-flash-program. Doing so left the

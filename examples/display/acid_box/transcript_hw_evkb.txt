================================================================================
★ THE "LOCKUP" WAS THE DEBUGGER. HOW THE FIRST SESSION WAS FOOLED.
================================================================================

The first session recorded: systick frozen at 1739 across 20 s of wall time,
PC=0xFFFFFFFE, $lr=$sp=0, s_sum holding its correct final value, touch never
begun, and no fault handler ever reached. Every one of those is explainable
without any firmware defect, and three of them were reproduced deliberately
this session on a board proven to be healthy.

★ ARTEFACT 1 -- REGISTER READS ON A RUNNING CORE RETURN ZEROS.
  LinkServer's gdbserver in --attach mode reports a FAKE STOP to gdb and hands
  back 0 for every core register while the target runs on. Demonstrated on the
  HEALTHY control, synthui_step_test: `info registers` gave r0-r15 = 0, sp = 0,
  lr = 0, pc = 0 -- while systick_millis_count advanced 2 ms between two reads
  in the same session. So `$lr=0, $sp=0` was never data. (Memory reads in this
  mode are live and non-invasive, which is why every symbol read stayed
  trustworthy. Writes are silently dropped: `set var transport.playing_ = 1`
  read back false.)

★ ARTEFACT 2 -- A DEBUGGER-HALTED CORE LOOKS EXACTLY LIKE A FROZEN ONE, AND
  THE FROZEN NUMBER SURVIVES RESETS.
  Once a probe session latches C_HALT, the core stays halted after gdb
  detaches. `wiretimedreset` does NOT clear it -- so the firmware never
  re-runs startup, systick_millis_count keeps its old DTCM value, and every
  later read returns the SAME number. This session read 16390 identically
  across two resets and 35 s of wall time and very nearly concluded "dead at
  16.39 s". It is the same shape as "1739, FROZEN across 20 s".
  THE ONLY HONEST LIVENESS TEST IS DHCSR: bit 17 S_HALT and bit 24
  S_RETIRE_ST say whether the core is halted or retiring instructions.
  A frozen counter says nothing until you have read them.

★ ARTEFACT 3 -- "NO FAULT HANDLER RAN" IS THE EXPECTED RESULT UNDER A DEBUG
  CONNECT, EVEN WITH NO FAULT.
  LinkServer's connect script sets DEMCR = 0x010007F1/0x010007F0, arming
  VC_HARDERR, VC_BUSERR, VC_MMERR, VC_INTERR, VC_STATERR, VC_CHKERR and
  VC_NOCPERR. Vector catch halts the core INSTEAD OF running the handler, so a
  breakpoint on fault_isr can never be hit whether or not a fault occurred.
  It was never evidence of an unstackable fault. And in fact CFSR and HFSR
  read 0 at every reading this session: no fault ever happened at all.

★ AND THE BRACKET WAS A BASE RATE, NOT A CLUE.
  The first session bracketed the death between acid_box.cpp:591 and :603 and
  read the tightness as strong evidence. The setup() timeline, measured on
  silicon (below), shows why that bracket is simply where the firmware
  usually IS: it is 55% of setup()'s wall-clock time. A debugger halt landing
  during boot is MORE LIKELY to land there than anywhere else.

  setup() checkpoint timeline, silicon, milliseconds (g_diag_t):

      204  after CONSOLE.begin + delay(200)
      204  after AudioMemory(24)
      301  after wm.enable() + volume            <- codec over LPI2C5:  97 ms
      751  after Display.begin()                 <- panel bring-up:    450 ms
      751  after lvgl_rt1176_begin()
      754  after lvgl_mipi_panel_create()
      754  after preset + patch + transport cfg
      754  after pump.begin()
      791  after build_ui() + screen load        <- whole UI built in:  37 ms
     1053  after the frame_done wait loop        <- first full paint:  262 ms
     2022  after the 3.6 MB checksum   (== :591) <- lvgl_sum_feed:     969 ms
     2022  after the two console printfs
     2022  after Wire2.begin()/setClock()(== :602)
     2103  after touch.begin()         (== :603) <- GT911 bring-up:     81 ms
     2103  setup() COMPLETE

  setup() spans 204 -> 2103 ms. lvgl_sum_feed() ALONE owns 1053 -> 2022 ms,
  969 of those 1899 ms. Half of boot is spent inside the single statement the
  first session bracketed.

★ THE SIGNATURE, REPRODUCED ON DEMAND.
  With the shipped image flashed and verified 4/4, free-running and proven
  healthy, one ordinary probe attach produced:

      DHCSR  = 0x00030003  (C_HALT=1, S_HALT=1 -- halted BY THE DEBUGGER)
      systick_millis_count = 1933      <- frozen, and in the same 1.7-2.0 s
                                          neighbourhood as the reported 1739
      s_sum  = 0x811C9DC5              <- the FNV-1a OFFSET BASIS: reset, and
                                          the checksum not yet finished
      touch._begun = false, _devId = 0
      CFSR / HFSR = 0 / 0

  That is the first session's report, on a board that had just been measured
  running for 184 s. The remaining difference is instructive: at 1933 ms s_sum
  reads the BASIS, because lvgl_sum_feed accumulates into a plain static that
  the compiler keeps in a register until the call returns. The first session
  recorded s_sum at its CORRECT FINAL value TOGETHER WITH systick=1739 and
  touch._begun=false -- and those three cannot come from one instant: a final
  s_sum means t >= 2022 ms, an unbegun touch means t < 2103 ms, so t is in an
  81 ms window that 1739 is not in. The readings were taken across different
  attaches, each freezing the target at a different point, and then read as
  one snapshot. That is the deepest version of the trap: not one wrong number,
  but several right numbers from different moments assembled into a story.

  (PC = 0xFFFFFFFE remains the one datum this session did not reproduce; every
  attach here reported PC = 0 or a real address. It is not load-bearing: the
  lockup it was taken to prove is refuted by 402 s of measured uptime, zero
  fault bits, and a live touch controller.)

================================================================================
METHOD, AND THE BUILD-DIAG VARIANT
================================================================================

The MCU-Link VCOM still carries ZERO bytes, so nothing here used a serial
console. Everything is SWD: framebuffer dumps (tools/rt1170-screenshot.py),
symbol reads and SCB register reads (tools/rt1170-swdprobe.py, added this
session).

build-diag/ is a SECOND build directory of this same example, configured with
-DACIDBOX_DIAG=1:

    cmake -B build-diag -DCMAKE_TOOLCHAIN_FILE=../../../toolchain/rt1170-evkb.toolchain.cmake \
          -DCMAKE_C_FLAGS=-DACIDBOX_DIAG=1 -DCMAKE_CXX_FLAGS=-DACIDBOX_DIAG=1

It adds volatile globals (g_diag_t, g_diag_rms, g_diag_bars, g_diag_played)
read by symbol over SWD, and starts the transport itself at 4000 ms so the
audio path can be MEASURED while the VCOM is dead. It exists because the
shipped contract is BOOT SILENT and that claim must not be softened to make
measurement convenient -- so the measurement lives in a build the gate never
compiles.

★ THE SHIPPED IMAGE IS UNCHANGED, AND THAT IS CHECKED, NOT ASSERTED. The
loadable binary of build/acid_box.elf after this session's edits is
BYTE-IDENTICAL (275456 bytes, objcopy -O binary, cmp) to the ELF that produced
the golden before them, the shipped build contains zero g_diag symbols and
zero diag_mark call sites, and ./run_qemu.sh still prints
ACIDBOX_UI_SUM=0xD3BC88D7 and PASSes. LICENSE-AUDIT: PASS.

BENCH PROTOCOL NOTES EARNED THIS SESSION
  - Never SIGKILL a LinkServer session mid-flash-program. Doing so left the
    target unreachable at the wire level ("Wire not connected", "Hardware
    interface transfer error" on every transfer, dapinfo included) while the
    MCU-Link itself still enumerated perfectly over USB. Neither
    wiretimedreset nor any software recovery restored it; a full board POWER
    CYCLE did.
  - `wiretimedreset` does not restart firmware on a core that a probe has
    latched halted. Watch systick RESTART FROM ~0, or you are re-reading a
    corpse that was never a corpse.
  - LinkServer's `run` subcommand is silent for a minute or more while it
    programs. Silent is not hung.

================================================================================
WHAT THIS GATE PROVES
================================================================================
Touch -> pattern -> SOUND, end to end, in one run:

  * the box boots with the right picture (FNV-1a golden over the whole 720x1280
    XRGB8888 framebuffer, taken before the input device exists),
  * it boots SILENT (no bar line ahead of the play tap),
  * an injected finger presses PLAY and the sequencer starts,
  * an injected finger taps step cell 2 -- a REST in the preset -- and the
    firmware writes the pattern (STEP[2]=note33 gate1),
  * and the AUDIO graph's own per-step RMS table changes at exactly that step:
    silent in a window that closed before the tap, sounding in a window that
    opened after it,
  * an injected drag turns the CUTOFF knob and the filter follows, strictly
    downward.

WHAT IT DOES NOT PROVE.  QEMU renders LVGL in software and models the WM8962
rather than driving one, so nothing here is a statement about the RK055 panel,
the codec's analogue path, or the GT911 on real glass.  Silicon confirmation is
owed and is the capstone plan's Task 8.

★ LOCAL-ONLY QEMU DEPENDENCY.  The gestures are injected through qemu2's
`imxrt.gt911` `touch-script` property, which is not upstream.  A fresh clone
sees this gate red for that reason alone -- the same class as `sai1-rxinject`
and the rt1062 half of `usb_descriptor_survey`.  That is the GPL firewall
working, not a regression.

Bar 3 is the reason the gate takes the LAST bar before the drag rather than the
first bar after the tap, and the reason it insists on seeing at least two of
them: a bar whose window was already open when the finger landed is not evidence
either way, and treating it as evidence would make the gate fail intermittently
for a reason that has nothing to do with the firmware.

MARGINS: sounding > 0.02, rest < 0.005 -- 4x separation between the two
thresholds, the acid_bass_test convention for float DSP (measured windows with
margin, never bit-goldens).  The measured room either side is far larger: gated
steps read 0.36..0.44, which is 18x the sounding floor, and rests read
0.0001..0.0006, which is 8x under the rest ceiling.  Neither number may be moved
to make a run pass.

★ BAR 1 IS NOT A VALID WINDOW and the capture above shows why: step 0 reads
0.1843 in bar 1 against 0.42+ in every bar after it.  The transport records
boundaries strictly inside (from, to], so it never emits tick 0 at phase 0 and
step 0 first fires at the loop seam.  The gate refuses a bar-1 pre-edit window by
name ("pad 2 too short") instead of lowering the 0.02 floor to accommodate it.

THE TOUCH SCRIPT — generated, never hand-counted
================================================================================
Regenerate with exactly this, run from the example directory (this is the block
that produced the committed touch_script.txt; 636 instants):

  {
    echo "# acid_box gate script -- GENERATED, never hand-counted.  Regenerate with"
    echo "# the block quoted in run_qemu.sh's header (and in transcript_qemu.txt)."
    ... header comment lines ...
    for i in $(seq 25);  do echo R; done     # pad 1
    echo "P 80 3"; echo R                    # tap PLAY
    for i in $(seq 300); do echo R; done     # pad 2
    echo "P 31 53"; echo R                   # tap STEP CELL 2
    for i in $(seq 300); do echo R; done     # pad 3
    echo "P 12 13"; echo "P 12 14"; echo "P 12 15"
    echo "P 12 16"; echo "P 12 17"; echo "P 12 18"
    echo R                                   # drag CUTOFF down
  } > touch_script.txt

(The committed file carries the full header comments; the instants are exactly
the ones above.  `grep -cE '^(P|R|\.)' touch_script.txt` == 636.)

★ THE CADENCE IS 20 ms, NOT THE 40 ms THE PLAN SAYS.  Read out of the model, not
assumed: IMXRT_GT911_STEP_MS == 20 in
~/Development/qemu2/include/hw/i2c/imxrt_gt911.h:195, with INT_PULSE_MS == 1
carved out of it by imxrt_gt911_tick()'s two-phase timer.  The pads follow from
that and one audio constant:

    bar    = 16 sixteenths at 128 BPM      = 1.875 s AUDIO time
    wall   = 1.875 / 0.81                  ~ 2.31 s   (this tree's measured
                                                       QEMU audio clock ratio)
    instants per bar = 2.31 s / 20 ms      ~ 116

    pad 1 =  25 instants ~ 0.5 s   settle after the first frame
    pad 2 = 300 instants ~ 6.0 s   ~ 2.6 bars before the edit
    pad 3 = 300 instants ~ 6.0 s   ~ 2.6 bars between the edit and the drag

Confirmed against the run above: the play tap lands, bars 1 and 2 complete, the
edit lands during bar 3, bars 4 and 5 complete, the drag lands.  Exactly the
2.6-bar spacing the arithmetic predicts.

20 ms is a FLOOR, not a period: imxrt_gt911_tick() refuses to advance while the
previous instant is unread, so a guest busy with a full-screen software render
stretches an instant instead of dropping it.  Load can therefore only make the
pads LONGER in audio time -- more bars in each window -- which is the safe
direction for every assertion here.  Measured (see "under load" below).

GEOMETRY.  The three tap points are percentages of the 720x1280 panel, derived
from acid_box.cpp's absolute placement:

    PLAY         pos(540,16) size(70,48)     -> 540..610 x  16..64
                 (80%, 3%)  = pixel (576, 38)                    inside
    step cell 2  pos(8+2*88, 640) size(82,82)-> 184..266 x 640..722
                 (31%, 53%) = pixel (223,678)                    inside
    CUTOFF knob  pos(15,90) size(150,150)    ->  15..165 x  90..240
                 (12%, 13%) = pixel ( 86,166)                    inside

★ THE DRAG STOPS AT 18% (y=230) ON PURPOSE.  synthui_knob does not set
LV_OBJ_FLAG_PRESS_LOCK, so LVGL re-runs its hit test on every read while the
press is held: a sample past the knob's bottom edge (y=240) would hand the press
to a different object and end the drag as PRESS_LOST with no further CUTOFF
lines.  1% of the panel is 12.8 px and the widget turns 280 deg per 200 px
(SYNTHUI_KNOB_DRAG_FULL_PX), so each 1% sample is ~18 deg: five prints, and the
knob does not reach its end stop, which is what keeps them strictly decreasing
rather than flattening onto a clamp.

UNDER LOAD.  Re-run with 6 spinners on an 8-core host: PASS, pre-edit window
bar 2, post-edit window bar 4 (bar 5 idle).  The windows MOVE and the gate does
not care, which is the point of selecting them by position relative to the
STEP token rather than by a pinned bar number.  The guards that would fire if a
pad ever became too short name the pad ("pad 2 too short", "pad 3 too short",
"the post-edit window is not provably post-edit") rather than failing as a
mysterious RMS mismatch.

================================================================================
TIMING BUDGET
================================================================================
Idle wall time 18 s: ~4.5 s boot (panel bring-up + one 720x1280 software render
+ touch bring-up), then ~13 s of script.  The runner does not sleep a fixed
window -- it polls for the third CUTOFF line, which is the last scripted
gesture, then waits 2 s for the tail of the drag.  Ceiling 120 s (240 x 0.5 s),
QRUN_TIMEOUT 150 s, gate_init's default 600 s backstop above that.  The poll
also breaks on `kill -0` failing, so a fatal model error costs 0.5 s rather than
the whole ceiling -- which is what makes proof (c2) above quick.

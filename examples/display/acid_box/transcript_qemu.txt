WHAT THIS GATE PROVES
================================================================================
Touch -> pattern -> SOUND, end to end, in one run:

  * the box boots with the right picture (FNV-1a golden over the whole 720x1280
    XRGB8888 PRESENTED framebuffer — the logical 1280x720 scene after the CW90
    PXP present — taken before the input device exists),
  * every present is right: the rotated pipeline counts no PXP errors, the
    damage path demonstrably ran, and the equality guard finds the presented
    buffer equal to the rotated canvas at boot and after every bar,
  * it boots SILENT (no bar line ahead of the play tap),
  * an injected finger presses PLAY and the sequencer starts,
  * an injected finger taps step cell 2 -- a REST in the preset -- and the
    firmware writes the pattern (STEP[2]=note33 gate1),
  * and the AUDIO graph's own per-step RMS table changes at exactly that step:
    silent in a window that closed before the tap, sounding in a window that
    opened after it,
  * an injected drag turns the CUTOFF knob and the filter follows, strictly
    downward.

WHAT IT DOES NOT PROVE.  QEMU renders LVGL in software and models the WM8962
rather than driving one, so nothing here is a statement about the RK055 panel,
the codec's analogue path, or the GT911 on real glass.  The PXP rotation is
QEMU's model too: display/pxp_rotate_probe measured that model bit-exact
against silicon, but the landscape acid_box itself has not yet run on the
board.  Silicon confirmation is owed (capstone plan Task 8 for the portrait
build; landscape plan Task 12 for this one).

★ LOCAL-ONLY QEMU DEPENDENCY.  The gestures are injected through qemu2's
`imxrt.gt911` `touch-script` property, which is not upstream.  A fresh clone
sees this gate red for that reason alone -- the same class as `sai1-rxinject`
and the rt1062 half of `usb_descriptor_survey`.  That is the GPL firewall
working, not a regression.

Regenerate with exactly this, run from the example directory (this is the block
that produced the committed touch_script.txt; 640 instants):

  {
    echo "# acid_box gate script -- GENERATED, never hand-counted.  Regenerate with"
    echo "# the block quoted in transcript_qemu.txt (run_qemu.sh's header points there)."
    echo "#"
    echo "# One instant per line, IMXRT_GT911_STEP_MS = 20 ms apart.  Percentages are"
    echo "# of the PHYSICAL 720x1280 panel; each is the CW90 map of a logical target"
    echo "# in acid_box.cpp's geometry block: physical (px,py) = (719-ly, lx), then"
    echo "# px*100/720 and py*100/1280, rounded.  The model computes"
    echo "# res*pct/100 in integers, so P 94 85 -> (676,1088) -> logical (1088,43)."
    echo "#"
    echo "# pad 1: 25 instants (~0.5 s); pads 2/3: 300 instants (~2.6 bars at 128 BPM"
    echo "# under this tree's ~0.81x QEMU audio clock)."
    for i in $(seq 25);  do echo R; done     # pad 1
    echo "P 94 85"; echo R                    # tap PLAY        (logical 1090,44)
    for i in $(seq 300); do echo R; done     # pad 2
    echo "P 80 22"; echo R                    # tap STEP CELL 2 (logical 282,146)
    for i in $(seq 300); do echo R; done     # pad 3
    for x in 19 18 17 16 15 14 13 12 11 10; do echo "P $x 7"; done   # drag CUTOFF: logical (91, 583->647), downward
    echo R
  } > touch_script.txt

★ THE CADENCE IS 20 ms, NOT THE 40 ms THE PLAN SAYS.  Read out of the model, not
assumed: IMXRT_GT911_STEP_MS == 20 in
~/Development/qemu2/include/hw/i2c/imxrt_gt911.h:195, with INT_PULSE_MS == 1
carved out of it by imxrt_gt911_tick()'s two-phase timer.  The pads follow from
that and one audio constant:

    bar    = 16 sixteenths at 128 BPM      = 1.875 s AUDIO time
    wall   = 1.875 / 0.81                  ~ 2.31 s   (this tree's measured
                                                       QEMU audio clock ratio)
    instants per bar = 2.31 s / 20 ms      ~ 116

    pad 1 =  25 instants ~ 0.5 s   settle after the first frame
    pad 2 = 300 instants ~ 6.0 s   ~ 2.6 bars before the edit
    pad 3 = 300 instants ~ 6.0 s   ~ 2.6 bars between the edit and the drag

Confirmed against the run above: the play tap lands, bars 1 and 2 complete, the
edit lands during bar 3, bars 4 and 5 complete, the drag lands during bar 6.
Exactly the 2.6-bar spacing the arithmetic predicts.

20 ms is a FLOOR, not a period: imxrt_gt911_tick() refuses to advance while the
previous instant is unread, so a guest busy with a full-screen software render
stretches an instant instead of dropping it.  Load can therefore only make the
pads LONGER in audio time -- more bars in each window -- which is the safe
direction for every assertion here.  Measured (see "under load" below).

GEOMETRY.  The UI is a LOGICAL 1280x720 frame presented rotated 90 degrees
clockwise on the 720x1280 panel: logical (lx,ly) sits at physical (719-ly, lx).
The GT911 model takes percentages of the PHYSICAL panel and computes
raw = res*pct/100 in integers (res 720x1280), so each tap is a logical target
from acid_box.cpp's geometry block, mapped to physical and rounded to a whole
percent -- and then truncated by the model, which is why the landing point is
not quite the target centre:

    PLAY         PLAY_X=1040, BAR_Y=20, 100x48           -> 1040..1139 x  20..67
                 centre (1090,44) -> physical (675,1090) -> 93.75%, 85.2%
                 -> P 94 85 -> raw (676,1088) -> logical (1088, 43)    inside
    step cell 2  LANE_X0+2*108=232, LANE_Y0=96, 100x100  ->  232..331 x  96..195
                 centre (282,146) -> physical (573, 282) -> 79.6%, 22.0%
                 -> P 80 22 -> raw (576, 281) -> logical ( 281,143)    inside
    CUTOFF knob  KNOB_X0=16, KNOB_Y0=520, 150x150        ->   16..165 x 520..669
                 drag logical (91, 582..647) -> physical (137..72, 91)
                 -> 19.0%..10.0%, 7.1% -> P 19 7 .. P 10 7
                 -> raw (136..72, 89) -> logical (89, 583..647)        inside

(physical (px,py) = (719-ly, lx); percent = px/7.2 and py/12.8, rounded; the
model's raw = res*pct/100 truncates, and logical = (raw_y, 719-raw_x).  Move a
widget and only its line changes.)

★ THE DRAG STOPS AT LOGICAL y 647 ON PURPOSE, 22 px inside the knob's bottom
edge (669).  The knob does not set LV_OBJ_FLAG_PRESS_LOCK, so LVGL re-runs its
hit test on every read while the press is held: a sample past that edge would
hand the press to a different object and end the drag as PRESS_LOST with no
further cutoff prints.  It is a DOWNWARD logical drag (cutoff strictly
decreasing, the portrait build's assertion unchanged); rotated, it is a
LEFTWARD raw drag, and the rotated indev makes that invisible to LVGL.  1 % of
the panel's 720 px short axis is 7.2 raw px, so each sample moves 7 or 8
logical px; the widget turns 280 deg per 200 px (SYNTHUI_KNOB_DRAG_FULL_PX over
its explicit ±140 range), ~10 deg a sample and 64 px ~ 90 deg in all -- from
+21.5 deg to about -68 deg, well clear of the -140 end stop, which is what
keeps the prints strictly decreasing rather than flattening onto a clamp.  The
portrait build's six 1 % samples of the 1280 px axis covered the same 64 px,
which is why both drags finish at 103.3 Hz.

★ `-rotate -90` UNDOES THE CW90 PRESENT, so the PNG is the upright landscape UI
(1280x720); without it the picture lies on its side.  ★ `-alpha off` IS
LOAD-BEARING: the X byte is 0 in the presented buffer, so read as BGRA every
pixel is fully transparent -- measured, the PNG came out with mean alpha 0 and
looks blank in a viewer, which is a false "blank frame" scare.  The PIL form of
the same image: Image.frombytes('RGB',(720,1280),raw,'raw','BGRX',2880)
.transpose(Image.Transpose.ROTATE_90) -- byte-identical to the convert output,
checked.

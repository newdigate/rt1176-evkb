WHY THIS TOOK THREE FIXES (all silicon-only -- no QEMU gate can see any of them,
because the gates run the SW path and acid_box's gate has no BT):

  1. Black screen / frozen setup.  acid_box clocks the graph from the SAI DMA
     ISR, so AudioOutputBluetooth::update() ran from power-on and encoded SBC on
     every block before begin() -- starving setup() (SWD: m_blocks=77k, m_l2=null,
     no panel/console).  Fix: skip all work in update() until the media channel
     exists.

  2. Livelock at stream start (media never flowed, loop frozen after begin()).
     update() encoded SBC IN the SAI ISR; flash-resident, it overran the 2.9 ms
     block period, so the ISR never yielded and poll() never ran -- ring full,
     ~99% dropped, s_btBegun never set.  Fix: DECOUPLE -- update() only copies PCM
     into a ring; poll() (main loop) does the encode + drain.

  3. Choppy (pcmdrops climbing, loop at a few Hz).  Two causes:
     (a) BtLink logged every Number_Of_Completed_Packets event; at media rate the
         console flood blocked the loop (M2Radio fix -- suppress 0x13).  [Measured
         to be secondary.]
     (b) The SBC encode was flash-resident (~2-3 ms/block vs ~0.5 ms in ITCM);
         at 344/s it nearly saturated the CM7 before the compositor ran.  Fix:
         route only Sbc.cpp to ITCM (the one per-block-hot object), evict the
         example's setup() (2564 B, runs once) to flash for the room.  THIS closed
         the budget: pcmdrops 1739 -> 0 ongoing.

ESP32 sink ("EVKB-SINK") no-regression: reaches STREAMING through the same path
(also discovered as an audio device in the inquiry above, bd=88:13:BF:58:86:9E).

ATTRIBUTION (B, streaming under wiggle, per second of wall time):
  svc   ~155-163 ms  = the L2cap ACL write SPINNING in Serial2's 64-byte TX ring.
                       Wire time: txb (~43.5 KB/s) x 3.333 us/B = ~145 ms, minus 64 B
                       of ring per packet (~14 ms) = ~130 ms; the ~25-35 ms remainder
                       is ~30-40 us per iteration of flash-resident service code
                       (SdpServer/L2cap/Avdtp::service).  WIRE-BOUND, as predicted --
                       the spec's rule for fix 1 fires.
  poll  ~58 ms       = enc ~50 ms (345 blocks x ~145 us: the ITCM SBC encode is 3x
                       cheaper than the 0.5 ms estimate) + drain ~7.5 ms.
  yield ~2-4 ms      (HciPump; ~25 ms/s when idle at 7100 iterations/s).
  lvgl  ~700 ms      = render + vsync fence for the same 30 frames as A (A's 885 ms
                       includes ~170 ms of idle lv_timer_handler() spins at 20k it/s).
  print ~50 ms       (instrument + bt_hb; see the instrument note).
  => Bluetooth costs ~30% of the loop's wall time and the 8-knob scene has the
     slack to absorb it: frames/s, frame interval, worst frame and touch latency
     are all UNCHANGED (touch p95 reads better in B -- human variance, not a gain).

THE RESPONSIVENESS DEFECT IS THE BRING-UP, NOT THE STREAMING.  The first loop()
iteration after boot ran the blocking A2dpSource::connect() for 16.8 s
(max_us=16834971 above; charged to `print` because the connect sits in that lap):
the panel was up, the sequencer ready, and the UI completely dead until
bt_streaming -- and setup()'s ~12 s BT firmware download blocks the same way just
before it.  With no headset in range the 5 s connect retry blocks for the inquiry
timeout every time.  That is the "noticeably less responsive" of NEW-33; the
steady-state numbers never showed it.  Fix: idleUi() -- every blocking BT wait
in this tree takes an idle callback, and acid_box now passes one that runs the
UI half of loop() (next section).

INSTRUMENT NOTES.  (1) The CM7 runs with NO instruction cache -- the imxrt1176
core's startup never writes SCB_CCR -- so flash-resident code executes from
FlexSPI at raw QSPI speed: the LOOPSTAT summary's early return costs 4.6 us per
idle iteration in A (print=~340 ms/s at 74k it/s) and ~32 us in B, where the
per-iteration M2Radio service chain also runs from flash and evicts it from the
FlexSPI AHB buffer.  Same instrument in both builds, so the A/B is fair; the
frame/touch numbers are untouched (a 4.6 us jitter against 33 ms frames).  It is
also why the flash-resident SBC encode measured 2-3 ms/block in NEW-9 and why
Sbc.cpp had to move to ITCM.  Enabling the I-cache is a core change with its own
issue.  (2) The loopstat line is two printf calls: Print::printf clamps at 128 B.

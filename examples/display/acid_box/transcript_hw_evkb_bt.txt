WHY THIS TOOK THREE FIXES (all silicon-only -- no QEMU gate can see any of them,
because the gates run the SW path and acid_box's gate has no BT):

  1. Black screen / frozen setup.  acid_box clocks the graph from the SAI DMA
     ISR, so AudioOutputBluetooth::update() ran from power-on and encoded SBC on
     every block before begin() -- starving setup() (SWD: m_blocks=77k, m_l2=null,
     no panel/console).  Fix: skip all work in update() until the media channel
     exists.

  2. Livelock at stream start (media never flowed, loop frozen after begin()).
     update() encoded SBC IN the SAI ISR; flash-resident, it overran the 2.9 ms
     block period, so the ISR never yielded and poll() never ran -- ring full,
     ~99% dropped, s_btBegun never set.  Fix: DECOUPLE -- update() only copies PCM
     into a ring; poll() (main loop) does the encode + drain.

  3. Choppy (pcmdrops climbing, loop at a few Hz).  Two causes:
     (a) BtLink logged every Number_Of_Completed_Packets event; at media rate the
         console flood blocked the loop (M2Radio fix -- suppress 0x13).  [Measured
         to be secondary.]
     (b) The SBC encode was flash-resident (~2-3 ms/block vs ~0.5 ms in ITCM);
         at 344/s it nearly saturated the CM7 before the compositor ran.  Fix:
         route only Sbc.cpp to ITCM (the one per-block-hot object), evict the
         example's setup() (2564 B, runs once) to flash for the room.  THIS closed
         the budget: pcmdrops 1739 -> 0 ongoing.

ESP32 sink ("EVKB-SINK") no-regression: reaches STREAMING through the same path
(also discovered as an audio device in the inquiry above, bd=88:13:BF:58:86:9E).

=== THE FPS MISS, AND WHAT IT IS EVIDENCE FOR ===

Criterion (Linear NEW-25): "sustained >= 30 fps while animating". Measured
20.6 fps, median frame 48.6 ms. Four boots agree to 0.07 %, so this is a
property of the code and not of the sample.

★ WHAT PHASE B ACTUALLY ANIMATES, which is the whole reading of the number:
every 15 ms timer tick it moves the cue to the next key and re-lits a third of
the bank. `set_cue` invalidates the WHOLE key (the widget's spec chose that:
"the ring is the outer 3.5 units on four sides; four strips would save little"),
so one tick dirties TWO whole keys for the cue plus up to sixteen halo boxes —
about 20,000 px of cue damage that only ever changes a 3.5-unit bezel ring.
This is the worst case the widget can be put in, and it is exactly the case
NEW-50 (narrow set_cue to the bezel band) addresses.

★ SO THE FIRST LEVER IS NEW-50, NOT A GPU COMPOSITOR. NEW-23's fader missed the
same criterion on software and went to the GC355, and that is the reflex this
measurement should NOT trigger: the fader animates a CAP that really does move,
while this widget is repainting 10,000 px to change a ring. Measure NEW-50
first; if a bezel-band invalidation does not clear 30 fps, then a compositor is
the honest answer and NEW-25's plan says to file it as its own issue.

★ acid_box, the widget's real consumer, is NOT this case: it moves the cue once
per 33 ms poller tick, not sixteen times per 15 ms. Its own bench numbers are in
examples/display/acid_box/transcript_hw_evkb.txt.

★★ BUT THE TAIL GREW, DETERMINISTICALLY, AND IT IS FILED AS NEW-53.
  us_max = 288557 288456 288497 288406 288649 288576 288480
That is 0.08 % spread across seven boots -- not a glitch.  The NEW-25 baseline's
worst frame was 97100 us; this is ~288500.  So the MEDIAN improved 1.66x while
the WORST frame grew ~3x.  It is a genuine refresh, not a harness artefact: the
sample is one refresh's own REFR_START->REFR_READY duration and the first frame
after the screen load is skipped (g_fps_skip).
The untested hypothesis is the one this whole issue turns on -- LVGL renders one
pass per invalidated area, a cue change now emits FOUR areas where it emitted
one, and Phase B fires every 15 ms against a ~30 ms refresh, so two anim ticks
can accumulate and 16 keys x 5 areas approaches LV_INV_BUF_SIZE = 32, past which
LVGL invalidates the whole screen.  A full 720x1280 software render is the right
order of magnitude for 288 ms.  UNVERIFIED; NEW-53 step 1 is to count areas per
refresh, which can be done in QEMU without silicon.
★ Being deterministic, this is also the reproducible multi-area load that
NEW-53's other half (an acid_box ROT_EQ failure) lacks.

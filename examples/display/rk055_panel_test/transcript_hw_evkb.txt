WHAT THIS PROVES ON SILICON (and only silicon)
-----------------------------------------------
DSI_OK is the milestone's whole point and is a HARDWARE-ONLY fact.  The QEMU
model reports D-PHY LOCK the instant PD_PLL clears and stores every DPI
register as plain RW, so the QEMU gate proves the bring-up SEQUENCE and nothing
about the analog link.  On the board it means:

  * the D-PHY PLL genuinely LOCKED at the sized bit rate -- desired
    791,999,991 Hz (58,666,666 x 24/2 x 9/8, integer-truncated twice), which
    the divider search rounds to CN=1 / CM=33 / CO=0 = 792,000,000 Hz actual;
  * across TWO data lanes, versus the RPi panel's one.  This is the first
    2-lane MIPI-DSI link brought up on this board;
  * with the DPI blanking arithmetic producing positive HFP/HBP/HSA
    (28 / 71 / 10) -- blanking-byte underflow is what made the mainline RPi
    modeline unreachable on this DSI host, and this modeline clears it.

CLK_OK is also a first: this is the first compiled consumer of
displayClockInit()'s no-VIDEO_PLL path.  It confirms on silicon that SYS_PLL2
reads stable (bit 29), not gated (bit 30) and not bypassed (bit 16) at boot --
i.e. the boot ROM really does leave PLL_528 running, so this panel needs no PLL
bring-up at all.  Note that check was added deliberately: the branch originally
set its lock flag vacuously true, which would have made clkOk() report success
for a clock source that might not be running, since a CCM CONTROL register
latches a mux selection whether or not the PLL behind it is alive.

LCDIFV2_OK means the scanout block accepted the 720x1280 geometry and the
layer-0 descriptor.  It does NOT mean pixels reach the glass -- there is no
panel driver yet (M2) and nothing painted into the framebuffer (M3).  The panel
is expected to show nothing at this milestone.


NOT PROVEN HERE
---------------
  * Anything past the DSI host.  The HX8394 has received no init sequence.
  * Sustained scanout bandwidth.  ~108 MB/s at 58.7 Hz is what the 240 MHz
    BUS_CLK_ROOT exists for, but nothing is scanning out real pixels yet, so
    the LCDIFv2 output-underrun counter is not meaningful until M3.


PROCEDURE NOTE -- worth heeding, it cost a failed flash
-------------------------------------------------------
The plan said to start the serial reader BEFORE flashing.  On this MCU-Link
that BROKE the debug session: with tools/rt1170-console.py holding the VCOM,
`LinkServer flash ... load` failed with

    Error: Hardware interface transfer error
    request to clear DAP error failed - status 131
    error on reset - Ee(83). Hardware Transfer Error
    LOAD_EXIT=255

and the VCOM re-enumerated mid-attempt ("port dropped, reconnecting").  The
identical command succeeded (LOAD_EXIT=0) as soon as nothing held the port.

Working order on this board:
    1. flash ... load     (VCOM free)
    2. flash ... verify   (VCOM free)
    3. attach the serial reader
    4. reset -- `LinkServer run <dev> <elf>` in the background works; there is
       no standalone `LinkServer reset` subcommand in 26.6.137.

The repo rule "start the reader before triggering a reset if you need boot
output" still holds -- it is specifically holding the port DURING PROGRAMMING
that fails.

WHAT THE EVIDENCE SAYS
----------------------
The failure point is TUNING index 9, opcode 0xC0 — the 3-byte {C0 1F 31}
generic long write.  It is the command IMMEDIATELY AFTER index 8, the 59-byte
0xE0 gamma table, which is by a wide margin the longest packet in the sequence.
Index 9 never varies across failures.

Decoding the DSI host snapshot (RM 49.7.3.5.4 PKT_STATUS / 49.7.3.10.4
IRQ_STATUS, both: [0] state machine not idle, [1] Tx packet done, [3] Tx FIFO
overflow, [4] Tx FIFO underflow):

  SPINS entry:0    the APB was ALREADY IDLE when packet 9 was submitted, so
                   packet 8 (the 59-byte one) was reported complete.  This is
                   NOT "busy on entry".
  SPINS start:1    the state machine asserted not-idle on the very first poll
                   after SEND_PACKET.  This is NOT "never started".
  SPINS idle:100000  APB_IDLE_SPIN_CAP exhausted.  This IS "never went idle":
                   the transfer began and the machine never returned to idle.
  PKT_STATUS=0x1   bit0 (not idle) stuck set; bit1 (Tx packet done) NEVER set
                   for this packet; bits 3/4 clear, so NOT a FIFO error.
  RXERR=0x0        no HS-TX / LP-RX / BTA timeout (all three are disabled —
                   CFG_*_TO_COUNT are 0 — so this is expected, not informative).
  FIFO wr:0        the TX payload FIFO drained: the one word was consumed.
  LOCK=0x1         the D-PHY PLL is STILL LOCKED at the failure point.  The
                   link did not collapse.
  IRQ1=0x3         bits 0+1 latched.  Bit 1 here is packet 8's Tx-packet-done
                   latch carried forward (IRQ_STATUS is read-to-clear and
                   dsiWrite() reads it once per transfer), so this is the
                   normal steady-state value, not a signal.

So: the host accepted the packet, drained its FIFO, went busy, and wedged with
the PLL still locked and no error bit anywhere.  Because dsiWrite() is TX-only
— no BTA, no read-back, PKT_CONTROL's BTA and BTA_ONLY bits never set, and
nothing in the path waits on a reply — the panel cannot influence this outcome.
PANEL_FAIL here is a HOST-side stall, not dead or absent glass.

HYPOTHESIS (recorded, NOT acted on)
-----------------------------------
LCDIFv2 scanout is deliberately started BEFORE the panel is configured
(Display::begin(), Task-14 HW-found ordering), so DPI video is streaming while
these LP command packets go out, and the host has to fit each APB packet into a
BLLP window.  What is new and unproven on silicon for RK055 versus the working
RPi-7" path is exactly the combination that would stress that: 2 lanes, burst
video mode (kDSI_DpiBurst), autoInsertEoTp = true, and a 59-byte payload where
the RPi driver's longest is 6.  The 59-byte packet plus its EoTp may not fit
the available window, leaving the APB machine mid-transfer when the next packet
is submitted — which would explain both the fixed location (always the packet
after the longest one) and the intermittency (the phase of the command stream
relative to the frame differs per boot).  UNVERIFIED.

QEMU
----
./run_qemu.sh still PASSes; a passing run's captured UART is byte-identical to
before these additions (the diagnostic lines print only on PANEL_FAIL, and
strictly after the PANEL_ token the gate greps for).

M2 PHASE-3/4 — THE FIX: PANEL INIT BEFORE SCANOUT (22/22 CLEAN)
=================================================================
Date:   2026-07-28
Board:  MIMXRT1170-EVKB, panel on J48 (40-pin FPC, native RK055 connector)
Probe:  MCU-LINK on-board (r0E2) CMSIS-DAP V2.250, serial 5DQ2DDHVWO5EI
Image:  examples/display/rk055_panel_test/build/rk055_panel_test.elf
        (MipiDisplay with PANEL_INIT_BEFORE_SCANOUT)

ROOT CAUSE
----------
The Phase-1 hypothesis, confirmed by fixing it: we were sending the HX8394 init
while the LCDIFv2 was ALREADY STREAMING DPI VIDEO.  NXP does not.  In
mcuxsdk/examples/driver_examples/lcdifv2/rgb565/lcdifv2_rgb565.c the panel is
brought up before the display controller exists:

    :152  BOARD_InitDisplayInterface()   <- DSI host bring-up AND the whole
                                            HX8394 init
    :161  LCDIFV2_Init()                 <- LCDIFv2 initialised only after
    :163  LCDIFV2_SetDisplayConfig()
    :165  LCDIFV2_EnableDisplay(true)
    :184  LCDIFV2_EnableLayer(true)      <- scanout actually begins later still

In video mode the host can only fit an LP escape packet into a blanking (BLLP)
window, so it WAITS rather than erroring — which is exactly the Phase-1
signature: no FIFO error, no RX error, D-PHY still locked, the APB state
machine simply never returning to idle.  The location was fixed (always tuning
index 9, the packet after the 59-byte gamma table) because that packet's
duration is fixed, so index 9 always lands at the same phase offset; the
absolute frame phase at boot varies, which gave the intermittency.

THE CHANGE (one change, nothing else)
-------------------------------------
Bring-up order became a PANEL property, the same shape this library already
uses for lane count, video mode and the clock plan:

  panels/rk055/panel_config.h   #define PANEL_INIT_BEFORE_SCANOUT 1
  panels/rpi7/panel_config.h    #define PANEL_INIT_BEFORE_SCANOUT 0

  Display::begin() now runs, for rk055:  clocks -> DSI host -> HX8394 -> LCDIFv2
                             for rpi7:   ATtiny -> clocks -> LCDIFv2 -> DSI host -> TC358762

The two panels genuinely want OPPOSITE orders and both are HW-found: a
TC358762 BRIDGE needs valid video sync present before it will lock (Task 14 —
starting it with no video left the RPi panel dark), whereas a NATIVE DSI
controller needs the link quiet to be programmed.  Both reasons are documented
in BOTH panel_config.h files so neither can be "simplified" to match the other.
No timing, register value, packet, or packet-sequence value was touched.
mipiDsiBegin() is unaffected by the move: it only programs the DPI input's
geometry, it does not require pixels to already be arriving — which is why
NXP's own BOARD_InitDisplayInterface() runs the entire DSI host bring-up before
LCDIFV2_Init() is called at all.

PROCEDURE NOTE — pkill LinkServer is NOT enough
-----------------------------------------------
`pkill LinkServer` kills only the wrapper; it leaves `redlinkserv` and
`crt_emu_cm_redlink` resident, and the next `LinkServer run` then finds the
probe occupied and silently produces a dead run.  Four consecutive no-captures
were caused by exactly this before the loop also did:

    pkill redlinkserv; pkill -f crt_emu_cm_redlink

Second note: the console log contains a NUL byte where the VCOM re-enumerates,
so BSD grep treats it as a binary file — tally these captures with `grep -a` or
a genuine PANEL_OK reads as a no-capture.

WHAT EACH LINE IS WORTH
-----------------------
FB_SUM      0x9831F3C5 on silicon is BYTE-IDENTICAL to the QEMU gate's value,
            and both match an expectation computed by a SECOND, independent
            implementation of the pattern rule in the gate sketch (its own
            bars[] table and loop nest -- it never calls into the driver, so
            the two cannot agree with each other while both disagree with the
            panel).  The framebuffer genuinely holds the pattern.

PANEL_SUM   TAP_ABSENT, TAP_ID = 0.  Working exactly as designed: the virtual
            HX8394's checksum tap is emulator fiction mapped over reserved
            space in the DSI host's AIPS slot, so on silicon the read returns 0
            instead of faulting.  The gate branches on TAP_ID, never on the
            checksum -- had it tested the checksum against 0 it would have
            conflated "no tap here" with "dark panel" and failed this run
            spuriously.  QEMU-ONLY BY CONSTRUCTION.

★ UNDERRUN  0/10, and note the ABSENCE of the "(QEMU: vacuous)" suffix -- that
            suffix keys off the same TAP_ID, so its absence is the token saying
            this is the real measurement.  ZERO LCDIFv2 output-FIFO underruns
            across 10 frames at ~108 MB/s sustained scanout (720x1280 RGB565 at
            58.7 Hz).  This is the number the whole M0 milestone existed for:
            raising BUS_CLK_ROOT to SYS_PLL3_OUT/2 = 240 MHz.  It is
            HARDWARE-ONLY BY CONSTRUCTION -- QEMU has no timing model, so its
            0/10 proves nothing.  The spec's pre-designed escalation (drop to
            kDSI_DpiNonBurstWithSyncEvent, or a larger ROOT70 divider) is NOT
            needed; 240 MHz has the headroom.

NOT PROVEN, STILL
-----------------
  * Sustained behaviour over long runs.  10 frames is ~170 ms.  A thermal or
    long-run underrun would not show here.
  * Any second buffer / page flip -- v1 is single-buffered, so tearing is not
    exercised.
  * Touch (v2), LVGL (v3).

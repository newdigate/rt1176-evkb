★★ THE FINDING THIS RUN FORCED: the PXP does not preserve the X byte
--------------------------------------------------------------------
The bench's FIRST silicon run (same geometry matrix, byte-identity oracle)
failed all 14 XRGB8888 cases while QEMU passed all 28 -- a genuine
model/silicon divergence.  A DIAG dump isolated it:

    DIAG src  C3A5F00D 5D9289BC FFCB036F 19039D1E
    DIAG xrgb 00A5F00D 009289BC 00CB036F 00039D1E   (OUT format RGB888/0x04)
    DIAG argb e=0 00A5F00D 009289BC 00CB036F 00039D1E (OUT format ARGB8888/0x00)

RGB bytes copy exactly; the X byte is written as the pipeline's COMPUTED
alpha, which is 0 with the alpha engine unconfigured (no AS surface,
Porter-Duff off, OUT_CTRL[ALPHA_OUTPUT]=0 "retain computed alpha" -- RM
52.3.1.22 pixel handling, 52.6.3 OUT_CTRL).  Both 32-bit OUT encodings
behave identically.  Deterministic, architectural, not a library bug.

Resolution, silicon-wins in both directions:
  - The QEMU PXP model's byte-preserving raw copy was LESS faithful than
    silicon: it now writes X=0 for 32-bit RGB outputs (imxrt_pxp.c), matching
    the measurement (its format-conversion paths already wrote A=0), and
    traps OUT_CTRL[ALPHA_OUTPUT]=1 loudly as unmodelled.
  - The bench oracle now asserts EXACTLY the hardware contract: RGB565 cases
    are byte-identity with lv_draw_buf_copy; XRGB8888 cases are RGB-identity
    with X:=0 inside the copied rect (the CPU reference has its in-rect X
    bytes zeroed, outside the timed window) and every byte outside the rect
    untouched (whole-max-extent checksums, unchanged).  A model OR silicon
    that PRESERVED X now goes red -- the assertion got more precise, not
    weaker; the original byte-identity claim was simply false on silicon.
  - Consumers are unaffected functionally: LVGL treats the byte as X, the
    LCDIFv2 ignores it on scanout, and the DSI wire is 24-bit.  What matters
    for the goldens is that QEMU and silicon now write the SAME bytes.

★★ ANALYSIS — the v7 8888 decision input
----------------------------------------

1. THE HEIGHT >= 2 RULE HOLDS AT XRGB8888, MORE STRONGLY THAN AT 565.
   Every multi-row 8888 case favors the PXP: from 3.4x at the pathological
   1-px-wide column (case 11: 968 vs 285 us) through ~13.4x for the bulk
   copies (cases 12-14) to 26.5x at 16x16 (case 1: 106 vs 4 us).  [The
   first publication of this table misquoted the range as "5.4-16.5x" --
   5.4x was an RGB565 figure; the numbers here are computed from the CASE
   rows above.]  The single-row case (10: 719x1) -- the CPU's one win at
   565 (70 vs 105 us) -- is a dead TIE at 8888 (135 vs 135 us): doubling
   the bytes doubled the CPU's row cost while the PXP's per-op cost stayed
   flat.  The rule stays conservative (single-row chains to the CPU
   default) and this transcript is what the handler's height>=2 comment
   cites for BOTH formats.  (For reference, the 565 multi-row range is
   2.0x -- the same 1x1280 column -- to 21x.)

2. THE CPU FULL-SCREEN 8888 SYNC COPY COSTS 174.3 ms — 5.3x THE 33 ms FRAME
   BUDGET (vs 89.5 ms / 2.7x at 565).  The PXP does it in 13.0 ms, a 13.4x
   win.  At 32 bpp the PXP sync-copy acceleration is load-bearing, not an
   optimization.

3. 565 numbers reproduce v6's within noise (full-screen 89.5 ms CPU /
   12.3 ms PXP then and now) -- the dual-format rewrite did not disturb the
   measured 565 behavior.

4. PXP throughput scales with byte volume and stays near-flat per op:
   full-screen 8888 moves 2x the bytes of 565 in 13.0 vs 12.3 ms --
   ~283 MB/s effective on the 32-bit path (3.686 MB in 13.0 ms), consistent
   with v6's AXI figure once byte volume is accounted for.

★★ DECISION, by the rule pre-registered in the spec (§2: the fastest
byte-preserving arm whose full-frame copy is under one refresh period, 33 ms,
with the panel scanning out): **pxp_aff -- the PXP with OUT_CTRL[ALPHA_OUTPUT]=1,
ALPHA=0xFF -- at 17.3 ms.**  Task 6 proceeds on variant 6a.

★ SILICON HONOURS THE ALPHA OVERRIDE, AT BOTH 32-BIT OUT ENCODINGS.  pxp_aff
(surfaces XRGB8888, OUT encoding 0x04 RGB888) and pxp_affa (the same bytes
declared ARGB8888, OUT encoding 0x00) both MATCH on BOTH source rows: the
xff row proves byte identity with the CPU copy for a source whose X byte is
0xFF (every LVGL-rendered XRGB8888 buffer), the mixed row proves the byte the
PXP writes is the OVERRIDE (X==0xFF where the source held C3/5D/FF/19...), not
the source's.  The RM's "when generating an output buffer with an alpha
component" (52.6.3) does not exclude RGB888; the model's uniform treatment of
0x00 and 0x04 (qemu2 b313293975) was right, and its "NOT YET MEASURED" comment
can now cite this section.  The ARGB8888 encoding is therefore NOT needed for
the handler; it stays XRGB8888.

★ THE eDMA ARM IS CORRECT AND HONEST -- and it loses.  Byte-preserving on the
mixed source in all 28 cells, 49.7 ms per full frame (5.2x the CPU, 32-byte
bursts, three 960-B bands), 14 us at 16x16, 76 us at the 4-byte-aligned
+13+7 offset (its slow regime), 24 ms at RGB565.  It is over the 33 ms
criterion, and the PXP is 2.9x faster still.  It stays in the port
(lvgl_edma_copy.{h,cpp}, host-tested planner) as the only accelerated copy this
tree has that preserves EVERY byte with no invariant about the writer -- the
answer if a buffer whose X byte carries meaning ever needs syncing.

★★ NEWLIB memcpy IS 3.8x SLOWER THAN LVGL's WORD LOOP ON THIS MEMORY.  cpu_clib
read 989.6 ms per full frame (8888) and 494.8 (565) against lv_memcpy's 260.6 /
134.3 -- and 278 us against 169 at 16x16.  The plan called it "the CPU floor,
likely <=2x faster"; it is a ceiling.  Not investigated (the arm exists to
bound the CPU, and the bound is now known in the wrong direction); the likely
mechanism is newlib-nano's byte/halfword prologue and unrolled LDR/STR pairs
each stalling on an uncached SDRAM read, where lv_memcpy's 8x-unrolled word
loop issues the same loads with less overhead per word.  Recorded because the
obvious "just use memcpy" is refuted by measurement, not argument.

W16 TX MULTIPORT AGGREGATION -- and the half the image cannot fake
------------------------------------------------------------------------------
Date: 2026-08-20.  Driver M2Radio b44877c, model qemu2 7e17eff5d3.
Gate: run_qemu_txaggr.sh.

    txaggr_done sent=6 flush=ok c53tx=1 batches=1 slots=6 queued=0
    txaggr_loop rx=6 c53rx=9 rxbatches=1 rxslots=6

Six frames staged with TX aggregation on, then flushTx() -- ONE data CMD53
carried all six, and nothing was left held (queued=0, the specific hazard of a
feature where a successful send means "queued", not "on the wire").

The second line is the part this image could not have produced on its own.
With tx-loopback=on the CARD splits the aggregated write by each packet's own
block-padded SDIOPkt size, hands each piece to the download slot the address
said it belonged to (checking that slot's WR_BITMAP credit as it goes), and
sends each one back up the UPLOAD ring.  All six came back, carrying the
indices this image put in them, in order -- so the card reproduced a layout
the host never gets to inspect.  A wrong pad, a wrong port_count or a wrong
start slot shows up as missing frames, not as a passing run.

And they came back in ONE aggregated READ (rxbatches=1 rxslots=6), so this run
exercises both directions of the same encoding against each other.

BASELINE, same image, AGGR_PKT_LIMIT set to 1:

    txaggr_done sent=6 flush=ok c53tx=6 batches=0 slots=0 queued=0
    txaggr_loop rx=6 c53rx=14 rxbatches=0 rxslots=0

  -- six frames, six commands, and all six still delivered and looped back.

NOT SILICON, and tx-loopback is itself an admitted fiction (the model's NOTE
15): a real card puts the frame on the air.  What this proves is that our two
ends agree with NXP's contract as read.

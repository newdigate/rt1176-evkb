------------------------------------------------------------------------------
W16 RX MULTIPORT AGGREGATION -- what this capture is, and the baseline it beat
------------------------------------------------------------------------------
Date: 2026-08-20.  Driver M2Radio b44877c, model qemu2 7e17eff5d3.
Gate: run_qemu_rxaggr.sh (see its header for the assertions and for the
deliberately-broken run that proved it can go red).

Eight uploads are burst onto ring slots 0..7 (inject-period-ms=0, so all eight
are resident before the host next looks) and the host must deliver every one,
in order, paired with the slot the CARD chose.

    demo_done frames=8 rx_data=8 rd_bitmap=0x0 ... c53rx=1 rxaggr=1/8

  c53rx=1     ONE data CMD53 carried all eight frames.
  rxaggr=1/8  one CMD53 covered more than one slot, and it covered eight.
  stranded=0/0 drainerr=0 notready=0 split=0  -- the W12/W13 health set
              untouched, and no packet's SDIOPkt size disagreed with the slot
              length the card published for it.

MEASURED BASELINE, same image, same burst, same model, with the driver's
AGGR_PKT_LIMIT set to 1 (i.e. exactly the pre-W16 behaviour):

    demo_done frames=8 rx_data=8 ... c53rx=8 rxaggr=0/0

  -- eight frames, eight commands.  Every DELIVERY assertion in the gate
  passed in that run; only the counters moved.  That is why the gate asserts
  both halves: one-command-per-frame is correct, just not faster, and a gate
  that checked delivery alone would have blessed it.

AND THE OTHER SEVEN COMMANDS PER FRAME.  Before W16 each of those eight frames
ALSO cost four CMD52s to read the rd-bitmap, two to read its RD_LEN, and one
for HOST_INT_STATUS.  Those are gone too -- not aggregated, replaced: the
multiport register port returns all of it in one byte-mode CMD53 (c53regs= in
the same line).  So the burst went from 8 x (7 CMD52 + 1 CMD53) to 1 register
read + 1 data CMD53.

WHAT THIS DOES NOT SAY.  Nothing here is silicon.  The aggregated address
encoding and the register port are both read off NXP's driver, and QEMU agrees
with us because we wrote both ends.  W15 phase 3 is the standing warning: a
model written from the same reading as the driver will agree with the driver
and both can be wrong together.  The silicon run is the gate that decides.

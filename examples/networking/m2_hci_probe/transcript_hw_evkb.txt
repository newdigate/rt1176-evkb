WHAT THIS PROVES, AND WHAT IT DOES NOT
--------------------------------------

★ **It does NOT prove Bluetooth works.  It proves the DRIVER works and the
CARD does not answer.**  Every claim about the IW416's Bluetooth belongs to
this file and to `m2_sdio_probe`'s B0 section, which explains WHY it does not
answer: the BT core appears to be sitting in its UART bootloader asking for a
firmware image the SDIO download never gives it.  Read that section first.

**1. The card came up completely on the Wi-Fi side.**

    sdio_begin=ok / iw416_begin=ok / fw_download=ok / card=1

So the negative below is not a dead card, a missing blob, or a bad preamble.

**2. The Reset failed BY NAME, with a full accounting.**

    hci_reset=timeout reason=no_response attempts=10 timeouts=10 framing=0 starved=0 qfull=0 late=0

Every counter matters here:
* `timeouts=10` — all ten attempts were TRANSMITTED and each waited its full
  500 ms.  ★ This is the silicon confirmation of a bug found in QEMU during
  BT-1: before `Hci::service()` restored the abandoned command's credit, this
  line read `timeouts=1 starved=9` — nine attempts never left the host.  On a
  bench that difference is the difference between "the card is silent" and "we
  only ever asked once", and it would have been invisible without the counter.
* `framing=0` — **not one malformed byte in 2.5 minutes at 115200.**  The
  R1901 hand bridge is electrically sound; a marginal bridge or a wrong baud
  would show framing faults here, and does not.
* `late=0` — nothing arrived after any deadline either.  The card is silent,
  not slow.
* `starved=0`, `qfull=0` — the driver never got in its own way.

**3. The image kept running.**  57 heartbeats, `card=1` throughout, no wedge —
so "no identity printed" is a REPORTED negative, not a crash.

WHAT IS NOW SETTLED
-------------------

**1. The protocol decode is right, and the download WORKS on the real card.**

    bt_fw_download=ok chip_id=0x7201 loader_ver=0 start_inds=2 chunks=142
                       sent=131856/131840 max_off=131840 retx=1 crc_err=0 card_err=0x0001

The card consumed the ENTIRE image, in its own structure: a 16-byte header
block, then the payload that header describes, repeating --
`16@0 2048@16 16@2064 2048@2080 ...` -- and ending `16@131824`, which is
exactly the last 16 bytes of a 131,840-byte image.  Nothing was left over and
nothing ran past the end.

It also exercised the ERROR path for real, unprompted: `card_err=0x0001`
(CRC_ERR) with `retx=1` -- the card rejected one block, asked for the same
offset again, we re-served it, and it continued.  `crc_err=0` says we rejected
none of ITS frames.  That is the recovery path working on silicon, which no
gate could have proven.

**2. ORDER IS LOAD-BEARING, and getting it wrong is silent.**  The first
attempt reported `no_start_indication` from a card that greets perfectly well.
The BT core greets ONCE per power-up -- three frames in ~200 ms -- and the
probe was bringing Serial2 up only after the SDIO enumeration and the 400 KB
WLAN download, seconds later.  The bytes were transmitted before the UART
existed.  Serial2 must be listening BEFORE the card is powered up, and the
download must run BEFORE the SDIO work.  NXP's own CONFIG_BT_IND_DNLD path has
that same shape.

WHAT IS STILL OPEN -- and it is not the download
------------------------------------------------

**The controller does not start HCI afterwards.**

    bt_raw_reset[0..2]: n=0 hex=none        (three raw HCI_Reset, 700 ms each)
    hci_reset=timeout reason=no_response attempts=10 timeouts=10 framing=0

★ The raw reset is fired IMMEDIATELY after the download, before any other code
runs, precisely so the SDIO sequence cannot be blamed.  It is not the SDIO
sequence.

★ AND THE SAME BUILD ANSWERS IN QEMU.  Against the fake bootloader in
`run_qemu_hci.sh`'s [fwdnld] phase, that identical raw probe returns
`bt_raw_reset[0]: n=7 hex=040E0401030C00` -- the Command Complete for Reset --
and the gate now ASSERTS it.  Same firmware, same code path, same instant: a
peer answers and the card does not.  So the silence is the card's.

The card also does NOT re-greet after the download (no further start
indication in 2 s), so it did not reject the image and fall back to its
bootloader.  It simply goes quiet.

**A SECOND FINDING, unlooked for:** after the UART download the WLAN SDIO

downloads are ALTERNATIVES, not additions, which matches NXP's own code: their
★★ CORRECTED 2026-08-25 -- THAT IS WRONG, and it was an artefact of using the

HYPOTHESES FOR THE NEXT SESSION, ranked, none of them tested
------------------------------------------------------------

1. **The download may be expected to carry a baud change.** NXP's loader
   tracks `change_baudrata_buffer_len` and subtracts it from the card's offset
   -- i.e. their normal flow INJECTS a baud-change buffer into the download
   stream.  A download that never does may leave the part expecting one.  The
   cheap test is to follow the standard flow exactly, including the change.
2. **The image may not match this part.** `uartIW416_bt.bin` is NXP's stock
   image; chipId reads 0x7201; u-blox may ship a MAYA-W161-specific one.  A
   silently-rejected signature would look exactly like this (accepted every
   block, then nothing).
3. **A combo part may need both images** in a particular order, the SDIO
   failure above being the other half of the same story.
4. Secure-boot/authentication mismatch, which would also be silent.

★ Whatever the answer, it is NOT the transport and NOT the protocol: 131,840
bytes went across correctly, with a real error recovered, and the card asked
for every one of them.

=====================================================
HYPOTHESIS 1 TESTED: the UART-config ("baud change") buffer -- REFUTED
=====================================================

Date: 2026-08-24.  Built with `-DM2_BT_INJECT_UART_CFG=ON`.

THE HYPOTHESIS.  NXP's loader, whenever it changes baud, replaces the FIRST
16-byte header the card asks for with a synthesized **type-5 "configure UART"**
header whose payload is twelve register writes -- clock divisors, MCR, ICR,
FCR and a re-init trigger at 0x7F00008F..0x7F000094 -- and then subtracts the
injected length from every later offset.  Since a booted firmware might need
that UART re-init to talk at all, the download completing while the controller
stays silent looked like it might be exactly this missing step.

★ It was testable WITHOUT changing baud: passing the CURRENT rate's divisors
(115200: clkDiv 0x0075F6FD, uartDiv 16) writes the register block and changes
no rate, so it isolates "does the card need this block written" from "can this
board do 3 Mbaud" -- which it cannot, having no usable flow control.

    ★★ THAT PARENTHESIS IS WRONG, and it cost the programme a week.  See
    "THE BAUD WAS NEVER THE ONE u-blox DOCUMENT" below (2026-08-25).  Flow
    control is needed for sustained A2DP throughput, NOT for a four-byte
    command and a seven-byte reply, and 3 Mbaud is exactly representable on
    this core (24 MHz / OSR 8 / SBR 1, 0.00% error).  Ruling the rate out on
    the strength of the flow-control wiring ruled out the one experiment the
    vendor's own procedure calls for.

WHAT WAS BUILT, and why it should have been right:

  * the type-5 header is byte-identical to NXP's `cmd5_hdrData`
    ({0x05,0,0,0, 0,0,0,0, <len:4 LE>, <crc32:4 BE>}), with len = 52;
  * the payload is their `changeBaudRateConfigData_t` -- twelve little-endian
    uint32 (address, value) pairs -- followed by a CRC-32;
  * ★ the CRC-32 variant was not guessed.  Poly 0x04C11DB7, init 0, no
    reflection, stored BIG-endian, VERIFIED by recomputing the shipped image's
    own first header: bytes `01 00 00 00 10 20 0a 00 00 08 00 00` give
    0x83DFA3EA, which is exactly the four bytes that follow them in the file.
    (That also decodes the image's block format: type 1, load address
    0x000A2010, length 2048, CRC-32 -- and explains the download's shape.)

THE RESULT -- the card REJECTS the header:

    bt_uart_cfg=injected
    bt_fw_download=stalled chip_id=0x7201 loader_ver=0 start_inds=2 chunks=2
                   sent=0/131840 max_off=0 retx=0 crc_err=0 card_err=0x0001
                   cfg_resends=1 cfg_unexp_len=0

The card took the type-5 header, answered with **CRC_ERR (card_err=0x0001)**,
asked for the 16-byte header AGAIN, was served the identical bytes, and then
went silent.  It never asked for the 52-byte payload at all.

★ **REFUTED, and worse than the baseline.**  Without the injection the download
completes in full (142 chunks, 131,840 bytes) and only HCI is silent; with it
the download does not even start.  So the UART-config block is not the missing
step -- on this card it is not accepted.

WHAT THAT SUGGESTS, without over-claiming.  The header we sent is NXP's own,
and its CRC is computed by an algorithm verified against the card's own image,
so the likeliest reading is that THIS BOOTLOADER DOES NOT IMPLEMENT THE TYPE-5
CONFIG COMMAND.  Note `loader_ver=0` in every capture: NXP's loader carries a
`bootLoaderSuppVersion_e` and gates behaviour on it, so a version-0 loader
accepting only plain image blocks is consistent with everything seen.  Not
proven: a subtly wrong field would look identical.

WHERE THAT LEAVES THE REMAINING HYPOTHESES

  2. **Wrong image for this module** -- untested, and now the strongest.
     `uartIW416_bt.bin` is NXP's stock image; this is a u-blox MAYA-W161 and
     u-blox may ship their own.  A silently-rejected signature looks exactly
     like what we see: every block accepted, then nothing.
  3. **A combo part may need both images**, the SDIO download failing after the
     UART one being the other half of that story.
  4. Secure-boot/authentication mismatch -- also silent.

★ A BYPRODUCT WORTH KEEPING.  Testing this made the [fwdnld] gate go
intermittently red with `bad_header` against a peer that had greeted perfectly
well.  The cause is real and applies to silicon: before the first valid frame
the host is not synchronised with the card at all, and a greeting truncated by
the ring reset in Serial2.begin() leaves its TAIL in the buffer.  The loader now
skips debris until it has seen one good frame -- COUNTING it as `presync=` so it
is visible -- and stays strict afterwards.  A gate found that, not the bench.

NXP'S OWN REWORK GUIDE FOUND -- and two more hypotheses tested
=====================================================

Date: 2026-08-24.

★ **NXP DOCUMENT A HARDWARE REWORK FOR THIS EXACT BOARD, and we had found
only part of it by ourselves.**  From the SDK's EdgeFast BT PAL hardware rework
guide (`middleware/edgefast_bluetooth/docs/HWRGEFBTPALUG`, topic
`MIMXRT1170EVKB_hwrework.md`):

    HCI UART rework
      1. Remove resistors R183 and R1816.
      2. Solder 0 ohm resistor to R404, R1901, and R1902.

We had fitted **R404** and **R1901**, worked out from the schematic and
confirmed by measurement.  We had fitted neither **R1902** nor removed **R183**
or **R1816**.  Reconciling their list with this repo's own board map:

| ref | what it is here | our state |
|---|---|---|
| R404  | GPIO_AD_31 -> PDn (J54.56) | **fitted by hand 2026-08-18** |
| R1901 | U355 -> BT_UART_RXD (J54.22) | **fitted by hand 2026-08-18** |
| R1902 | U355 -> BT_UART_CTS (J54.34), the CARD'S RTS OUTPUT | DNP -- we judged flow control unusable |
| R1816 | ties that same pad to RGMII1_PHY_INTB | fitted -- it is WHY we judged that |
| R183  | **U27.2 -> GPIO_AD_31** | fitted |

★ **R183 was not in our board map at all, and it is worth knowing.**  U27 is a
Macronix `MX25L4006` SPI NOR flash, and pin 2 on that package is its DATA
OUTPUT.  So the PDn net -- which is also Arduino D12/MISO -- carries a flash
chip's output.  Harmless while that flash is never selected, but it means a
third driver can appear on the line we use to power-cycle the radio, which is
exactly why NXP say to remove it once R404 is fitted.  Recorded as a latent
hazard; it does NOT explain the symptom, since PDn demonstrably works (the card
powers up and greets every time).

★ Their pair -- remove R1816, fit R1902 -- is what turns the HOST'S CTS INPUT
from "the Ethernet PHY's interrupt" into a real UART signal.  It is not rework
we can do here without giving up the gigabit PHY.

HYPOTHESIS: THE CARD NEEDS FLOW CONTROL -- TESTED, REFUTED
----------------------------------------------------------

NXP configure this link WITH hardware flow control
(`enableRxRTS = 1; enableTxCTS = 1`).  That suggested a clean explanation of
the whole symptom: the boot ROM does not use flow control and talks, while the
booted firmware does, sees its CTS input unasserted, and never transmits.

★ Testable with NO rework, because the direction that matters is already
populated.  J54 pin 36 is the CARD'S CTS INPUT (the net is named BT_UART_RTS,
from the host's point of view), it reaches GPIO_DISP_B2_13, and we had simply
never driven it.  CTS is active LOW, so an undriven pad reads "not clear to
send".  Driving it low as a plain GPIO makes the card permanently clear to
send -- at the price of holding the gigabit PHY in reset, since R1866 ties that
net to ETHPHY_RST_B.

    bt_cts=asserted (PHY held in reset)
    bt_fw_download=ok chip_id=0x7201 ... sent=131856/131840 max_off=131840
    bt_post_dnld[0..3]: n=0 hex=none
    bt_raw_reset[0..2]: n=0 hex=none
    hci_reset=timeout reason=no_response attempts=10 timeouts=10 framing=0

**No change whatsoever.**  The download still completes; the controller is
still silent.  So the card is not withholding transmission for want of CTS.

★★ THIS REFUTATION IS WITHDRAWN (2026-08-25).  The test drove CTS LOW BEFORE
the PDn release -- m2AssertBtCts() was called at line 401 and
m2ReleaseWifiReset() at line 410 -- and the MAYA-W1 system integration manual
(UBX-21010495 R09) s2.4.5 Table 6 says UART_CTSn and UART_RTSn are
CONFIGURATION PINS sampled at module reset: CON[7] and CON[8], both "Reserved
set to 1", their UART function only arriving ~1 ms after reset.  Holding CTS
low across the reset therefore latched CON[7]=0, a Reserved configuration.
So "no change whatsoever" cannot tell "flow control is not the problem" apart
from "the module booted into an undefined configuration", and this hypothesis
returns to UNTESTED.  The call has been moved after m2ReleaseWifiReset() so a
retest means something.
★ Note what makes CON[7] correct in the DEFAULT builds: nothing drives that
pad, and R81 pulls ETHPHY_RST_B up to SENSOR_3V3 through the fitted R1866, so
the card sees 1.  Every run except the CTS one had a valid configuration.

WHERE THE HYPOTHESES NOW STAND

  1. UART-config / "baud change" buffer -- **REFUTED** (previous section).
  2. **Wrong image for this module -- UNTESTED, and now much stronger.**
     ★ The SDK supports `WIFI_IW416_BOARD_MURATA_1XK_M2` for IW416 over M.2 and
     has **no u-blox MAYA support of any kind** -- though it does carry
     `WIFI_AW611_BOARD_UBX_JODY_W5_M2`, so u-blox modules are not foreign to

     against a MAYA-W161.  A silently-rejected image looks exactly like this.
  3. Combo needs both images -- untested.
  4. Secure-boot / signature mismatch -- untested, and indistinguishable from 2
     from the host's side.
  5. Card needs flow control -- ~~REFUTED~~ **WITHDRAWN 2026-08-25**, the

**All 421 objects compile.**  It fails at LINK, and the reason is structural:

    undefined reference to `_bt_conn_cb_list_start' / `_bt_conn_cb_list_end'
    undefined reference to `_bt_gatt_service_static_list_start' / _end
    undefined reference to `_bt_l2cap_fixed_chan_list_start' / _end
    undefined reference to `_bt_l2cap_br_fixed_chan_list_start' / _end

    undefined reference to `EDGEFAST_BT_LITTLEFS_STORAGE_MAX_SECTORS'
    undefined reference to `EDGEFAST_BT_LITTLEFS_STORAGE_START_ADDRESS'
    region `m_text' overflowed by 1117988 bytes

★ **THE MECHANISM IS ARM-COMPILER-ONLY.**  `edgefast_open`'s
`source/porting/porting.h` maps every one of those symbols to ARM scatter-file
names -- `_bt_conn_cb_list_start` becomes `Load$$ER_bt_conn_cb$$Base` -- inside

    #if defined(__CC_ARM) || (defined(__ARMCC_VERSION))

with no GCC branch.  The structs themselves are placed by Zephyr's
`STRUCT_SECTION_ITERABLE`, i.e. into `._<type>.static.*`, which a GCC linker
script is supposed to bracket.  The board's only linker file for this example is
`linker/arm/MIMXRT1176xxxxx_cm7_flexspi_nor.scf` -- a SCATTER FILE -- and no
`.ld` anywhere in the SDK defines these symbols (grepped).  So the armgcc
configurations `example.yml` advertises cannot link as shipped.

Confirmed by experiment rather than inferred: adding the standard Zephyr
`ITERABLE_SECTION_ROM` shape for the ONE family the default config needed
(`._bt_conn_cb.static.*`) to the device's `MIMXRT1176xxxxx_cm7_sdram.ld` made
that pair resolve -- and then selecting the IW416 module we actually have
(`board_murata_1xk_m2`) pulled in the full stack and reopened ALL of the
others, plus littlefs placement, ram functions, and 1.6 MB of text against a
region that cannot hold it.  ★ That patch was REVERTED and the SDK's linker
script restored; the build directories were removed.

WHAT IT WOULD TAKE, AND WHY IT WAS NOT DONE

Writing GCC linker support for EdgeFast: every iterable-section family, the
littlefs storage region, the ram-function region, and a flash/SDRAM layout that
fits.  Hours to days -- and the result would be OUR PORT, not NXP's validated
build, which defeats the purpose.  The whole point of running their stack was
to have a reference whose behaviour we can trust more than our own.

Neither ARM Compiler nor IAR is installed on this machine, so the supported
route is not available either.

next step.  Hypothesis 2 -- the stock `uartIW416_bt.bin` being the wrong image

package and feed it to the loader this repo already has, which is known to

★ Worth keeping: the SDK supports `WIFI_IW416_BOARD_MURATA_1XK_M2` for

THE u-blox FIRMWARE HUNT: THERE ISN'T ONE -- and it found a better lead

Date: 2026-08-24.  Web research only; nothing downloaded.

★ **AND THE LINUX FLOW NAMES THE IMAGE `sdiouartiw416_combo_v0.bin` -- "Wi-Fi

firmware**, and the UART download exists as the independent-download

THE ARITHMETIC THAT FOLLOWS, AND IT POINTS AT OUR OWN CODE
----------------------------------------------------------

    sduartIW416_wlan_bt.bin (combo)   411,064 bytes
    sdIW416_wlan.bin        (WLAN)    279,164 bytes
    uartIW416_bt.bin        (BT)      131,840 bytes
                            279,164 + 131,840 = 411,004

So the combo image is the WLAN image with the BT image appended, to within 60
bytes -- exactly what W17's A/B inferred.  And our SDIO download reports:

    fw_download=ok sent=402288/411064 chunks=417 last_req=0 fw_status=0xFEDC

**402,288 of 411,064 -- it stops 8,776 bytes short, deep inside the BLUETOOTH
portion.**  It got through all 279,164 bytes of WLAN and 123,124 bytes of BT,
then stopped.

★ **THE SUSPECT IS `Iw416::downloadFirmware()`'s TERMINATION RULE.**  It polls
the card's requested-length register up to 1000 times at 1 ms, and treats a
zero length after progress as "the image is in".  If the card pauses longer
than ~1 s between segments -- which is exactly what one would expect while it
validates and starts the WLAN image before asking for the BT part -- we call it
done and never send the rest.  The card then has no usable BT firmware, falls
back to its UART bootloader, and greets us there.  Which is precisely what we
see.

That is a concrete, checkable hypothesis in code we own, and it is far cheaper
to test than anything else outstanding: raise the poll window and see whether
`sent` reaches 411,064.

WHY IT IS NOT OBVIOUSLY THE WHOLE ANSWER, and must be tested rather than
assumed: we later fed the BT core a COMPLETE 131,840-byte image over UART and
it still did not run.  If a truncated SDIO image were the only problem, the
UART download should have fixed it.  So either the BT core specifically needs
its firmware via SDIO, or there are two faults.  Do not merge the two stories
before the measurement.

HYPOTHESES AFTER TODAY

  1. UART-config / baud buffer -- REFUTED on silicon.
  2. Wrong/u-blox-specific image -- REFUTED by u-blox's own documentation.
  3. **Combo needs both parts, and our SDIO download TRUNCATES it 8,776 bytes
     early -- NEW, strongest, and in our own code.**
  4. Secure-boot / signature mismatch -- untested, unchanged.
  5. Card needs flow control -- WITHDRAWN 2026-08-25 (CON[7] violated).
  6. Helper-file two-stage download -- REFUTED by AN14310.

THE BAUD WAS NEVER THE ONE u-blox DOCUMENT -- 2026-08-25
=====================================================

Source: the u-blox documents for THIS card, read for the first time on
2026-08-25 -- M2-MAYA-W1 data sheet UBX-22004354 R05 (which names our exact
part, M2-MAYA-W161-00C-00, NXP IW416) and MAYA-W1 system integration manual
UBX-21010495 R09.  Both are C1-Public.

WHAT THE VENDOR'S OWN BRING-UP IS (SIM s4.4.3 and s4.4.6)

  * the Wi-Fi driver loads `sdiouartiw416_combo_v0.bin` over SDIO, described
    as "the Wi-Fi/Bluetooth combo firmware image for the MAYA-W1 series" --
    one image, BOTH radios, no separate Bluetooth download;
  * Bluetooth is then attached with

        hciattach /dev/ttyUSB0 any 3000000 flow

    i.e. **3 Mbaud with hardware flow control**.

★★ EVERY PROBE THIS TREE EVER RAN USED 115200.  Checked, not remembered: the
only Serial2 rate anywhere in m2_hci_probe.cpp, m2_sdio_probe.cpp or
M2Radio/hci was 115200.  A controller listening at 3 Mbaud cannot decode bytes
sent at 115200, so it never replies and never transmits -- which is exactly
what is on record above: n=0 with framing=0, over minutes, on a line that had
just carried 131,840 bytes correctly.  A wrong-rate link that was TALKING
would have shown framing errors; none ever appeared, and that absence now
reads as evidence rather than as a puzzle.

WHY 115200 IS STILL THE RIGHT RATE FOR THE DOWNLOAD, and why that misled us:
the boot ROM greets at 115200 (AB 01 72 00 47, decoded and verified three
ways above) and the V3 download runs there perfectly.  The rate that changes
is the one the BOOTED FIRMWARE uses.  So the transport being provably correct
at 115200 -- which it is -- says nothing about the rate afterwards.

WHAT WAS BUILT

  m2_hci_probe now ESCALATES: if Reset fails at 115200 it sweeps
  3000000 / 921600 / 460800 / 115200, printing a cell per rate, and on the
  first that answers it re-runs identity and inquiry there.
  ★ Escalation rather than an unconditional sweep, because sweeping in front
  of the main sequence changes what the [hci] gate tests -- its [garbage]
  phase scripts corruption against the FIRST command it sees.  Measured: with
  the sweep unconditional, [full] went from cmds=7 to cmds=8 at once.
  ★ 3 Mbaud is exactly representable here: the core clocks LPUART from 24 MHz,
  so OSR=8 SBR=1 gives 3,000,000 with 0.00% error (921600 and 460800 land at
  +0.16%).  No divisor obstacle exists.

NOT YET RUN ON SILICON.  This section records a corrected hypothesis and the
instrument built to test it, nothing more.  The gates can prove the sweep
attempts every rate and claims none without a reply; they CANNOT prove a rate
is right, because QEMU's chardev has no notion of baud.  Only the bench can.

STATE OF THE HYPOTHESES after this reading

  1. UART-config / "baud change" buffer -- REFUTED (unchanged).
  2. Wrong image for this module -- still open, but WEAKER: the SIM's own
     procedure downloads a COMBO image over SDIO and never mentions a
     BT-only UART download for this part.
  3. Combo needs both images -- superseded: s4.4.3 says the combo image IS
     both.
  4. Secure boot / signature -- still open, still untestable from the host.
  5. Card needs flow control -- WITHDRAWN (CON[7] violated; see above).
  6. ★ NEW, and now the leading one: **we were talking at the wrong rate.**

ALSO SETTLED BY THESE DOCUMENTS, so nobody re-derives them

  * J54 pin 54 = W_DISABLE2# = NXP BT_INDEPENDENT_RESET, input, active low,
    3.3 V; pin 56 = W_DISABLE1# = PDn, full power-down for BOTH radios
    (high = normal).  Two different pins, two different jobs.
  * s2.4.2: "A firmware download to the module is required after each reset."
    ★ So pulsing BT_RST after a successful download DISCARDS the firmware --
    it cannot start it.  BT_RST is a start-over lever, not a kick-into-life
    lever, and the 2026-08-24 idea of using it that way is dead.
  * s2.4.2 also: BT_RESET/WLAN_RESET "can be left open if they are not
    needed" -- so leaving it idle-high, as we always have, is sanctioned.
  * s2.4.1: PDn must be asserted a MINIMUM OF 100 ms for correct reset.
    We hold it 110 ms (10 ms + 100 ms in m2ReleaseWifiReset) -- compliant,
    but with only 10% margin, so do not shorten it.
  * s2.4.4: BT_DEV_WAKE (J54 pin 42 -> GPIO_AD_28) is a host-to-module
    wake input, active low.  ★ We have NEVER driven it.  Untested lever;
    note it collides with LPSPI1 SCK on the Arduino header.
  * Card VIO defaults to 1.8 V, which is why U354/U355 exist on the EVKB.
    Already understood and already handled -- not a fault.

THE BOOT-SLEEP WAKE PULSE -- 2026-08-25 -- THE CARD REACTS, AND STILL WILL NOT RUN
=====================================================

FOUND BY READING NXP'S LOADER FOR ITS CALL ORDER, not its code.
`fw_loader_uart.c` calls `wakeUpControllerFromBootSleep()` from
`uart_fw_download()` -- BEFORE the image, not after it -- and for the RT1170 it
names **GPIO_DISP_B2_13**: re-mux away from LPUART2_RTS_B to a plain GPIO,
drive LOW, hold 10 ms, hand the pad back to LPUART2_RTS_B.  Pin identity, level
and call order only; nothing transcribed (LA_OPT), same standard as the V3
decode.  Implemented as `m2WakeFromBootSleep()`, ON by default.

★ THAT PAD IS THE ONE THIS TREE HAD BEEN CALLING "the card's CTS input" (J54
pin 36).  NXP do not treat it as flow control at this point in the sequence at
all -- they treat it as a wake trigger.  And it is NOT the CTS experiment
already run and refuted: that one held the pad LOW indefinitely, from BEFORE
the module reset (latching CON[7]=0, a Reserved configuration), mux left on
GPIO and never returned.

RESULT -- and there IS a measured change, the first this programme has produced:

    run B  BT download, no CTS, NO wake     start_inds=2
    run C  BT download, CTS held, NO wake   start_inds=2
    run D  BT download, no CTS, WAKE PULSE  start_inds=3   <-- one variable

=====================================================
THE CONTINUITY PROBE FINDS IT -- PDn IS CLAMPED LOW -- 2026-08-25
=====================================================

Built for rt1062 (`M2_CONTINUITY_PROBE`, default ON there, OFF on rt1176 so the
two gates are undisturbed), run on the MIMXRT1060-EVKB with R345 and R96 both
hand-bridged:

    rx_continuity: pullup_reads=1 pulldown_reads=1 -> DRIVEN HIGH externally
    pdn_swing:     drives_low=1 drives_high=0      -> PIN STUCK
    rx_after_pdn:  any_high=1 edges=0

★★ THREE ANSWERS IN ONE RUN, and the netlist could not have given any of them.

  1. **The RX path is GOOD.**  `pullup_reads=1 pulldown_reads=1` means something
     EXTERNAL holds that pad high through both of our internal pulls -- which is
     exactly what a healthy idle UART line looks like.  So both hand bridges
     conduct, U10 is driving, and the card side is powered.  Everything I was
     worried about downstream is fine.

  2. **PDn CANNOT BE RELEASED.**  `drives_low=1 drives_high=0`: the pin pulls
     low happily and cannot go high.  PDn low is FULL POWER-DOWN, so the module
     is being held off.

  3. `edges=0` after the cycle follows from (2) and is the whole silence: a
     module in power-down never boots, so it never greets, so start_inds=0.

WHY THE PIN IS STUCK -- and it is the collision I flagged when recommending the
R345 bridge, now measured rather than predicted.  GPIO_AD_B1_03 fans out to
THREE fitted loads:

    GPIO_AD_B1_03 -R343 (FITTED)- SD_PWREN -R235- Q5 gate (with R232)
                  -R344 (FITTED)- SPDIF_IN -J20.1 | J20.2 - U15.4
                  -R345 (bridged)- WL_RST# -R89-R82- J8.56 (PDn)

Both competitors clamp it: Q5's gate network is a resistive pull toward ground,
and U15.4 on the SPDIF net is an active driver.  Through two 47R series parts
our GPIO wins the pull-DOWN and loses the pull-UP, which is precisely the
asymmetry measured.

THE FIX: **remove R343 and R344**, leaving GPIO_AD_B1_03 driving only WL_RST#.
Cost: SD-card power control and the SPDIF input stop working.  Neither matters
for a Bluetooth bench test, and both are exactly what NXP's own Wi-Fi examples
must assume when they drive this pin as WL_RST.

★ AND NOTE WHAT THIS VINDICATES.  Reading the netlist five different ways could
not distinguish "wired correctly" from "wired correctly and clamped".  One
electrical measurement did it immediately.  The same instrument settled the
same class of question on the 1170 (the R1901 bridge), which is why it was
worth reinstating rather than reading more schematic.

=====================================================
THE "PIN STUCK" VERDICT WAS MY BUG -- GPIO1 vs GPIO6 -- 2026-08-25
=====================================================

★★ RETRACTION, and it cost two resistors off the board.

The previous section concluded "PDn is clamped low" from
`pdn_swing: drives_low=1 drives_high=0`, blamed R343/R344, and recommended
removing them.  They were removed.  The reading did not change.

**The reading was an artefact of my own port.**  The teensy4 core sets
`IOMUXC_GPR_GPR26..29 = 0xFFFFFFFF` in startup.c, which hands every pad to the
FAST GPIO aliases -- GPIO6..GPIO9.  The IOMUX ALT still selects the "GPIO1"
function and NXP's pin naming still calls it GPIO1_IO19, but GPIO6 is what owns
the pad.  My rt1062 port wrote GPIO1 registers, so:

  * every write went nowhere -- PDn was NEVER actually driven, which is by
    itself enough to explain a card that never greets;
  * `GPIO1_PSR` returned a value unrelated to the pin, which is what produced
    the false `drives_low=1 drives_high=0`.  Read low, read low: the first
    inverts to "true", the second stays "false".  A stuck pin and a
    disconnected register look identical through that code.

★ AND IT MEANS THE RX VERDICT IN THAT SECTION WAS ALSO UNSAFE, for the same
reason -- it was read from GPIO1_PSR too.  Neither line should have been
trusted.

CORRECTED (GPIO6 throughout on rt1062):

    rx_continuity: pullup_reads=1 pulldown_reads=1 -> DRIVEN HIGH externally
    pdn_swing:     drives_low=1 drives_high=1      -> PIN SWINGS
    rx_after_pdn:  any_high=1 edges=0

So with the port fixed: **PDn genuinely cycles** (verified by reading the pad
back while driving it), and **the RX line is electrically healthy** -- held high
by something external through both of our internal pulls, which is what an idle
UART from a powered card looks like.  Both hand bridges conduct.

AND THE CARD STILL DOES NOT GREET: `edges=0`, `start_inds=0`, `chip_id=0x0000`.

★ R343/R344 DID NOT NEED REMOVING.  With GPIO6 the pin swings regardless.  The
removal is harmless for a Bluetooth bench test (it costs SD-card power control
and the SPDIF input) but it was asked for on a wrong diagnosis, and that is
worth recording so nobody repeats it on the next board.

WHAT IS STILL OPEN.  The most likely remaining candidate is simply the WATCH
WINDOW: `rx_after_pdn` samples for 400 ms, while the 1170's own sequence waits
1000 ms after PDn release before the loader looks, and the greeting is known to
arrive within roughly the first 200 ms of THAT wait on that board.  A 1060 that
boots more slowly would fall outside a 400 ms window entirely.  Widening it is
the next cheap test.

★★ AND `bt init` IS UNREACHABLE THERE -- an SDK defect, not a Bluetooth result.
Traced through three macros:

    SHELL_CMD_REGISTER(bt, &bt_cmds, "...", cmd_default_handler)
      -> SHELL_CMD_ARG_REGISTER(bt, ..., minarg=0, additonarg=0)
      -> SHELL_COMMAND_EXDEFINE(..., miniArg=0, addtionArg=0)
      -> .parameter.range.min = 0 , .parameter.range.max = 0

and fsl_shell.c accepts a command only when
`((range.min + 1) <= argc) && ((range.max + 1) >= argc)` -- i.e. argc == 1
exactly.  So `bt` alone prints its subcommand tree and **every subcommand is
rejected by construction**, with the misleading message "Incorrect command
parameter(s)".

the NEWER `edgefast_open` shell on the 1170 ACCEPTS `bt init` (it hangs, which
is the finding recorded earlier).  The older `edgefast_bluetooth` shell cannot
dispatch subcommands at all in this configuration.

tree ships `a2dp_source` and `a2dp_sink` for `evkcmimxrt1060`, and those
initialise the stack AT STARTUP with no shell interaction -- so they exercise
exactly the path `bt init` would, without needing the broken dispatch.

NXP'S CHATTY LOADER ON THE 1170 -- THE 3 MBAUD SWITCH CORRUPTS THE LINK -- 2026-08-26
=====================================================

Ran the OLDER edgefast_bluetooth shell (the one that prints, and which supports
evkbmimxrt1170) on the 1170, with DEBUG_PRINT enabled in fw_loader_uart.c so
NXP's own loader narrates every step.  This is on the board where downloads
otherwise complete.  Command is `bt.init` (dotted -- that shell's syntax).

★★ THE FINDING, and it is a NEW one: **the download's secondary-baud switch to
3,000,000 succeeds, and every byte after it is CORRUPT.**

Sequence from NXP's own trace:
  1. loader opens at 115200, the card requests header bytes correctly
     (REQ=0xA7 Len=10 Off=0 Err=0), CRCs valid;
  2. a `command5`/type-5 UART-config block is sent (register writes at
     0x7F00008F..94) and ACKed -- so on THIS board/firmware the type-5 command
     IS accepted (contrast our own probe, where injecting it standalone was
     rejected: order and context matter);
  3. `change baud-rate req to 3000000`, `reInitUartInst(BR 3000000) FlowCtrl 0`,
     `changeBaudrate() ret 0` -- the switch is reported successful;
  4. immediately after: `Invalid Header 0x00`, `Invalid Header 0x71`,
     `REQ = 0xA7, Len = 10a7, Off = 5400, Err = 400, CRC = 0`,
     `CRC Mismatched`, and `file download: 0: 131840` -- stuck at offset 0
     forever.  The offsets are byte-concatenations (`5400` = two bytes run
     together): classic wrong-baud framing loss.

★ WHAT THAT MEANS.  The card DID switch to 3 Mbaud and IS transmitting; the
host cannot cleanly receive it.  The RT1176 LPUART2 at 3,000,000 baud on this
board -- DMA-fed, no flow control (R1816/R1902 rework not done) -- does not
recover the card's frames.  Two independent tries:
  * flow control left ON (stock): the FIRST post-switch header times out, the
    loader falls back to 115200, retries, and LOOPS FOREVER printing dots
    (observed >20 min).  A patch reverting only the 0,0 shell-range issue does
    not reach this; the download loop itself never terminates.
  * flow control forced OFF at all three secondary-baud reInit sites, PLUS the
    card's CTS asserted by holding the RTS pad (GPIO_DISP_B2_13) low as GPIO:
    the switch now completes and the corruption above appears -- so the earlier
    infinite loop was the loader retrying a link it could not read, not a
    different failure.

★★ HOW THIS RELATES TO OUR OWN PROBE.  Our m2_hci_probe NEVER does the type-5
config + 3 Mbaud switch during download -- it downloads the whole image at
115200 and succeeds (chunks=142, all bytes).  NXP's stock flow tries to go to
3 Mbaud DURING the download and corrupts.  So on THIS board there are two
different failure modes depending on the download path, and NEITHER ends with a
running controller:
  * our path: clean 115200 download, image accepted, controller silent
    (the AFTER-download mystery -- unchanged, still the CA-276115 question);
  * NXP's path: 3 Mbaud switch mid-download, link corrupts, download never
    completes (a BOARD/baud-integrity problem, distinct and lower-level).

★ THE ACTIONABLE PIECE FOR THE BENCH: the 3 Mbaud instability is consistent
with the missing flow control (R1816 removed + R1902 fitted) that NXP's rework
guide requires and this board does not have -- at 3 Mbaud with DMA and no RTS
back-pressure, the host cannot keep up cleanly.  This is the FIRST evidence
that the un-done half of the rework has an observable cost, and it is on the
DOWNLOAD, not the post-download silence.  It does NOT explain the silence after
our own clean 115200 download, which remains the module-level question for
u-blox.

★★ THE ROOT CAUSE WAS ONLY THE HOST RTS -- NOT THE BAUD RATE.  The raw reset AND
the driver both succeed at 115200 on attempt 1; the baud sweep never runs.  So
the controller runs HCI at the DOWNLOAD rate (115200 for us), and the IW416
firmware gates its HCI transmit on the host's RTS line (BT_UART_RTS =
GPIO_DISP_B2_13).  Our probe never asserted it, so the controller sat mute.  The
3 Mbaud / 0xFC09-set-baud theories from instrumenting EdgeFast were red herrings
-- EdgeFast works because of its RTS/CTS FLOW CONTROL, not its 3 M rate.
manufacturer=0x0048 is Marvell, the IW416 lineage.

★ HOW EDGEFAST WAS INSTRUMENTED (its source, LA_OPT facts-only): its HCI UART
opens with enableRxRTS/enableTxCTS = 1 (hardware RTS/CTS on).  That flow control
is the thing our probe lacked.  Also settled a scare along the way:
board.h's `BOARD_BT_UART_BASEADDR LPUART7` is a STALE default -- the RevC3
netlist (BT_UART_* -> GPIO_DISP_B2_10-13, bridged to LPUART2_TXD/RXD via
R2019/R2020) and the shell's own pin-mux both put the M.2 BT UART on LPUART2,
matching this tree.  Our probe was on the right UART all along.

★ THE FIX IS AN EXPLICIT OPTION, NOT THE DEFAULT.  Build the bench image with
-DM2_BT_ASSERT_CTS=ON to get HCI on hardware.  Default stays OFF so the 121 QEMU
gates (which model no UART flow control) are byte-unchanged.  Caveat: the assert

with 1 G Ethernet.  For A2DP media rates, revisit proper dynamic hardware RXRTSE
flow control; the static assert is sufficient for BT-1/BT-2 control traffic.

★ TWO BUGS FOUND AND FIXED HERE, both worth keeping:
  1. The SSP request events (IO_Capability_Request 0x31 .. Simple_Pairing_Complete
     0x36) sit ABOVE the post-Reset default HCI Event Mask, so the controller
     could not ask the host to pair: Authentication_Requested failed 0x05 with NO
     io_cap_req in between.  Fix: Set_Event_Mask all-ones (0x0C01) before connect.
  2. Set_Connection_Encryption must wait for Authentication_Complete, not just
     Simple_Pairing_Complete -- firing it after pairing-complete but before
     auth-complete returns 0x2F Insufficient Security.  Event order is
     pairing_complete -> link_key -> auth_complete -> (then) encryption.

Link key is in RAM only (not yet persisted) -- reconnect after reboot re-pairs.

==============================================================================
m2_uap_lwip on real hardware -- 2026-08-22
MIMXRT1170-EVKB RevC3 + u-blox M2-MAYA-W161 (IW416), fw_release=0x9B105C15
Client: ESP8266 running tools/esp8266-uapclient (static 192.168.44.50)
==============================================================================
The AP hosts, a client joins, and the client's packets arrive at a BOUND UDP
SOCKET.  That last step is what makes this an upstack rather than a driver
demo: the frames have travelled air -> RxPD -> bss demux -> netif -> lwip ->
IP -> UDP -> socket, and every layer had to be right for the callback to fire.

BRING-UP
------------------------------------------------------------------------------
    sdio_begin=ok
    iw416_begin=ok
    fw_download=ok
    fw_release=0x9B105C15 mac=6C1DEB910C45
    uap_configure=ok result=0x0
    uap_bss_start=ok result=0x0
    uap_hosting ssid=RT1176-UAP-TEST chan=6
    uap_netif_up addr=192.168.44.1
    uap_udp_bound port=5001
    uap_lwip_done

  uapConfigure() sends the FULL open-AP TLV set.  It has to: a minimal
  SYS_CONFIGURE kills this firmware's command port outright (W17 FAULT 1,
  reproduced 5/5 runs), so there is no harmless partial config and no config
  GET.  The example does not offer one.

THE PROOF -- A PACKET AT THE SOCKET
------------------------------------------------------------------------------
    uap_udp_first from=192.168.44.50:58394 len=23
                  ascii=RT1176-UAP-CLIENT-HELLO
                  bytes=5254313137362D5541502D434C49454E542D48454C4C4F

  * from 192.168.44.50 -- the client's static address, configured on the CLIENT
    and never told to this firmware;
  * "RT1176-UAP-CLIENT-HELLO", 23 bytes -- the exact literal in the client
    sketch, which appears NOWHERE in this image.  Grep it: it is not here.
  * delivered through udp_recv() on a pcb bound to port 5001, so lwip parsed
    the Ethernet header, the IP header and the UDP header on the way.

  A raw frame counter could have been fooled by a beacon or by another
  station's traffic.  A payload this firmware cannot generate, arriving at a
  socket this firmware bound, cannot.

THE ACCOUNTING IS EXACT, WHICH IS THE POINT
------------------------------------------------------------------------------
    hb card=1 bss=1 udp_rx=74 udp_bytes=1702 rx_bss0=0 rx_bss1=75 unrouted=0

    udp_rx=74 x 23 bytes = 1702 = udp_bytes            EXACT
    rx_bss1=75 = 74 UDP datagrams + 1 gratuitous ARP   EXACT
    rx_bss0=0     nothing was mis-tagged to the STA interface
    unrouted=0    no frame arrived for an interface that does not exist

  Every frame the card delivered is accounted for, and the one frame that is
  not a UDP datagram is the ARP the client emits on taking its address -- the
  same frame dumped in m2_uap_probe's transcript.  An accounting that closes to
  the byte is worth more than a counter that merely climbs.

WHAT IS NOT HERE
------------------------------------------------------------------------------
  * NO DHCP SERVER.  Clients must be statically configured to match
    (192.168.44.x/24, gateway .1).  That is the handoff's zero-dependency
    Phase 1 and it is a real limitation, not an oversight.
  * NO ROUTING OR NAT between the STA and uAP sides -- explicitly out of scope
    until the rest soaks.
  * NO SECURITY.  The network is open.  WPA2 needs the AKMP/cipher/passphrase
    TLVs on the same builder, and with them this repo's standing rule that a
    PSK is supplied at configure time and never written to a tracked file.
  * TX aggregation is NOT enabled by the uAP netif init, unlike the STA one: a
    batch mixing both interfaces is untested on silicon, and this is the hot
    path W8/W12/W16 were each dug out of.
  * The AP hosts INDEFINITELY -- there is no BSS_STOP.  The board beacons until
    it is reset or reflashed.

QEMU
------------------------------------------------------------------------------
run_qemu.sh asserts the card-ABSENT fallback only, and its vacuity guards are
the substance: an example whose purpose is to TRANSMIT must be provably silent
with no card, so every AP line -- configure, start, hosting, netif, socket --
must be ABSENT.  Demonstrated red by appending a fake `uap_hosting` line to the
capture: "FAIL: emitted '^uap_hosting ' with no card present".

DHCP -- 2026-08-22.  The client is handed an address it did not choose.
==============================================================================
lwip ships a DHCP CLIENT and never a server, so this one is written in the
example.  Smallest thing that works: one /24, a ten-address pool,
DISCOVER/REQUEST only, no persistence, no conflict detection.

    uap_dhcp_up pool=192.168.44.100-109
    uap_dhcp_ack mac=84F3EBB7C45B ip=192.168.44.100

    client: addr_mode=dhcp
            client_state=ASSOCIATED bssid=6C:1D:EB:91:0C:45 ch=6 ip=192.168.44.100

  ★ 192.168.44.100 IS THE ORACLE.  The client did not pick it and cannot have
    guessed it: that address appears nowhere in the client sketch, whose only
    hard-coded address is the .50 static fallback it is no longer using.  It
    came out of this server's pool, through a DISCOVER/OFFER/REQUEST/ACK
    exchange, and was accepted by the ESP8266's own DHCP state machine.  Both
    ends then independently report the same address and the same MAC.

    dhcp_disc=1 dhcp_req=1 dhcp_ack=1 dhcp_full=0

  One DISCOVER, one REQUEST, one ACK.  No retries -- which matters, because a
  client that had to retry would still end up with an address and the run would
  still look successful while hiding a server that answers unreliably.

AND THE TRAFFIC MOVED TO IT
------------------------------------------------------------------------------
    uap_udp_first from=192.168.44.100:56388 len=23 ascii=RT1176-UAP-CLIENT-HELLO
    hb ... udp_rx=77 udp_bytes=1771 rx_bss0=0 rx_bss1=80 unrouted=0

  The datagrams now arrive FROM the assigned address, so the lease is not just
  acknowledged, it is in use.

  The accounting closes exactly again:
    udp_rx=77 x 23 = 1771 = udp_bytes                       EXACT
    rx_bss1=80 = 77 UDP + DISCOVER + REQUEST + gratuitous ARP   EXACT
    rx_bss0=0, unrouted=0

WHY IT LIVES IN THE EXAMPLE
------------------------------------------------------------------------------
It is not in M2Radio, deliberately.  It has not soaked, and promoting an
unsoaked API is how a bad interface becomes permanent.  Promote it once it has
run for more than a bench session and has been made to face the things this
version ignores: leases never expire, a full pool is counted (dhcp_full) but
nothing is reclaimed, and RENEW is answered as though it were a fresh REQUEST.
Those are acceptable in an example that says so and unacceptable in a library
that does not.

★ A LATENT BUG FOUND WHILE WRITING THIS UP, AND FIXED RATHER THAN FILED.  The
DHCP pcb was bound to IP_ANY_TYPE, so it would have answered a DISCOVER arriving
on ANY netif -- meaning the moment this is paired with the station path (the
module supports STA+uAP simultaneously, a later phase), it would have started
handing out addresses on somebody else's network.  It is harmless today because
there is no STA netif in this example, which is precisely why it would have
shipped unnoticed.  Now udp_bind_netif(pcb, &uapNif).  Writing down what a thing
does not do is a good way to notice that it does something worse.

WPA2-PSK -- 2026-08-22.  The AP is secured, and a foreign radio agrees.
==============================================================================
    uap_configure=ok result=0x0
    uap_hosting ssid=RT1176-UAP-TEST chan=6 security=wpa2-psk
    uap_dhcp_ack mac=84F3EBB7C45B ip=192.168.44.100
    hb ... udp_rx=71 udp_bytes=1633 rx_bss0=0 rx_bss1=74 unrouted=0
           dhcp_disc=1 dhcp_req=1 dhcp_ack=1 dhcp_full=0

    client: joining ssid=RT1176-UAP-TEST security=wpa2-psk
            client_state=ASSOCIATED bssid=6C:1D:EB:91:0C:45 ch=6 ip=192.168.44.100

FOUR TLVs ON TOP OF THE OPEN SET
------------------------------------------------------------------------------
    0x0140 ENCRYPT_PROTOCOL  len 2   PROTOCOL_WPA2 0x0020 (was 0x0001, open)
    0x0141 AKMP              len 4   KEY_MGMT_PSK 0x0002 + key_mgmt_operation
    0x0191 PWK_CIPHER        len 4   PROTOCOL_WPA2 + CIPHER_AES_CCMP 0x08 + rsvd
    0x0192 GWK_CIPHER        len 2   CIPHER_AES_CCMP 0x08 + rsvd
    0x013C WPA_PASSPHRASE    len = strlen

  auth_type stays MLAN_AUTH_MODE_OPEN: WPA2-PSK uses open-system 802.11
  authentication and then does the 4-way handshake, so setting a "WPA" auth
  type here would be wrong in the way that produces a network nothing can join.

THE PROOF, AND IT IS THREE INDEPENDENT WITNESSES
------------------------------------------------------------------------------
  1. THE CARD accepted the configuration (result=0x0000) and started the BSS.
  2. A FOREIGN RADIO -- this Mac -- reports:
         Security: WPA2 Personal
     on the same SSID and channel where it reported "Security: None" in the
     open runs earlier the same day.  It knows nothing about our firmware.
  3. THE CLIENT ASSOCIATED, which it could not do without completing a 4-way
     handshake against the passphrase.  A wrong or absent key fails here, and
     fails visibly -- it would sit at assoc=0 forever.
  Then DHCP and traffic on top, unchanged from the open runs.

  The accounting still closes exactly:
     udp_rx=71 x 23 = 1633 = udp_bytes                     EXACT
     rx_bss1=74 = 71 UDP + DISCOVER + REQUEST + ARP        EXACT
     rx_bss0=0, unrouted=0

HOW THE PASSPHRASE IS HANDLED, AND WHY IT IS MECHANICAL
------------------------------------------------------------------------------
  * Supplied ONLY at configure time: -DM2_UAP_PSK="...".
  * Written to uap_creds.h in the BUILD DIRECTORY, which CMake CHECKS is
    gitignored (`git check-ignore`) and refuses to write to otherwise.
  * The client gets it by tools/esp8266-uapclient/make-creds.sh copying it
    file-to-file from that same header into client_creds.h, which was added to
    .gitignore BEFORE it was ever created.
  * A passphrase outside 8..63 characters is a FATAL_ERROR at configure time,
    not a warning -- WPA2 rejects a short one and the AP would come up OPEN
    while the log still said WPA2.  That failure mode is the reason for the
    check.
  * Never printed.  The console says security=wpa2-psk and nothing else; the
    SSID is broadcast so it costs nothing, the passphrase never appears.
  * The one used here was randomly generated for this run, used once, and is
    not a real network's.  Verified absent from every tracked file
    (`git grep -F` on the literal) before committing.

  This is not caution for its own sake: this repo leaked live Wi-Fi passwords
  into PUSHED history in W6, and redacting at HEAD did not undo it.  The
  handling rule is mechanical precisely so it does not depend on anyone being
  careful on the day.

★ NOTE FOR A FRESH CLONE: with no -DM2_UAP_PSK the example builds OPEN and
every gate still passes -- the gates never needed a credential and still do
not.  A missing passphrase is a different AP, not a broken build.

JOIN AND LEAVE -- 2026-08-22.  Membership tracked both ways, three cycles.
==============================================================================
The client leaves and rejoins on a cycle (30 s joined, 8 s away) rather than
being unplugged once.  A single disconnect proves an event fired once; a cycle
shows the AP tracking membership BOTH ways repeatedly, which is what a leave
gate would have to assert -- and it catches the failure a one-shot cannot: a
count that goes 1 -> 0 correctly the first time and never comes back.

    uap_membership from=0 to=1 lastevent=0x1000051 joins=1 leaves=0
    uap_membership from=1 to=0 lastevent=0x100002C joins=1 leaves=1
    uap_membership from=0 to=1 lastevent=0x1000051 joins=2 leaves=1
    uap_membership from=1 to=0 lastevent=0x100002C joins=2 leaves=2
    uap_membership from=0 to=1 lastevent=0x1000051 joins=3 leaves=2
    uap_membership from=1 to=0 lastevent=0x100002C joins=3 leaves=3

  Client side, matching one for one: client_leaving cycle=1,2,3 /
  client_rejoining cycle=1,2,3.

THE EVENT WORD CARRIES MORE THAN AN ID
------------------------------------------------------------------------------
mlan packs the BSS into the event cause:
    EVENT_GET_BSS_TYPE(cause) = (cause >> 24) & 0xFF
    EVENT_GET_BSS_NUM(cause)  = (cause >> 16) & BSS_NUM_MASK
So the observed values decode as:

    0x0100002C -> bss_type 1 (uAP), EVENT_MICRO_AP_STA_DEAUTH  (0x2C)
    0x01000051 -> bss_type 1 (uAP), EVENT_MICRO_AP_RSN_CONNECT (0x51)

  Both are tagged bss_type=1, which is independent confirmation that these are
  uAP events and not something leaking from the station side.

★ THE JOIN EVENT ID DEPENDS ON THE SECURITY MODE, and this is the finding worth
carrying forward.  On the OPEN AP the join event was
EVENT_MICRO_AP_STA_ASSOC (0x2D) -- recorded earlier in this transcript.  On the
WPA2 AP it is EVENT_MICRO_AP_RSN_CONNECT (0x51), because RSN_CONNECT is raised
after the 4-way handshake completes, which is the point at which a station on a
secured network is actually usable.

  A join gate that asserts 0x2D would therefore PASS on an open AP and FAIL on
  a WPA2 one, for a link that is working perfectly.  Any such gate must accept
  BOTH, or assert on STA_LIST's count instead -- which is why the count is what
  this example treats as authoritative.

WHY MEMBERSHIP IS POLLED AND NOT ACCUMULATED FROM EVENTS
------------------------------------------------------------------------------
sta_count comes from STA_LIST every 2 s; the events only say WHEN it changed.
An event can be missed -- a service pass that ran late, a full ring -- and a
membership figure that is only ever adjusted by deltas drifts silently and
permanently once one is lost.  The card's own list cannot drift.  joins/leaves
are derived from observed transitions of that count, so they are counts of what
was SEEN to change rather than of events received.

THE ~17% TX LOSS, CHASED AND CLOSED -- 2026-08-22
==============================================================================
W17 left ~17% of AP->client ARP requests unanswered with client power save OFF,
and named three suspects: lwip rate-limiting, air loss, and "something else".
It was none of those in the sense meant.  It is the BROADCAST path, and it is
not a fault.

WHAT WAS WRONG WITH THE OLD MEASUREMENT
------------------------------------------------------------------------------
Two things, and both had to be fixed before the number could be trusted:
  1. IT AGGREGATED.  "25 of 30" cannot distinguish losses spread evenly from
     losses arriving in one burst, and those imply different causes.
  2. IT HAD A BUILT-IN LAG.  A request went out at the end of a 5 s service
     window and its reply was counted in the NEXT one, so the final request
     could never be counted and the ratio was structurally pessimistic.
The new probe records a per-request HIT or MISS with its own bounded wait.

THE A/B -- ONE VARIABLE, THE DESTINATION
------------------------------------------------------------------------------
    arp_probe begin dst=broadcast target=192.168.44.100 n=40 wait_ms=400
    XX...X.......................X..X.....X.
    arp_probe done sent=40 hit=34 miss=6 pct=85

    arp_probe begin dst=unicast   target=192.168.44.100 n=40 wait_ms=400
    ........................................
    arp_probe done sent=40 hit=40 miss=0 pct=100

  Same client, same channel, same firmware image, minutes apart.  BROADCAST 85%,
  UNICAST 100%.  And the broadcast misses are SCATTERED, not bursty -- which is
  what the per-request record buys: a burst would have implied a buffer or a
  timing window, and the spread implies plain per-frame loss.

  ★ 85% also agrees with the old aggregate's 83%.  So the earlier measurement
    was not WRONG, just uninformative -- worth saying, because a new method that
    disagreed with the old one would have needed explaining before anything
    built on it.

WHY, AND WHY IT IS NOT A BUG
------------------------------------------------------------------------------
802.11 ACKNOWLEDGES AND RETRIES UNICAST FRAMES, AND DOES NEITHER FOR BROADCAST.
A unicast frame that collides is retried until it gets through; a broadcast
frame that collides is simply gone.  Nothing in the driver, the card or the
client is misbehaving -- an AP that broadcasts to a station is using a lossy
primitive, by design.
  arp_txfail stayed 0 and txcount tracked arp_sent exactly in every arm, so the
  frames always left the host.  The loss is on the air and only on the
  unacknowledged path.

THE CONSEQUENCE, WHICH WAS A REAL DEFECT
------------------------------------------------------------------------------
This example's DHCP server replied to the BROADCAST address, so every OFFER and
ACK inherited that ~15%.  That is exactly the asymmetry recorded earlier in this
transcript and left unexplained:

    before (broadcast replies, 3 rejoins)   dhcp_disc=4 dhcp_req=3 dhcp_ack=3
                                            -- one DISCOVER never became a
                                               REQUEST, i.e. one OFFER was lost
    after  (unicast replies,   4 joins)     dhcp_disc=4 dhcp_req=4 dhcp_ack=4
                                            dhcp_bcast=0

  Fixed by replying to the address being offered when RFC 2131 s4.1 allows it:
  a client that sets the BROADCAST flag cannot receive a unicast before it is
  configured and MUST be broadcast to; a client that leaves it clear can be
  unicast.  No client seen here sets it (dhcp_bcast=0).
  Replying unicast to an address the client does not hold yet needs an ARP
  mapping it cannot answer for, so one is installed directly from the chaddr
  being replied to -- which is what ETHARP_SUPPORT_STATIC_ENTRIES is for.  That
  is enabled for THIS example only (add_definitions before the lwip import,
  directory-scoped, its own build tree); the shared lwip port config is
  untouched and m2_lwip_test is unaffected.

WHAT THIS MEANS FOR ANYTHING BUILT ON TOP
------------------------------------------------------------------------------
  * Unicast AP->client traffic is LOSSLESS here (40/40).  TX is not merely
    correct, it is reliable, which is more than the earlier entry could say.
  * ANY protocol that depends on broadcast reaching a uAP client must tolerate
    ~15% loss or avoid broadcast.  DHCP was the instance that mattered; ARP
    requests from the AP are the other obvious one, and lwip retries those on
    its own.
  * A gate asserting "N sent, N received" over a broadcast path would be flaky
    by construction, and it would look like a firmware regression.

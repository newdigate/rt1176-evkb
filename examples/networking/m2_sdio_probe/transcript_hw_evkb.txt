What is PROVEN about the host side
----------------------------------

Controller and pads match NXP's own board support for this EVK
(mcuxsdk examples/_boards/evkbmimxrt1170):

  BOARD_SDMMC_SDIO_HOST_BASEADDR = USDHC1            <- same controller
  SDIO_RST = GPIO_AD_16 (ball N17) as GPIO9_IO15     <- same pad

  BOARD_SDMMC_SD_IO_VOLTAGE_CONTROL_TYPE = kSD_IOVoltageCtrlByHost
                                                     <- 3.3V initial is correct

`rst_pads: ... dr=1 psr=1` for both lines, with SION forced on so PSR reflects
the actual pin. Both resets are released AND CONFIRMED HIGH AT THE PIN. This is
not "we wrote a register and hoped".

`pres_state=0xFF888088`, read through the USDHC1 pads themselves:

  bit 31:24 DLSL = 0xFF  all DAT lines idle HIGH
  bit 23    CLSL = 1     CMD idles HIGH — the R373 10K pull-up works
  bit 3     SDSTB = 1    SD clock stable
  bit 7     SDOFF = 1    clock gated while idle (normal)

Ruled out: pads not muxed, NVCC_SD rail dead, anything holding the bus low,
module dragging lines down, clock divider unstable.

`int_status=0x18000` = ERR(15) | CTOE(16). The controller sends CMD5 and nothing
answers; CC never sets. (QEMU reports 0x18001 — it also sets CC, which the
silicon correctly does not.)

Hypotheses tested and REFUTED
-----------------------------

1. Missing initialisation clocks.
   begin() used delayMicroseconds(2000) where SdFat's hardware-proven
   SdioTeensy uses SYS_CTRL[INITA]. i.MX USDHC gates SD_CLK while idle, so the
   delay emitted zero clocks. FIXED — INITA now sent, confirmed to self-clear.
   Real defect. Not this defect.

2. Module held in reset (single line, GPIO3/ALT5).
   GPIO_AD_16 -> J54 pin 23 has no pull resistor on either side, so it floats
   at POR. Drove it via GPIO3/ALT5. Read-back was inconclusive because SION was
   off. Real defect. Not this defect.

3. Wrong reset instance and sequence.
   NXP drives BOTH lines via GPIO9 (ALT10), not GPIO3: SDIO_RST high, wait
   100 ms, WL_RST high, wait 100 ms. Replicated exactly, plus SION so the pads
   could be read back. Both now confirmed high at the pin. Not this defect.

4. USDHC clock root.
   SdFat's RT1176 branch — and this driver, inheriting its note — take
   SYS_PLL2_PFD2 (mux 4, div 2 -> 198 MHz) while ASSUMING the boot ROM left
   PFD2 at 396 MHz; the imxrt1176 core's startup.c never programs PLL2. NXP
   does not assume it: BOARD_USDHC1ClockConfiguration() calls CLOCK_InitSysPll2()
   and CLOCK_InitPfd(kCLOCK_PllSys2, kCLOCK_Pfd2, 24) first.
   The trap is that a wrong root is nearly invisible — SDSTB asserts either way,
   so the controller looks healthy while the card sees the wrong frequency.
   Switched to OSC_24M (mux 1, undivided), which is always running and
   boot-independent, with BASE_CLOCK matched. Kept, because it removes an
   assumption. Not this defect either.

NOTE ON REASONING: hypothesis 4 was initially dismissed on the grounds that
SDSTB asserted and INITA self-cleared. That was wrong. SDSTB proves the divider
is stable, NOT that the frequency is what the driver believes. The dismissal
cost a cycle; the note is here so the next person does not repeat it.

What is left
------------

Firmware has now replicated NXP's documented path for this board. The remaining
candidates are physical or card-specific and cannot be settled from firmware:

1. The card is not making contact, or is faulty. It is seated and screwed, but
   "screwed down" and "all 75 contacts mating" are not the same claim.
2. The 32.768 kHz sleep clock on J54 pin 50 (from Y2 via R823, both fitted,
   Y2 powered from WL_3V3). Some combo parts will not leave internal reset
   without it. Never measured.
3. Something specific to this u-blox card versus the NXP/Murata M.2 cards NXP
   validates against.

Next steps that would actually decide it:
  * A scope on J54 pin 9 (CLK) and pin 11 (CMD) during the CMD5 attempt: does
    the clock reach the connector, and does anything drive CMD?
  * A scope or counter on J54 pin 50 to confirm Y2 is oscillating.
  * Swap in a known-good M.2 card, or try this card in a known-good host.

Not suspected
-------------

The SDIO I/O voltage. Every other M.2 signal is level-shifted to 1.8V while the
six SDIO lines run straight to the MCU, which invites the theory that NVCC_SD
must be switched to 1.8V (it is selectable — U311, an NX3L1G53GT SPDT switch,
under SD1_VSELECT). But NXP configures kSD_IOVoltageCtrlByHost, which is the
UHS switch performed AFTER identification, and standard SDIO begins at 3.3V.
The default 3.3V leg is correct for CMD5.

But comparing the two configs turned up something both share:

    #elif defined(WIFI_IW416_BOARD_UBX_MAYA_W1_USD)
    #define SD8978
    #define SDMMCHOST_OPERATION_VOLTAGE_1V8      <-- and the same in MURATA_1XK_M2

NXP run these modules' SDIO at 1.8 V. This driver had only ever used the 3.3 V
default. The switch is real and MCU-controllable on this board:

    GPIO_AD_34 (ball J16) ALT4 = USDHC1_VSELECT
      -> R168 (FITTED) -> SD1_VSELECT -> U311.5 (NX3L1G53GT SPDT)
      -> selects VDD_1V8 (pin 6) or SENSOR_3V3 (pins 7/8) onto SD1_POSV
      -> R1977 -> NVCC_SD

and it is SAFE rather than a level mismatch, because NVCC_SD feeds both the bus
pull-ups (R373/374/375) AND the MCU's own NVCC_SD1 pad supply (ball D14, via
R375) — the whole bus moves together. (NVCC_SD2, ball G13, is a separate domain
on FLASH_VCC and is unaffected.)

Implemented as SdioHost::useIoVoltage1V8(), applied inside begin() after RSTA
clears VEND_SPEC, then VEND_SPEC[1] = VSELECT.

Result: unchanged.

    sdio_begin=cmd5-no-response rc=-6
    int_status=0x18000 r4=0x0

The card is equally silent at 1.8 V and at 3.3 V.

CAVEAT: without a meter on TP33 (which sits directly on NVCC_SD) it cannot be
proven the rail actually moved. The evidence that it did is indirect — the bus
still idles high afterwards, which needs live pull-ups on a live rail. Anyone
with a multimeter should confirm at TP33 before treating 1.8 V as ruled out.

The capability is kept but defaults OFF: J15 is the same bus and a 3.3 V-only
microSD must not meet a 1.8 V rail.

=====================================================
*** THE CARD IS ALIVE *** — BT_WAKE_HOST held low
=====================================================

Date: 2026-08-17 (same session). First positive evidence of life from the card.

J54 pin 20 (UART_WAKE# / NXP BT_WAKE_HOST) is the ONLY card->host signal on this
connector that reaches the MCU:

    J54.20 -> R811 (0R, FITTED) -> BT_WAKE_B_3V3 -> R238 (0R, FITTED)
           -> U19.N16 = GPIO_AD_27          (no level shifter; pin 20 is 3.3 V)

Pin 21 (SDIO_WAKE#) is populated but blocked at jumper J104, open by default.
Pin 22 (BT UART TX) dies at R1901, which is DNP. So pin 20 is the only channel.

The EVKB provides NO pull-up on that net (its only members are R238, R811 and
the MCU ball), and the datasheet calls the pin open-drain, "Pullup required on
platform" -- so the MCU's internal pull-up does that job.

Measurement, with the pad configured as an input:

    bt_wake(pin20): pullup_reads=0 pulldown_reads=0 pad=0x4 ever_low=1
      -> HELD LOW externally

The control is what makes this conclusive. A single low reading could just mean
the internal pull-up never took effect. Reading under pull-UP and then pull-DOWN
separates the cases:

    up=1 down=0 -> floating, nothing drives it
    up=0 down=0 -> something ACTIVELY HOLDS IT LOW   <-- what we see
    up=1 down=1 -> something actively holds it high

`pad=0x4` confirms the pad writes stick, and `gdir=0x40008000` (bits 15 and 30
only) confirms bit 26 is an input, so the MCU is not driving it.

WHY THIS MEANS THE CARD IS POWERED AND RUNNING
----------------------------------------------

Per the datasheet (Figure 8), UART_WAKE# is driven by the card's on-board
NTB0104 level shifter, whose output-enable is tied to the card's VIO through
R12. If the card's internal 1.8 V DC-DC were not running, that shifter would be
DISABLED and its output high-Z -- and our internal pull-up would read HIGH.

It reads LOW. So the card has 3.3 V, its internal DC-DC is up, its VIO rail is
up, the on-card shifter is enabled, and it is actively asserting BT_WAKE_HOST.

The only thing on that net besides the MCU is the card, so nothing else can be
responsible.

WHAT THIS OVERTURNS
-------------------

Every earlier section of this transcript concluded "the card or the socket is
dead". That conclusion is now WRONG and is retained above only as the record of
how the investigation ran. The card is neither dead nor failing to make contact:
it is powered, running, and driving a pin the host can see.

The socket is also at least partly proven: pin 20 is making contact.

WHAT IT DOES NOT EXPLAIN
------------------------

Why the WLAN side never answers CMD5. The card being alive makes that harder to
explain, not easier -- it removes the simplest available answer.

Worth noting BT_WAKE_HOST asserted low is what an NXP BT controller does when it
has something to say to the host. This card may be sitting in its boot ROM
waiting for a firmware download over UART -- which on this board it can never
receive an answer to, because R1901 is DNP.

=====================================================
TRANSMIT-AND-WATCH over LPUART2 — no reaction
=====================================================

Date: 2026-08-17 (same session). Serial2 (LPUART2) brought up for this, TX only
in practice -- the card's reply path dies at DNP R1901. No flow control: CTS/RTS
would mux DISP_B2_12/13, which are the gigabit PHY's interrupt and reset lines.

Method: sample pin 20 for ~20 ms (2000 reads) as a baseline, transmit HCI Reset
(H4: 01 03 0C 00), sample another ~20 ms, and compare. If the card is listening,
processing an HCI command is exactly the kind of thing that makes an NXP
controller move BT_WAKE_HOST.

    serial2=up_115200
    hci_probe: before[high=0 edges=0] after[high=0 edges=0] serial2_rx: total=1 last=0x0
    (identical on every 5 s repetition)

RESULT: no reaction. Pin 20 stays low; ZERO edges in either window. The card
does not observably respond to UART traffic.

The RX byte is not from the card
--------------------------------

`serial2_rx: total=1 last=0x0` looked alarming -- R1901 is DNP, so nothing
should ever arrive. It is an artefact: exactly ONE byte, value 0x00, latched at
Serial2.begin() and never repeated across 40 s of running. That is the classic
signature of a pad being muxed -- the line settling to idle-high reads as a
start bit followed by zeros. Note this pad also reaches Arduino header pin J9.2
through fitted R2, so it is a floating header pin either way.

Checked rather than assumed, because if real bytes had accumulated the R1901
finding would be wrong and Track B would not be blocked.

What the permanently-low wake line does and does not tell us
------------------------------------------------------------

BT_WAKE_HOST is held low continuously, from power-up, and never moves. The
datasheet says "Active Low by default... used by the Bluetooth radio to wake up
the platform". Two readings remain open and this test does not separate them:

 (a) The card's support circuitry is powered (its NTB0104 is enabled, which
     requires the card's VIO) but the MAYA-W1 module inside is NOT running, so
     its BT_WAKE_HOST output simply sits low.
 (b) Low is the module's normal asserted state after boot, and the module IS
     running but has nothing further to say over a channel it cannot complete.

Either way the card is drawing power and driving a pin, which is more than a
dead card does.

Next step that WOULD separate them: fit R1901 (0402, 0 Ω) and read the card's
UART directly. That is now the single highest-value modification to this board
-- it converts the only bidirectional interface the card has from write-only to
usable, and would say immediately whether the module answers HCI at all.

=====================================================
R1901 BRIDGED — the card's UART TX is stuck LOW
=====================================================

Date: 2026-08-18. R1901 (module->MCU RXD, DNP from the factory) fitted by hand
with a solder bridge.

### The bridge conducts — verified, not assumed

    r1901_bridge: pullup_reads=0 pulldown_reads=0 -> DRIVEN LOW

Same pull-up/pull-down control used for pin 20. With R1901 open the MCU RX pad
has no driver at all -- its net reaches only Arduino header pin J9.2 (via fitted
R2) and the DNP pad -- so it would FLOAT and an internal pull would swing it.
It does not swing: the line is actively driven. The bridge works.

### But it is driven LOW, and a UART idle line must be HIGH

So the card's UART_TXD sits at logic zero permanently -- exactly like
BT_WAKE_HOST on pin 20.

### Pulsing BT_INDEPENDENT_RESET changes nothing

GPIO_AD_15 -> J54 pin 54 (W_DISABLE2#) is the one card reset the MCU can
actually drive. Asserted low 20 ms, released, then the UART TX line watched for
150 ms at ~100 kHz:

    bt_reset_pulse: rx_any_high=0 rx_edges=0

Zero edges. The line never leaves low.

(`serial2_rx: total` incrementing by one per cycle is our own artefact: the test
re-calls Serial2.begin(), and re-muxing the pad latches another spurious 0x00.)

### The picture this completes

EVERY card->host signal is stuck at logic low, and nothing we do moves any of
them:

    pin 20  UART_WAKE# / BT_WAKE_HOST   held low
    pin 22  UART_TXD                    held low  (now visible thanks to R1901)
    SDIO    CMD                         no response to CMD5, ever

They are DRIVEN low, not floating -- which means the card's own DC-DC and its
level shifters (NTB0104, U355) are powered and working. What sits behind them,
the MAYA-W1 module itself, has all outputs at zero. That is what a chip held in
reset or not booting looks like.

### The one control we do not have: PDn

J54 pin 56 (W_DISABLE1# = PDn, "High = normal mode, Low = full power-down") is
the master power-down for the whole radio. On RevC3 the MCU CANNOT drive it:
R404 is DNP, so GPIO_AD_31 is disconnected and the pin merely sits on the 10K
pull-up R829 to WL_3V3.

A module held in full power-down would present exactly what we measure: powered
support circuitry, every module output low, no SDIO, no UART, no wake.

We cannot currently confirm or refute that, because we can neither drive nor
read pin 56.

### Next modification, precisely motivated

**Fit R404** (0402, 0 Ω -- the same job just done on R1901). That connects
GPIO_AD_31 to the PDn chain and lets firmware power-cycle the radio properly.
It is the only untested control left, and its failure mode is an exact match for
the symptom.

Note GPIO_AD_31 is also Arduino D12/MISO, so driving it affects header SPI.

=====================================================
*** SUCCESS *** — R404 bridged, the card ENUMERATES
=====================================================

Date: 2026-08-18. R404 (GPIO_AD_31 -> the PDn chain, DNP from the factory)
fitted by hand with a solder bridge, after R1901.

    sdio_begin=ok rc=0
    int_status=0x1 r4=0x90FF8000
    io_functions=1
    rca=0x1
    cccr_rev=0x3
    manfid=0x2DF
    cardid=0x9158

`manfid=0x2DF` is the Marvell/NXP SDIO manufacturer code; `cardid=0x9158` is the
88W8978/IW416-family device ID. BOTH ARE READ OFF THE WIRE from the card's CIS
tuple chain -- this firmware contains neither value. `r4=0x90FF8000` decodes as
C=1 (ready), 1 IO function, OCR window 0xFF8000, matching the datasheet's
"Number of SDIO functions: 1 (Wi-Fi)".

Corroborating signals, both previously stuck low, both now correct:

    bt_wake(pin20): pullup_reads=1 pulldown_reads=1 -> HELD HIGH externally
    after_pdn_cycle: rx_any_high=1 rx_edges=26

BT_WAKE_HOST released, and the card's UART TX produced 26 edges during the
power-up window -- the Bluetooth boot ROM transmitting.

ROOT CAUSE
----------

**PDn (J54 pin 56, W_DISABLE1#) needed an actual asserted-LOW transition, and
R404 being DNP made that impossible.**

The pin was never "wrong": R829's 10K pull-up held it at the logic-high "normal
mode" level the datasheet asks for, which is why every static check passed. But
the module had come up in a state it could not leave, and with R404 unpopulated
GPIO_AD_31 was disconnected, so no firmware could assert PDn to power-cycle it.
The radio sat in that state indefinitely with every output at zero.

Bridging R404 let m2ReleaseWifiReset() drive PDn low, then high, then wait ~1 s
for the ROM to boot. That is the whole fix.

Why this was so hard to see:

* A held-high-by-pull-up PDn looks identical to a driven-high PDn on every
  measurement available from the host.
* Every card->host signal was DRIVEN low, not floating, which correctly proved
  the card's DC-DC and level shifters were powered -- and misleadingly suggested
  the module behind them was merely faulty.
* NXP's own wifi_cli fails identically on this board, because it drives
  BOARD_INITPINSM2_WL_RST_GPIO = GPIO9_IO30 = GPIO_AD_31, which without R404
  reaches nothing. NXP's software is correct; the RevC3 board's DNP defeats it.

WHAT THIS BOARD NEEDS FOR AN M.2 Wi-Fi CARD
--------------------------------------------

Two 0402 0 Ω resistors, both DNP from the factory:

| Ref   | Connects                          | Without it |
|-------|-----------------------------------|------------|
| R404  | GPIO_AD_31 -> PDn (J54 pin 56)    | **The radio can never be power-cycled and does not boot. Fatal.** |
| R1901 | U355 -> BT_UART_RXD (J54 pin 22)  | Bluetooth HCI is transmit-only; no reply can ever be read |

R404 is the one that matters for Wi-Fi. R1901 is required for Bluetooth and was
also what made the diagnosis possible, by turning the card's UART TX line from
invisible into observable.

Note GPIO_AD_31 is also Arduino D12/MISO, and GPIO_DISP_B2_11 (the BT UART RX)
is Arduino D0 -- both header pins are now committed to the M.2 card.

throughout. They are kept above as the record of how the investigation actually

W2 — CMD53 + FIRMWARE DOWNLOAD — FIRMWARE_READY
=====================================================

Date: 2026-08-18.

    iw416_begin=ok ioport=0x10000 fw_status=0xFEDC card_status=0xD requested_len=0
    fw_download=ok sent=402288/411064 chunks=417 last_req=0 fw_status=0xFEDC

0xFEDC is FIRMWARE_READY. The IW416 firmware is downloaded and running.
card_status=0xD is DN_LD_CARD_RDY | CARD_IO_READY.

`sent` stops short of the image size because the bootloader stopped asking at
402288 bytes and jumped -- the "want == 0 after progress means done" path,
which is how NXP's loop terminates too.

How it was built
----------------

  SdioHost::cmd53Read/Write   CMD53 block mode, PIO through the USDHC data port
  SdioFunc                    CCCR function enable + block size
  Iw416                       card registers + the download handshake

Protocol follows NXP's mcuxsdk wifi_nxp (sdio_nxp_abs/fwdnld_sdio.c,
BSD-3-Clause). Nothing vendored -- independent implementation of the documented
sequence.

THE BUG THAT COST THE MOST: the wrong CARD_STATUS_REG
------------------------------------------------------

NXP's own fwdnld_sdio.c says:

    /* Read CARD_STATUS_REG (0X30) FN =1 */

**0x30 is the SD8801 address.** SD8978/IW416 uses CARD_TO_HOST_EVENT_REG =
**0x5C** (mlan_sdio_defs.h, the SD8978 arm). The comment is stale by a chip
generation, and the code around it resolves the macro correctly -- so only the
comment is wrong, and only a reader following the comment gets burned.

The failure mode is nasty: reading 0x30 returns 0x00 forever, so the
card-readiness gate never fires. Without that gate the host writes whenever the
length register happens to be non-zero, into a card that is not listening.
EVERY CHUNK STILL REPORTS SUCCESS and the entire image transfers. Only the final
validation fails.

That produced two complete, plausible-looking downloads that ended in
fw_status=0x1:

    sdIW416_wlan.bin.inc        sent=279164/279164 chunks=2795  fw_status=0x1
    sduartIW416_wlan_bt.bin.inc sent=411064/411064 chunks=568   fw_status=0x1

Note the chunk counts differ wildly between images, which looked like meaningful
protocol behaviour and was not. Adding the 0x5C gate fixed it immediately:
417 chunks, fw_status=0xFEDC.

Other things worth knowing
--------------------------

* The bootloader asks for **2049** bytes at a time. A 2048-byte staging buffer
  fails on the very first large request; give it headroom.
* The firmware array must go in **.progmem**. The imxrt1176 linker script folds
  `.rodata*` into `.data`, which lives in DTCM (256K) -- a 273 KB const array
  there overflows the region and the link fails with ".bss is not within region
  DTCM". Note `FLASHMEM` is `#define FLASHMEM` (empty) in AudioStream.h and does
  NOT do this job; `__attribute__((section(".progmem")))` does.
* The blob is NOT in this repo. It is NXP LA_OPT-licensed binary, supplied at
  configure time:
      -DM2RADIO_IW416_FW=<sdk>/components/conn_fwloader/fw_bin/inc/IW416/sduartIW416_wlan_bt.bin.inc
  Without it the example builds and reports `fw_download=skipped`, so the QEMU
  gate is unaffected on a machine with no SDK.

W3 — HOST COMMAND INTERFACE — GET_HW_SPEC ANSWERS
=====================================================

Date: 2026-08-18.

    iw416_cfg: fw_pre=0x0 d9=0x0->0x1 c4=0x0->0x4 c5=0x0->0x1 r04=0x0->0xFF d8=0x0->0x10
    fw_download=ok sent=402288/411064 chunks=417 last_req=0 fw_status=0xFEDC
    hw_spec=ok int_seen=0xC2 cmd_rd_len=256 resp_type=1 resp_cmd=0x8003 resp_result=0
    mac=6C:1D:EB:91:0C:45 fw_release=0x9B105C15 hw_version=0x7201

resp_cmd=0x8003 is GET_HW_SPEC (0x0003) with HostCmd_RET_BIT set, result=0.
The MAC is READ OFF THE CARD over the command port -- 6C:1D:EB is a u-blox
OUI, and none of those bytes exist in this firmware.  int_seen=0xC2 is
DN_LD (0x02) | CMD_PORT_UPLD (0x40) | CMD_PORT_DNLD (0x80): the card acked
our command download and flagged its reply on the command port's own bits.

WHAT WAS MISSING: the SD8978 "new mode" init block, whole
---------------------------------------------------------

NXP's wlan_sdio_init_ioport() (wifidriver/sdio.c, SD8978 arm) runs six writes
before the firmware download, and the W3 attempts had none of them:

    HOST_INT_MASK  (0x08)  = 0x00      everything MASKED until fw is running
    CARD_CONFIG_2_1(0xD9) |= 0x01      CMD53 "new mode" -- cmd port exists
    CMD_CONFIG_0   (0xC4) |= 0x04      publish reply length in CMD_RD_LEN_0/1
    CMD_CONFIG_1   (0xC5) |= 0x01      cmd-port ready auto-reset after CMD53
    HOST_INT_RSR   (0x04) |= 0xFF      HOST_INT_STATUS becomes clear-on-READ
    CARD_MISC_CFG  (0xD8) |= 0x10      data-path ready auto-reset

HIM_ENABLE (0xC3) is written only AFTER FIRMWARE_READY -- NXP's
sd_wifi_post_init() -- now Iw416::enableHostInt().  All six registers read 0x00
pre-write on this card and took their bits exactly (the iw416_cfg line above is
those read-backs).

THE FOUR BUGS, EACH PAID FOR
-----------------------------

1. HOST_INT_STATUS was being WRITTEN (~mask, "write-1-to-clear" -- a guess).
   NXP never writes that register anywhere in the tree: with HOST_INT_RSR set
   it clears on READ.  The ~mask write (0xBE) was garbage on every axis.

2. Reply length was read from RD_LEN_P0 (0x18/0x19).  That is the DATA port's
   length register; a command-port reply publishes at CMD_RD_LEN_0/1
   (0xC0/0xC1), and only when CMD_CONFIG_0 bit 2 is set.  cmd-timeout forever.

3. Commands were sent ~50 ms after the last download chunk.  The bootloader
   had jumped but the firmware was still booting: the probe's own
   downloadFirmware() returned OK on the "stopped asking" path WITHOUT waiting
   for FIRMWARE_READY, and a host command into a booting firmware KILLS it --
   fw_status settles at 0xF00B instead of 0xFEDC and no interrupt ever fires
   again (int_seen=0x0).  The READY poll now runs on every exit path, which is
   also what makes fw_download=ok mean what it says.  NXP's
   sdio_post_fwdnld_check_conn_ready() polls up to 5 s before anything else
   may touch the card.

4. The first packet on the command port was taken on faith as the answer.  It
   is not: the port also carries the FUNC_INIT response and EVENT packets, and
   GET_HW_SPEC parsed one of those as "success" with mac=00:00:00:00:00:00.
   waitCmdResp() now discards packets until [pkttype]=1 and [command]=cmd|0x8000.

Bugs 1-2 were the handoff's two suspects, confirmed in that order; bugs 3-4
were found by the new instrumentation (int_seen / cmd_rd_len / fw_pre / resp_*
in the report), not by guessing: each failing flash produced the evidence that
named the next bug.

Note on the hang the handoff warned about: it was never reproduced after the
~mask write and the premature HIM_ENABLE-in-begin() were removed.  The W2
recovery image (same begin() unmask, no getHwSpec) ran clean, so the hang
lived in the getHwSpec path -- most plausibly the CMD53 to a command port
that "new mode" had never enabled, wedging the card mid-transfer.

    mac_ctrl=ok
    scan=ok num=3
    scan_ap0: bssid=78:20:51:8F:19:5E rssi=-74 ch=4 ssid="OnestreamQJN7"

Sequence that worked, first try (per the design doc):

    FUNC_INIT -> GET_HW_SPEC -> MAC_CONTROL(0x0028, action=0x0013
    RX_ON|TX_ON|ETHERNETII) -> 802_11_SCAN(0x0006, bss_mode=ANY,

The single response (1536 bytes = 6 blocks, resp_cmd=0x8006 resp_result=0)

hw_spec line show the LAST command-port packet, which after W4 is the scan
response (0x8006/1536), not GET_HW_SPEC's.  They are live evidence, not a
per-command record.

W5 — DATA-PATH RX (MONITOR MODE) — REAL 802.11 FRAMES
=====================================================

Date: 2026-08-18.  Design: docs/superpowers/specs/2026-08-18-m2-w5-monitor-design.md

    monitor=ok result=0x0 frames=16 ch=4
    mon_dbg: uploads=17 reads=16 status_or=0x1 bitmap_or=0xFFFF rxtype_or=0x5 last_pkttype=0x0
    mon_fr0: fc=0x80 ta=78:20:51:8F:19:5E rssi=-81 len=425 bssid=78:20:51:8F:19:5E ssid="OnestreamQJN7"
    mon_fr1: fc=0x80 ta=7A:20:51:4F:19:5E rssi=-82 len=338 bssid=7A:20:51:4F:19:5E ssid=""
    mon_fr2: fc=0x80 ta=7A:20:51:5F:19:5E rssi=-82 len=338 bssid=7A:20:51:5F:19:5E ssid=""
    mon_fr3: fc=0x94 ta=F8:0D:60:34:50:08 rssi=-73 len=28
    mon_fr4: fc=0x80 ta=78:20:51:8F:19:5E rssi=-82 len=425 bssid=78:20:51:8F:19:5E ssid="OnestreamQJN7"

A BEACON (fc=0x80) from BSSID 78:20:51:8F:19:5E / SSID "OnestreamQJN7" -- the
exact AP W4's scan reported -- captured LIVE off the air in monitor mode, plus
a Block Ack control frame (fc=0x94) from an Apple device (F8:0D:60). The
mgmt|ctrl|data filter (0x07) is working. This is the data-path RX proof: raw
802.11 frames the firmware pulled from the air and DMA'd up the SDIO data port.

How it works (design doc has the full layout):

    NET_MONITOR (0x0102, action SET, activity 1, filter 0x07, ch 4) -- accepted
      resp_cmd=0x8102 result=0.  The firmware DOES carry CONFIG_NET_MONITOR.
    Then the reusable data-port read: poll HOST_INT_STATUS for UP_LD (bit 0,
      the DATA port -- distinct from the command port's bit 6), read RD_BITMAP
      (0x10/0x11), take the lowest set port, length from RD_LEN_P<n>
      (0x18 + 2n), CMD53-read at ioport|n.
    Each buffer: [u16 size][u16 pkttype=0 DATA] then RxPD; the 802.11 frame is
      at INTF_HEADER_LEN + rx_pkt_offset, length rx_pkt_length, rx_pkt_type =
      PKT_TYPE_802DOT11 (5). RSSI dBm = snr - nf (RxPD).

THE frames=0 THAT WAS NOT A BUG
--------------------------------

The FIRST W5 flash reported frames=0 with monitor=ok result=0. It was tempting
to treat that as a driver bug and start changing the RX path.  Instead the
capture was instrumented (mon_dbg: uploads / reads / bitmap_or / rxtype_or /
last_pkttype) and reflashed.  The counters are PURELY observational -- they
cannot make frames appear -- and the next window captured 16.  So the zero was
never code: it was a transient.  The AP is marginal this session (-81..-85 dBm,
vs -74 when W4 ran), and a 3 s window caught a fade.  The RX code was correct
throughout.

The lasting value: mon_dbg makes a zero self-diagnosing.  uploads=0 -> quiet
air (no firmware upload).  uploads>0 reads=0 -> interrupt/bitmap mismatch.
reads>0 rxtype_or without bit 0x5 -> frames arrive but not as 802DOT11.  A bare
frames=0 is ambiguous; the counters are not.  They are kept in the driver for
that reason -- the same instrument-first discipline W3 and W4 used.

Association (auth + assoc + WPA2) is deferred to W6, where an OPEN test AP can
be stood up deliberately; monitor mode needed nothing external and proved the
data path first.

W6 STEP 1 — SCAN SECURITY SURVEY — NO OPEN AP IN RANGE
=====================================================

Date: 2026-08-18.  Design: docs/superpowers/specs/2026-08-18-m2-w6-associate-design.md

    scan=ok num=3
    scan_ap0: bssid=78:20:51:8F:19:5E rssi=-81 ch=4 sec=wpa2 ssid="OnestreamQJN7"
    scan_ap1: bssid=7A:20:51:4F:19:5E rssi=-80 ch=4 sec=wpa2 ssid=""
    scan_ap2: bssid=7A:20:51:5F:19:5E rssi=-80 ch=4 sec=wpa2 ssid=""

The scan now classifies each BSS OPEN / WEP / WPA / WPA2 from the beacon
capability Privacy bit (0x0010) and the RSN (IE 48) / WPA (vendor 00:50:F2:01)
IEs.  The classification is un-fakeable: sec=wpa2 comes from finding the RSN IE
in each live beacon, which the firmware does not announce.

VERDICT: all three APs in range are WPA2.  There is NO open AP to associate to.

Why this matters for W6: association without a key exchange only works against
an OPEN network.  Joining "OnestreamQJN7" would require the WPA2 4-way EAPOL
handshake (PMK/PTK) -- a large, separate phase -- plus its password.  So W6
steps 2-4 (ASSOCIATE 0x0012, TX over WR_BITMAP, DHCP/ARP round-trip) are
BLOCKED on external input: either the user stands up an OPEN AP (a phone
hotspot with no password) in range, or authorises the WPA2 path with a
credential.

This is why only step 1 was implemented.  This project ships only what silicon
verifies (the two-gate rule); association cannot be verified with no AP to
join, and writing untested ASSOCIATE/TX firmware would violate that discipline.
Step 1 is the AP-independent part -- verifiable now, and it produced the datum
that decides whether the rest can proceed (it cannot, autonomously).

=====================================================
W6 — WPA2 ASSOCIATION — ASSOCIATES; HANDSHAKE NEEDS THE RIGHT PSK
=====================================================

Date: 2026-08-18.  Design: docs/superpowers/specs/2026-08-18-m2-w6-associate-design.md
Target: OnestreamQJN7 (WPA2), supplied by the user with -DM2RADIO_WIFI_SSID/PSK.

WHAT WORKS (hardware-verified)

    supplicant_pmk=ok result=0x0
    associate=ok cap_info=0x1411 assoc_status=0
    wpa_rsn_ie=30140100000FAC040100000FAC040100000FAC020000

* SUPPLICANT_PMK (0x00C4): the firmware's embedded supplicant accepts the
  SSID + passphrase (result 0).  The host does no WPA2 crypto.
* ASSOCIATE (0x0012): 802.11 association SUCCEEDS -- assoc_status=0, and
  cap_info=0x1411 is a real IEEE capability (ESS|Privacy|ShortSlot), not an
  error code.  The full associate command (SSID/PHY/CF/Rates/RSN TLVs built
  from the scanned BSS) is correct.
* deauthenticate(), the command/event/data-port machinery, and the retry
  loop all work.

WHAT DOES NOT (and why it is NOT a code fault)

    connect=cmd-crc last_event=0x8 event_info=0x2078000F

* last_event=0x8 = EVENT_DEAUTHENTICATED; the low 16 bits of event_info =
  0x000F = IEEE reason code 15 = "4-Way Handshake timeout".  The AP starts
  the WPA2 handshake after association, our supplicant's reply does not carry
  a valid MIC, and the AP deauthenticates.
* The captured RSN IE decodes as plain WPA2-PSK / CCMP / NO PMF / NO SHA256:
    30 14 | 0100 | 000FAC04 (group CCMP) | 0100 000FAC04 (pairwise CCMP)
          | 0100 000FAC02 (AKM = PSK) | 0000 (RSN caps: PMF clear)
  So there is no PMF or SHA256-AKM requirement this minimal ASSOCIATE fails to
  handle -- the association parameters are exactly right for this AP.

CONCLUSION: reason 15 after a clean association, against a standard
WPA2-PSK-CCMP AP with the correct RSN IE echoed and the SSID matched exactly,
is the textbook signature of a PMK mismatch -- the passphrase does not match
the AP's key.  The association CODE is complete and correct (proven by
assoc_status=0); the 4-way handshake needs the correct PSK, which is the
user's to supply/verify.  Once it matches, EVENT_PORT_RELEASE (0x2b) should
replace the reason-15 deauth and connect=ok.

METHOD NOTE -- the AP-throttle detour (paid for, do not repeat)

An early run associated cleanly (assoc_status=0); the next several returned
cap_info=0xFFFA/0xFFFC (firmware internal error / "timeout waiting for AP").
That was NOT a code regression -- the associate bytes were identical.  ~11
rapid associate/vanish cycles from repeated reflashing tripped the AP's
deauth-flood protection, so it stopped answering our MAC.  Letting the AP rest
during a reprogram restored clean association.  Lesson: when association starts
timing out mid-session after many reflashes, rest the AP before suspecting the
firmware.  cap_info disambiguates: 0xFFFx = internal/timeout (link/AP state);
a normal small value = a real AP response whose status_code is the IEEE code.

WHAT IT SETTLES
---------------

**1. The RX path is good, and the 26 edges were a real protocol burst.**

    after_pdn_cycle: rom_bytes=16 hex=00AB01720047AB01720047AB01720047

Sixteen bytes: a leading 0x00 (the pad-settle artefact this file has recorded
before), then the five-byte pattern `AB 01 72 00 47` repeated THREE times.
That is the "26 edges" of 2026-08-18, resolved.

★ **Those bytes contain a value we read independently over a DIFFERENT
INTERFACE.**  The same boot prints, from the SDIO side:

    hw_spec=ok ... hw_version=0x7201

and `0x7201` little-endian is `01 72` — bytes 2 and 3 of the pattern.  Two
interfaces that share no code agreeing on that number is the strongest evidence
available here that the UART is correctly framed at 115200 and that these are
MEANINGFUL PROTOCOL BYTES rather than noise or a baud mismatch.  Stated as a
strong correlation, not a decode: the meaning of `AB`, of the `00`, and of the
trailing `47` (plausibly a checksum) is NOT established by this run.

**2. No HCI command is ever answered — before or after the SDIO download.**

    hci_pre_download:  quiet=5  reply=none n=0 match=0
    hci_post_download: quiet=10 reply=none n=0 match=0
    hci_probe:         quiet=0  reply=none n=0 match=0     (every 5 s, forever)

The brackets are what make this readable.  `quiet=` counts bytes arriving in an
equal-length window BEFORE the command, so a chattering ROM cannot be misread as
a reply: 5 and 10 bytes were still trickling in during setup, and ZERO
thereafter.  The card transmits its burst at power-up, gets no answer, and goes
silent for good.  `reply=none n=0` is then an honest negative and not an absence
of listening.

**3. BT_WAKE_HOST never moves.**

    bt_wake(pin20): pullup_reads=1 pulldown_reads=1 ever_low=0 -> HELD HIGH externally
    bt_wake_sample: high=1 edges=0

An NXP BT controller asserts this line when it has something for the host.  It
never does.  Consistent with a core that is not running BT firmware at all.
(Contrast 2026-08-17, when it was stuck LOW because the module was in
power-down — a different failure with the opposite signature.)

**4. Everything else on the card is healthy**, which is what makes the negative
meaningful rather than a symptom of a dead module:

    sdio_begin=ok  manfid=0x2DF cardid=0x9158
    iw416_begin=ok fw_status=0xFEDC
    fw_download=ok sent=402288/411064 chunks=417 last_req=0
    hw_spec=ok mac=6C:1D:EB:91:0C:45 fw_release=0x9B105C15 hw_version=0x7201

THE HYPOTHESIS THIS PRODUCES — and the evidence for it
------------------------------------------------------

**The BT core is sitting in its own UART bootloader, asking for a firmware
download that the SDIO path never gives it.**

Two independent things point that way:

* The card announces itself on the BT UART at power-up, three times, then stops
  — the shape of a request that timed out, not of a controller that is running.
* ★ **The combo download does not consume the whole blob**:
  `sent=402288/411064 ... last_req=0`.  The card stopped asking after 402,288
  bytes, leaving **8,776 bytes** of the image undelivered.  The blob's own name
  is `sd`io-wlan + `uart`-bt, and W17's A/B against the Wi-Fi-only
  `sdIW416_wlan.bin` found the two differ by an APPENDED BT image.  A download
  that takes the WLAN part and stops is exactly what that layout predicts.

★ **This CONTRADICTS NXP's own reference**, and the contradiction is the useful
part.  `controller_wifi_nxp.c`'s `controller_init()` does the combo SDIO
download and then goes straight to `controller_hci_uart_init()` — i.e. it
assumes BT is up after the SDIO download.  It also carries an alternative path,
`CONFIG_BT_IND_DNLD`, which downloads a BT-ONLY image over the UART first.  This
board's behaviour says the second path is the one this module needs.  Whether
that is a property of the u-blox MAYA-W161 variant or of some sequencing
detail is NOT settled by this run.

WHAT WOULD SETTLE IT — the next cheap question
----------------------------------------------

Feed the BT UART a firmware image and see whether the burst stops and HCI
starts answering.  Do it as a probe, bracketed, before designing anything:
the burst repeating exactly three times is itself a measurable signal, so
"did the card stop asking?" is answerable without a full download working.

WHAT THIS RUN DOES **NOT** SAY
------------------------------

* NOT that Bluetooth is broken on this card.  Nothing here has fed the BT core
  the firmware it is asking for.
* NOT that 115200 is wrong.  The 0x7201 correlation is evidence it is right.
* NOT that `AB 01 72 00 47` is decoded.  It is recorded, not understood.

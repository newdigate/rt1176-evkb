m2_throughput_test -- hardware verification on the real MIMXRT1170-EVKB RevC3
==============================================================================
Date: 2026-08-19.  Card: u-blox M2-MAYA-W161 (IW416/SD8978), antenna fixed in
W8, IEEE PS ON (the W10 workaround; delay_to_ps=1000 keeps the card awake
under load).  Driver: M2Radio @ 60280af (W11 bus counters), lwip @ the W11
lwipopts bump (TCP_WND/TCP_SND_BUF = 8*MSS).

Rig: the user's HOUSE AP, not the bench ESP -- first association against a
real WMM AP.  EVKB joins "OnestreamQJN7" (2.4 GHz side), DHCP 192.168.1.102;
peer is the Mac at 192.168.1.101 on the same router's 5 GHz side
("OnestreamQJN7_5G", 802.11ac ch36, WPA2 Personal).  The Mac runs
tput_peer.py and its own byte counts + wall clock are the authoritative
numbers (the board cannot fake them); board serial lines are cross-checks.
House PSK handled per the standing rule: session scratchpad -> CMake cache
-> generated gitignored header only.

W11 BASELINE (before any bottleneck fix):

    Mac (authoritative)                          board cross-check
    TPUT tcp-rx mbps=9.69                        tcp_rx bytes=12124160 ms=10114 kbps=9590
    TPUT tcp-tx mbps=4.91                        tcp_tx bytes=6141952  ms=10012 kbps=4907

ATTRIBUTION (from the new bus counters, full 4-test window):

    c53:   +33,472 data CMD53s moving 43.9 MB block-padded = 1,311 B avg
           -> exactly ONE frame per CMD53, no aggregation.
    c52tx: +85,680 -> ~5.6 CMD52s per TX frame (wr_bitmap re-reads).
    c52svc: ~1,000/s at IDLE -- but that is NOT a command-cost measurement:
           serviceLink's quiet path runs delay(1) per pass (Iw416.cpp), so
           the idle 1 kHz is the DELAY pacing the loop, not the bus.
           Measured under load instead (tcp-rx window, 5.98 s, all three
           counters): 63,029 commands = ~10,500/s -> ~0.1 ms per SDIO
           command software-inclusive.
    Sustained active rate: 33,472 frames / ~40 s of tests = ~840 frames/s
           ~= 1.2 ms per frame, consistent with ~10 bus commands per frame
           at ~0.1 ms each -> at ~1.4 KB/frame that IS the measured
           5-10 Mbps.  The bus transactions per frame, not the air link,
           are the ceiling.

  The one-fix conclusion (W11 Task 5): amortize the bitmap CMD52s over the
  ring.  W8's reference trace already proved the fw contract allows it --
  NXP's host writes successive TX ports from ONE wr_bitmap read while the
  fw batch-frees at ring top, and RX uploads land on successive ports
  drainable from ONE rd_bitmap read.  Our driver re-reads per frame.

------------------------------------------------------------------------------
W11 Task 5: the one fix REGRESSED and was reverted; the attempt exposed a NEW
fault.  Same day, same rig.
------------------------------------------------------------------------------

1) THE FIX ATTEMPT (M2Radio 3a34d2d, reviewed+approved, reverted same day):
   cached wr/rd bitmap views to amortize the 4-CMD52 bitmap reads across the
   ring (the contract NXP's host demonstrably uses).  Result on silicon:
   EVERY cell fell -- tcp-rx 9.69->6.93, tcp-tx 4.91->1.44, udp-tx
   6.72->2.27 Mbps.  The counters say why, comparing the SAME phase
   (udp-tx): 8.6 CMD52s/frame before (52,140/6,032) vs 21.9 after
   (+46,144 polls for 2,104 frames) -- a 2.5x regression.  The cached
   view lets the host burn all ring credits in a fast burst, then sit in the
   dry-wait poll loop (delay(1) per iteration, ~5 ms/frame) while the fw
   frees ports at its own batchy cadence.  The pre-fix read-per-frame
   pattern was ACCIDENTALLY LOAD-BEARING: it paced the host to exactly the
   fw's sustainable rate, so the first read nearly always hit.  Lesson: on
   this fw, amortizing bitmap reads needs interrupt-driven free notification
   (DAT1) or mlan-style deep TX queueing -- not a passive cache.
   Reverted (M2Radio revert commit); revert-run counters confirmed the
   pre-fix idle signature returned.

2) FAULT #5 -- ⚠ THIS SECTION'S ORIGINAL CONCLUSION WAS WRONG.  It read
   "IEEE PS + busy RX kills the fw's RX path"; W12 disproved that the next
   morning with a controlled matrix (see the W12 section at the end of this
   file).  PS is EXONERATED: the freeze rate is the same with PS off.  The
   real pattern is REPEATED CONNECTIONS within one firmware life -- a boot's
   FIRST blast has never once frozen (0/13), later blasts freeze ~35%.
   The original text is kept below unedited, because HOW it went wrong is
   the lesson: the A/B/A that produced it gave the PS-off arm a fresh boot
   and the PS-on arms repeat runs, so it compared PS against boot-freshness
   and read the result as PS.  A confound, not a measurement.

   --- original W11 text, superseded ---
   FAULT #5, discovered by the revert's control run: IEEE PS + BUSY RX
   kills the fw's RX path.  Repeatable A/B/A, all on the reverted
   (known-good W10) driver, fresh fw download each boot:

     PS ON : control #1 -- tcp-rx froze mid-run at 5.5 MB (stall valve
             fired; then 100% ping loss; even idle broadcast RX dead).
     PS ON : control #2 -- froze at ~1.0 MB, same signature.
     PS OFF: tcp-rx x3  -- ALL CLEAN (7.60 / 8.10 / 4.83 Mbps).
     PS ON : tcp-rx x3  -- one completed (2.72 Mbps, degraded), then a
             freeze; the third attempt hit an already-dead RX path, so it
             is DOA rather than an independent trial.

   Signature matches the W10 erratum (RX dead incl. broadcasts, assoc
   held, no self-recovery, card reset revives) but the REGIME IS THE
   OPPOSITE: sustained ~7-10 Mbps RX with PS enabled.  Honest score:
   PS-off 3/3 clean; PS-on froze in 3 independent boots and completed
   1 of 4 fresh trials (+1 DOA).  The W11 baseline's clean PS-on matrix
   was the lucky draw.
   MECHANISM HYPOTHESIS (unverified, W12's first job): our W10 PS code
   sends the sleep-confirm UNCONDITIONALLY on EVENT_PS_SLEEP -- mlan
   defers the confirm while RX/TX is pending.  Confirming sleep while the
   fw has uploads queued plausibly wedges its RX path.  If true, the fix
   is a conditional confirm (defer while the data path is active), and
   PS-on would then be safe in BOTH regimes.

3) STANDING TENSION until W12 resolves it: PS ON is required for idle
   links (W10 erratum: sparse+PS-off dies in 1-44 min) but kills busy-RX
   links (this fault); PS OFF is the reverse.  A deployment must pick per
   workload.  The committed example keeps PS ON (connectStation default),
   which is safe for its idle-between-tests life; expect tcp-rx freezes
   if you blast it repeatedly -- reflash revives.

4) Numbers caveat, now measured: 2.4 GHz air variance on identical
   configs spans ~4.8-9.7 Mbps run to run.  The W11 table is a capability
   floor, not a precision benchmark; the REGRESSION verdict in (1) rests
   on the counter mechanism, not the Mbps deltas alone.

------------------------------------------------------------------------------
W12: fault #5 RE-CHARACTERIZED.  Power save is NOT involved.  The trigger is
REPEATED CONNECTIONS within one firmware life.
------------------------------------------------------------------------------
Date: 2026-08-19 (next morning).  Same rig, same house AP, same ELF except
the PS build flag.  Method: a scripted matrix (scratchpad fault5_multi.sh)
that reflashes per boot -- so every boot starts from a fresh fw download --
then runs N consecutive 10 s tcp-rx blasts, recording the ORDINAL of the
blast that dies.  Reflashing per boot is what W11 failed to hold constant.

  ARM A (PS ON, connectStation default), 4 boots x up to 4 blasts:
    boot1: 11.12 PASS | FREEZE(2nd)
    boot2: 7.23 / 10.27 / 13.68 / 13.31 -- all PASS
    boot3: 13.55 / 13.42 PASS | FREEZE(3rd)
    boot4: 13.62 / 13.52 / 13.74 PASS | FREEZE(4th)
      -> 3 freezes / 13 blasts

  ARM B (PS OFF, -DM2_PS_OFF=1, verified on the wire by the boot line
  "ps_mode=OFF(A/B arm)"), same shape:
    boot1: 13.09 PASS | FREEZE(2nd)
    boot2: 13.70 PASS | FREEZE(2nd)
    boot3: 13.23 / 12.28 / 9.80 PASS | FREEZE(4th)
    boot4: 2.95 / 7.76 / 14.00 / 11.10 -- all PASS
      -> 3 freezes / 12 blasts

  PLUS an earlier single-blast-per-boot arm (PS on, 5 boots): 5/5 PASS.

  POOLED, by position within the firmware life:
    FIRST blast of a boot :  0 freezes / 13   (0%)
    LATER blasts          :  6 freezes / 17   (~35%)

  CONCLUSIONS:
  * PS on vs PS off: 23% vs 25% freeze rate -- INDISTINGUISHABLE.  The W11
    claim is withdrawn; the PS-conditional-sleep-confirm fix it implied was
    never implemented, which is the one piece of luck in this story.
  * The surviving signal is POSITION IN THE FIRMWARE LIFE, not PS and not
    load: a fresh fw download always survives its first blast; something
    accumulates across TCP connections / repeated blasts and eventually
    wedges host-visible RX.
  * Freeze signature (unchanged from W11): c53 data-CMD53 counter PINNED
    (the host stops reading uploads at all -- so this is NOT lwip pbuf
    exhaustion, which would show frames still being read and dropped),
    rx flat, association held, stall valve fires, only a reflash revives.
  * Throughput note: this matrix peaked at 13.7 Mbps vs W11's 9.69 -- the
    W11 table's ceiling was partly air conditions, and the "5-10 Mbps"
    figure should be read as ~3-14 Mbps depending on the 2.4 GHz band's
    mood.  The per-frame bus-cost attribution is unaffected.

  METHOD LESSON (the reason W11 got it wrong): when a fault is stochastic,
  an A/B whose arms differ in ANY other respect -- here, one arm got fresh
  boots and the other did not -- measures the difference you did not intend.
  Reflash per trial, randomize nothing you can hold fixed, and report the
  trial ordinal, not just the pass/fail count.

  NEXT (W12 continues): the ring is the prime suspect -- our m_rxPort vs the
  fw's upload port drifting out of sync would produce exactly a pinned-c53,
  fw-still-associated freeze.  Instrument ring=T/R/resyncs + rd_bitmap into
  the freeze dump and reproduce, before changing any code.

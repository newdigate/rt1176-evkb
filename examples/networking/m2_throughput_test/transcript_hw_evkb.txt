    c52tx: +85,680 -> ~5.6 CMD52s per TX frame (wr_bitmap re-reads).

W11 Task 5: the one fix REGRESSED and was reverted; the attempt exposed a NEW
fault.  Same day, same rig.
------------------------------------------------------------------------------

1) THE FIX ATTEMPT (M2Radio 3a34d2d, reviewed+approved, reverted same day):
   cached wr/rd bitmap views to amortize the 4-CMD52 bitmap reads across the
   ring (the contract NXP's host demonstrably uses).  Result on silicon:
   EVERY cell fell -- tcp-rx 9.69->6.93, tcp-tx 4.91->1.44, udp-tx
   6.72->2.27 Mbps.  The counters say why, comparing the SAME phase
   (udp-tx): 8.6 CMD52s/frame before (52,140/6,032) vs 21.9 after
   (+46,144 polls for 2,104 frames) -- a 2.5x regression.  The cached
   view lets the host burn all ring credits in a fast burst, then sit in the
   dry-wait poll loop (delay(1) per iteration, ~5 ms/frame) while the fw
   frees ports at its own batchy cadence.  The pre-fix read-per-frame
   pattern was ACCIDENTALLY LOAD-BEARING: it paced the host to exactly the
   fw's sustainable rate, so the first read nearly always hit.  Lesson: on
   this fw, amortizing bitmap reads needs interrupt-driven free notification
   (DAT1) or mlan-style deep TX queueing -- not a passive cache.
   Reverted (M2Radio revert commit); revert-run counters confirmed the
   pre-fix idle signature returned.

2) FAULT #5 -- ⚠ THIS SECTION'S ORIGINAL CONCLUSION WAS WRONG.  It read
   "IEEE PS + busy RX kills the fw's RX path"; W12 disproved that the next
   morning with a controlled matrix (see the W12 section at the end of this
   file).  PS is EXONERATED: the freeze rate is the same with PS off.  The
   real pattern is REPEATED CONNECTIONS within one firmware life -- a boot's
   FIRST blast has never once frozen (0/13), later blasts freeze ~35%.
   The original text is kept below unedited, because HOW it went wrong is
   the lesson: the A/B/A that produced it gave the PS-off arm a fresh boot
   and the PS-on arms repeat runs, so it compared PS against boot-freshness
   and read the result as PS.  A confound, not a measurement.

   --- original W11 text, superseded ---
   FAULT #5, discovered by the revert's control run: IEEE PS + BUSY RX
   kills the fw's RX path.  Repeatable A/B/A, all on the reverted
   (known-good W10) driver, fresh fw download each boot:

     PS ON : control #1 -- tcp-rx froze mid-run at 5.5 MB (stall valve

3) [WITHDRAWN by W12 -- there is NO PS-vs-load tension.  PS off does not

W12: fault #5 RE-CHARACTERIZED.  Power save is NOT involved.  The trigger is
REPEATED CONNECTIONS within one firmware life.
------------------------------------------------------------------------------
Date: 2026-08-19 (next morning).  Same rig, same house AP, same ELF except
the PS build flag.  Method: a scripted matrix (scratchpad fault5_multi.sh)
that reflashes per boot -- so every boot starts from a fresh fw download --
then runs N consecutive 10 s tcp-rx blasts, recording the ORDINAL of the
blast that dies.  Reflashing per boot is what W11 failed to hold constant.

  ARM A (PS ON, connectStation default), 4 boots x up to 4 blasts:
    boot1: 11.12 PASS | FREEZE(2nd)
    boot2: 7.23 / 10.27 / 13.68 / 13.31 -- all PASS
    boot3: 13.55 / 13.42 PASS | FREEZE(3rd)
    boot4: 13.62 / 13.52 / 13.74 PASS | FREEZE(4th)
      -> 3 freezes / 13 blasts

  ARM B (PS OFF, -DM2_PS_OFF=1, verified on the wire by the boot line
  "ps_mode=OFF(A/B arm)"), same shape:
    boot1: 13.09 PASS | FREEZE(2nd)
    boot2: 13.70 PASS | FREEZE(2nd)
    boot3: 13.23 / 12.28 / 9.80 PASS | FREEZE(4th)
    boot4: 2.95 / 7.76 / 14.00 / 11.10 -- all PASS
      -> 3 freezes / 12 blasts

  PLUS an earlier single-blast-per-boot arm (PS on, 5 boots): 5/5 PASS.

  POOLED, by position within the firmware life:
    FIRST blast of a boot :  0 freezes / 13   (0%)
    LATER blasts          :  6 freezes / 17   (~35%)

  CONCLUSIONS:
  * PS on vs PS off: 23% vs 25% freeze rate -- INDISTINGUISHABLE.  The W11
    claim is withdrawn; the PS-conditional-sleep-confirm fix it implied was
    never implemented, which is the one piece of luck in this story.
  * The surviving signal is POSITION IN THE FIRMWARE LIFE, not PS and not
    load: a fresh fw download always survives its first blast; something
    accumulates across TCP connections / repeated blasts and eventually
    wedges host-visible RX.
  * Freeze signature (unchanged from W11): c53 data-CMD53 counter PINNED
    (the host stops reading uploads at all -- so this is NOT lwip pbuf
    exhaustion, which would show frames still being read and dropped),
    rx flat, association held, stall valve fires, only a reflash revives.
  * Throughput note: this matrix peaked at 13.7 Mbps vs W11's 9.69 -- the
    W11 table's ceiling was partly air conditions, and the "5-10 Mbps"
    figure should be read as ~3-14 Mbps depending on the 2.4 GHz band's
    mood.  The per-frame bus-cost attribution is unaffected.

  METHOD LESSON (the reason W11 got it wrong): when a fault is stochastic,
  an A/B whose arms differ in ANY other respect -- here, one arm got fresh
  boots and the other did not -- measures the difference you did not intend.
  Reflash per trial, randomize nothing you can hold fixed, and report the
  trial ordinal, not just the pass/fail count.

  NEXT (W12 continues): the ring is the prime suspect -- our m_rxPort vs the
  fw's upload port drifting out of sync would produce exactly a pinned-c53,
  fw-still-associated freeze.  Instrument ring=T/R/resyncs + rd_bitmap into
  the freeze dump and reproduce, before changing any code.

W12: FAULT #5 ROOT-CAUSED.  Not PS, not the AP, not the card: a HOST-SIDE
lost-interrupt bug.  Uploads are stranded when a clear-on-read status bit is
consumed by a path that does not drain them.
------------------------------------------------------------------------------

THE CAPTURE (instrumented freeze dump, fired by the 30 s stall valve):

    tput: FREEZE (tcp_rx stall) rd_bitmap=0x20000 wr_bitmap=0xFFFFF800
          ring=12/17/339 c53=26493 rx_data=17616 rx_drop=0 ps=0/26/16

Read it carefully, because it eliminates every earlier theory at once:
  * rd_bitmap=0x20000 -> the FIRMWARE has an upload waiting on port 17.
    The card is alive and offering data.  Not a card-side death.
  * ring=12/17/... -> the host's own next RX port is ALSO 17.  Host and fw
    AGREE.  So this is NOT ring desync (the W8 fault) -- the host is
    parked on exactly the right port and simply never looks.
  * c53 pinned (26493, unchanged for the rest of the run) -> the host
    issued NO data CMD53 at all.  Combined with rx_drop=0 this also rules
    out lwip pbuf exhaustion, which would show frames read and dropped.

MECHANISM: HOST_INT_STATUS (fn1 0x0C) is configured CLEAR-ON-READ.
serviceLink() drains the data ring only when it sees HOST_INT_UP_LD in ITS
OWN read (Iw416.cpp ~1195).  But four other paths read the same register and
throw the data bit away -- above all readHostResp() (~238), which polls it
every 1 ms while waiting for a command reply, keeping only CMD_PORT_UPLD.
If an upload's interrupt lands in one of those reads it is consumed and
lost; the fw does not re-raise an interrupt for an upload that is already
pending; the frame is stranded in the ring forever and host-visible RX is
dead until the card is re-downloaded.  rxRingResyncs=339 in the dump is the
ring model repeatedly patching over the same lossage.

WHY IT LOOKED LIKE EVERYTHING ELSE (three wrong theories, in order):
  1. "IEEE PS + busy RX" (W11) -- PS commands are host commands, and every
     host command opens a readHostResp() window, so PS-on genuinely does
     create extra chances to lose the bit.  But so does any other command,
     which is why the PS-off arm froze at the same rate.
  2. "Repeated connections" (W12 morning) -- more blasts = more command
     traffic = more windows.  A real correlation, not a cause.
  3. "Poor RF" (W12 midday) -- retries change timing and lengthen the
     windows.  Again a modulator, not the cause.
  All three are the same underlying race seen through different lenses.
  The freeze rate rose and fell with anything that changed how often a
  data upload could coincide with a command's status poll.

THE FIX (M2Radio, W12): two layers.
  1. Never discard interrupt bits.  A sticky m_intPending accumulates the
     bits from EVERY HOST_INT_STATUS reader; serviceLink() consumes them
     and clears a bit only once it has actually serviced that condition.
     (This is what NXP's mlan does: interrupt status is accumulated and
     processed in the main loop, never dropped at the observation site.)
  2. Self-healing net: on quiet passes, periodically compare the ring's
     current port against rd_bitmap directly and drain if the fw is
     holding something, counting rxStrandedRecovered().  Non-zero means an
     interrupt was lost and the net caught it; a healthy build reads 0.
     This class of bug has now bitten twice (W8 ring, W12 stranded
     uploads), so the data path no longer trusts a single edge indication.

METHOD NOTE: this was found by INSTRUMENTING THE FAILURE, not by reasoning
about it.  Three plausible mechanisms had already been argued convincingly
and all three were wrong; a single dump of rd_bitmap + ring position at the
moment of the freeze settled it in one shot.  The dump reads only the
bitmap registers and deliberately never touches HOST_INT_STATUS -- reading
that register to diagnose the fault would have consumed the very bits under
investigation and caused the stall it was meant to explain.

W12 FIX VERIFIED ON SILICON -- and two of my own analyses of the RESIDUALS
were wrong.  Recorded in full because the errors are the instructive part.
------------------------------------------------------------------------------

THE FIX WORKS.  Three independent 20-25 min soaks, each on ONE firmware
life, against a fault that previously killed RX within 1-3 blasts:

    driver / net width        blasts  freezes  MB moved   stranded  drainerr
    2f8c814 (narrow net)        110      0      1524        4          n/a
    84c2520 (widened net)       110      0      1137        7           0
    84c2520 + my narrowing       87      0      1481        3           0

  c53 (data CMD53s) climbed monotonically in all three -- the un-fakeable
  signal, since the freeze signature was that exact counter frozen.

RESIDUAL 1: stranded != 0 with drainerr == 0.  My hypothesis was that the
  leftover strands were the drain's BY-DESIGN error-exit clears, recovered
  by the net.  REFUTED: drainerr stayed 0 while stranded reached 7.  So a
  genuine layer-1 loss path remains -- an upload interrupt is still being
  lost somewhere the sticky-bit accumulator does not cover.  UNIDENTIFIED
  and OPEN.  Impact is bounded: the net recovers it within ~64 ms, which is
  why the link stays healthy, but "healthy" here means a backstop is doing
  work that layer 1 should have made unnecessary.
  (Candidate to chase next: the command-port analogue the review flagged as
  M5 -- readHostResp branches on its OWN read rather than the accumulator,
  so a CMD_PORT_UPLD shelved by readDataPacket is recorded but never
  consumed.  Not live on today's call graph, but the same shape.)

RESIDUAL 2 -- MY ERROR, twice over.  I read resyncs=6150 (widened net) next
  to the pre-fix freeze dump's resyncs=339 and concluded the widened net was
  thrashing the ring over stale bitmap bits.  I narrowed it back and wrote a
  code comment asserting "SILICON REFUTED IT".  Then the narrowed build
  measured resyncs=12390 -- HIGHER.  The comparison was invalid: 339 came
  from a run of ~1.5 blasts, 6150 from 110.  Per blast:

      pre-fix ~226   widened 56   narrowed 142

  Resync rate is a PRE-EXISTING property of the ring model (tens to
  hundreds per blast), it is not a regression, and the widened net is if
  anything the better of the two.  My narrowing was reverted; the driver
  stands at the reviewed 84c2520.
  TWO LESSONS, both already in this file's history and both re-learned:
   * Never compare absolute counters across runs of different length.  This
     is the same class of error as W11's confounded PS A/B -- I built a
     conclusion on a comparison whose arms were not comparable.
   * A conclusion asserted in a CODE COMMENT is worse than one in a log: it
     outlives the run that produced it and reads as established fact.  That
     comment was committed for minutes before the next measurement killed
     it.

STATUS: the fix lands (fault #5 goes from "RX dead, needs reflash, within
1-3 blasts" to "300+ blasts across three soaks, zero freezes").  Both
residuals stay OPEN and documented rather than explained away:
  1. an unidentified layer-1 loss path (stranded>0, drainerr=0);
  2. the desync variant of the fault, which the net covers only when the

W13: both residuals closed.  The leftover `stranded` is NOT a host bug -- every
host-side mechanism for losing the interrupt has now been refuted by a counter.
------------------------------------------------------------------------------
Date: 2026-08-19 (late).  Driver M2Radio 7aec26b, run through the new
tools/wifi-soak.sh (this was its first real use).

RESULT: 80 blasts, ONE firmware life, 0 freezes, 1.78 GB moved.

    stranded=3/0   drainerr=0   notready=0   resyncs=14703

RESIDUAL #1 -- three hypotheses, all killed by measurement, in order:
  1. "the strands are the drain's by-design error-exit clears"
     -> REFUTED W12: drainerr stayed 0 while stranded climbed.
  2. "readHostResp branches on its own read, so a shelved CMD_PORT_UPLD is
     never consumed" (review item M5)
     -> REFUTED BY INSPECTION, by the implementer, against my instruction:
        readHostResp accumulates HOST_INT_UP_LD but never branches on it and
        never clears it, so that shape can strand a COMMAND-port bit only,
        never a data upload.  The fix landed anyway (it is correct, and the
        command port has no bitmap to recover from) -- but it is not this.
  3. "readRingPacket returns CMD_TIMEOUT for both 'bitmap empty' and 'bit set
     but RD_LEN reads 0', so the drain treats a false-empty as complete and
     clears the upload bit -- stranding with NO bus error"
     -> REFUTED THIS RUN: notready=0 with stranded=3.  The drain never once
        exited on a false empty.  (Instrumented before implementing, exactly
        because hypothesis 1 had already died that way.)

  With all five HOST_INT_STATUS readers verified to accumulate into
  m_intPending, and all three host-side loss mechanisms refuted, the
  remaining explanation is that THE FIRMWARE DOES NOT ALWAYS RAISE
  HOST_INT_UP_LD for an upload it has queued.  We are not losing the
  interrupt; there was no interrupt.  If that is right the safety net is not
  papering over a host bug -- it is the correct and only fix, and
  `stranded` is a measure of firmware behaviour, not of our defects.
  Rate: 3 per 80 blasts (~1.4 GB).  Recovery latency <= 64 ms.  NOT further
  chased: three refutations is enough to stop guessing, and the next
  evidence would need a bus analyser, not another counter.

RESIDUAL #2 -- desync variant, CLOSED with a positive check.
  The net now probes the candidate slot's OWN length register before acting
  (RD_LEN is per-slot: 0x18 + (port<<1), verified against NXP's
  SDIO_RD_LEN_P0_L + (port<<1)); a stale bitmap bit with zero length is
  ignored -- no drain, no resync, no counter, ring pointer unmoved.  This is
  what the W12 `bm != 0` widening should have been.  desync recoveries: 0
  this run (the variant is real but rare; the check costs 2 CMD52s only when
  the bitmap is non-empty and our own slot is clear).

RESYNCS, finally understood: 14703 over 80 blasts = ~184/blast, in line with
  every previous run (~50-230).  Crucially notready=0 means every one of
  those resyncs then read a REAL packet.  So the ring position routinely
  lags the firmware and the resync path productively corrects it -- it is
  normal operation, not damage.  My W12 reading of this counter as "thrash"
  was wrong twice over (once from comparing absolute counts across unequal
  runs, once from assuming the resyncs were finding nothing).

W15 phase 3: DAT1 silicon validation -- FAILED first, root-caused to a missing
CCCR write, model corrected to reproduce the failure, driver fixed, PASSED.
------------------------------------------------------------------------------
Date: 2026-08-20.  Rig: ESP8266 bench AP (house creds rotated and retired).
Both arms are m2_throughput_test builds with bench creds; traffic is the
ESP's 1 Hz broadcast + DHCP/ARP + PS event chatter (no LAN peer available:
the Mac is not on the ESP's network, so blast-level load stays QEMU-only).

ARM A -- polled (default), 143 s:  joined, ip=192.168.4.100, cardints=0,
  idle service cost ~1,070 CMD52/s (the documented ~1 kHz poll), c53=67,
  stranded=0/0 drainerr=0 notready=0 resyncs=0.

ARM B -- irq mode, FIRST ATTEMPT, 150 s: **VALIDATION FAILURE.**
  irq_mode=ON, connect=ok, then: cardints=0 the whole run, DHCP never
  bound, c53 pinned at 15.  A forensics line (raw uSDHC regs) made it
  decisive:  usdhc=0x0/0x157F71FF/0x100 on every tick =
    INT_STATUS bit 8 NEVER LATCHED / status-enable armed / signal-enable
    still armed (so the ISR never fired).
  The controller sat armed forever; THE CARD NEVER ASSERTED DAT1.

ROOT CAUSE: the SDIO spec gates the DAT1 pin CARD-SIDE in CCCR 0x04
  (IENM bit 0 + IEN1 bit 1), and the driver never wrote it -- it only ever
  configured the vendor HOST_INT_MASK (fn1), which selects which
  conditions the firmware raises, not whether the pin asserts.  NXP's own
  fsl_sdio.c SDIO_EnableIOInterrupt() writes CCCR 0x04.  The QEMU model
  had the same blind spot (derived the line from HOST_INT_STATUS &
  HOST_INT_MASK alone), which is exactly why emulation was green: THE
  MODEL SHARED THE DRIVER'S MISCONCEPTION -- the failure mode the W14
  design doc named as the honest risk of self-modelled hardware.

THE FIX, in the order the two-gate rule demands:
  1. qemu2 2ed9314631: the model's DAT1 line now requires CCCR 0x04
     IENM|IEN1.  Re-run against the UNFIXED driver, m2_rx_demo[irq] went
     RED in emulation -- "FAIL: cardInts()=0" -- reproducing silicon's
     failure exactly.  The model now encodes the contract.
  2. M2Radio c64ca1f: setInterruptMode(true) writes CCCR 0x04 = 0x03
     before arming the controller; on write failure it stays polled and
     interruptMode() reads false.  [irq] gate back to GREEN, ring/
     stranded/fallback gates unaffected.

ARM B -- irq mode, FIXED DRIVER, 195 s: **PASS.**
  cardints=1 on the first status tick, 502 by t=194 -- DAT1 fires on real
  silicon and every assertion is serviced.  ip bound normally.  c53=91
  (delivery rate matches the polled arm's 67/143 s).  Idle service cost
  ~88 CMD52/s vs 1,070 polled = **12x reduction on silicon** (the residual
  is the 64 ms safety-net tick, by design -- W13's missing-interrupt fw
  behaviour still needs it).  stranded=0/0 drainerr=0 notready=0
  resyncs=0: nothing the interrupt path made worse.  usdhc INT_STATUS
  reads 0 at print time because every latch is serviced within the tick.

WHAT THIS VALIDATES AND WHAT IT DOES NOT:
  * Validated: DAT1 asserts per queued work on the MAYA-W161, the
    ISR/mask/flag/rearm protocol works, PS sleep-wake cycling coexists
    with interrupt mode (166 sleeps in arm B), and the idle win is real.
  * NOT validated: blast-level load under interrupt mode on silicon (no
    peer on the ESP LAN this session) -- QEMU covers it; a future session
    with a LAN peer should repeat the tcp-rx soak in irq mode.
  * Interrupt mode remains DEFAULT OFF in the driver.  Flipping the
    default is a decision for after a load soak, not after one sparse run.

THE LESSON, stated for the next self-modelled peripheral: a hardware model
written from the same reading of the spec as the driver will AGREE with the
driver, and both can be wrong together -- emulation green, silicon dead.
The recovery loop that worked here: instrument the failure on silicon,
correct the MODEL first until emulation reproduces the silicon failure
against the unfixed driver, only then fix the driver, and keep the red run
in the record.  Model-flatters-driver is not hypothetical; this was it.

W15 phase 3 ADDENDUM (post-review correction to the list above): the driver's
"with DAT1 dead, the 64 ms net tick keeps both ports limping -- degrades to
slow polling, never to nothing" property must move to the NOT-VALIDATED list,
because the one silicon run that exercised the DAT1-dead condition (arm B,
first attempt) CONTRADICTS its data-path half: DHCP never bound in 150 s and
c53 pinned at 15, with the net-tick fold verifiably present in that build.
Two caveats keep this an open question rather than a refutation: c53 counts
DATA-port CMD53s only, so the event/command half of the claim (deauth/PS
events still seen) is untested, not disproved; and the data death is
plausibly PS interplay (the fw's awake window may be shorter than the 64 ms
poll cadence), not the tick failing.  Practical consequence: on a board with
flaky DAT1, irq mode may present as association-up/data-dead rather than
slow -- the detection signal is cardints= frozen.  A deliberate test needs:
CCCR write suppressed, PS OFF, a LAN peer, watch whether RX limps at ~64 ms.

W16: multiport aggregation.  The REGISTER PORT is validated on silicon -- and

------------------------------------------------------------------------------
Date: 2026-08-20.  Rig: ESP8266 bench AP (house creds rotated and retired), no
LAN peer, so this is a SPARSE run: association, DHCP, PS chatter and the ESP's
broadcasts.  Driver M2Radio b44877c+, model qemu2 7e17eff5d3.

WHAT W16 CHANGED.  W11 measured this link's ceiling as ~10 SDIO bus commands
per frame, one frame per CMD53.  W16 attacks that on two fronts: the multiport
REGISTER PORT (one byte-mode CMD53 at fn1 address 0 returns HOST_INT_STATUS,
both ring bitmaps, all 32 per-slot RD_LENs and the command-port length, in
place of seven CMD52s) and multiport AGGREGATION (one CMD53 spanning several
ring slots, both directions).  Only the first of the two is exercised by a
sparse link; see "STILL OWED" at the end.

ARM A -- THE FALSE POSITIVE, and it is the instructive part.

The register port rests on one thing nothing in this tree had measured: NXP
reads the register file with the CMD53 address held FIXED (OP Code 0), which
for an ordinary SDIO function means "read one register 196 times".  Because
that failure would be SILENT -- an all-zero snapshot is byte-identical to a
healthy idle card -- the driver shipped with a sanity check.  The first version
of that check compared the snapshot's byte at 0x5C against the cardStatus()
value begin() had read by CMD52: "a register that cannot be zero".

    tput: ip=192.168.4.100 ... regs:0/1,rxtx:8/3,aggr:0/0,total:66073
          mpregs=0/0x40/0 ... stranded=1/0 drainerr=0 notready=0 resyncs=0

  mpregs=0 -- rejected on the FIRST read, 0x40 where 0x0D was expected, and
  the driver spent the whole run on the CMD52 fallback.

THE CHECK WAS WRONG, NOT THE CARD.  Register 0x5C is CARD_TO_HOST_EVENT_REG.
It means DN_LD_CARD_RDY|CARD_IO_READY (0x0D) to the BOOT ROM and UP_LD_CP_RDY
(0x40) once firmware is running -- NXP's own mlan_sdio_defs.h says so.  The
"constant" was a live register captured minutes earlier, in a different phase
of the card's life.  A stale reference dressed as an invariant.

  Replaced with a test of the FAILURE MODE rather than of any register's
  value: is every byte of the 196 the same?  A port obeying OP Code 0
  literally can produce nothing else; a running card's register file cannot be
  uniform (32 RD_LENs read zero on an idle link while 0x5C carries the
  command-port ready bits).  The live CMD52 reading is still taken, once, and
  reported as mpRegsWitness() -- as EVIDENCE, never as a verdict.

ARM B -- CORRECTED BUILD.  ~105 s, stable to the last digit across the run:

    tput: ip=192.168.4.100 ps=1/113/58/57/0
          bus=c52tx:0,c52svc:31,c53:65/18432,regs:104733/4,rxtx:61/4,
              aggr:0/0,total:104833
          mpregs=1/0x0/0 witness=0x4048 split=0 state=idle reconnects=0
          stranded=0/0 drainerr=0 notready=0 resyncs=0 cardints=0

  mpregs=1        THE MEASUREMENT.  This card's multiport register port DOES
                  stream the register file for a fixed-address byte-mode
                  CMD53.  NXP's driver assumes it; nothing in this tree had
                  ever confirmed it; it is confirmed now.
  witness=0x4048  what the two transports said about 0x5C at the same moment:
                  0x40 through the register port, 0x48 through CMD52,
                  microseconds apart.  Both are live CARD_TO_HOST_EVENT
                  values.  That difference IS the reason arm A's check was
                  invalid, preserved as evidence rather than argued.
  c52tx:0 c52svc:31   the CMD52 polling storm is gone.  31 CMD52s in 105 s,
                  against the ~1,070/s this driver used to poll at.
  stranded/drainerr/notready/resyncs/split all 0.

THE BUS-COST A/B, normalised per SERVICE PASS (both arms run the same
delay(1)-paced loop, so a pass is the same unit in both):

    arm A (CMD52 transport)   527,117 CMD52 over ~48k passes  = ~11 per pass
    arm B (register port)     104,733 CMD53 over ~105k passes = ~1 per pass

  Roughly ELEVEN bus commands per service pass become ONE.  Seven of those
  eleven are the pre-W16 service poll proper (1 status + 4 rd-bitmap + 2
  RD_LEN); the other four were the wr-bitmap read, which the service path no
  longer does at all.
  ★ HONEST CAVEAT: arm A's split between c52tx and c52svc was mis-attributed
  (the fallback's wr-bitmap reads were counted as TX polling, which made an
  idle link appear to do 191,607 CMD52s of TX polling for three transmitted
  frames).  That bug was fixed after this measurement.  It moved commands
  between two counters that are BOTH terms of the total, so the totals -- and
  therefore the ratio above -- are unaffected.  Stated rather than quietly
  omitted, because a counter that lies is exactly what W12's two wrong
  conclusions were built on.

STILL OWED, and it is the headline item:
  * AGGREGATION ITSELF IS UNMEASURED ON SILICON.  `aggr:0/0` in every line
    above, and that is CORRECT rather than a failure: a sparse link never has
    two occupied ring slots at once, so there is nothing to aggregate.
    Aggregation only helps when frames arrive faster than the host services
    them, which needs blast-level load, which needs a peer on the bench AP's
    LAN.  There was none this session.  Until that run happens, RX and TX
    aggregation are proven in QEMU (gates [rxaggr]/[txaggr], each demonstrated
    failing against a non-aggregating driver) and NOT on hardware.
  * No Mbps number here at all.  A sparse link cannot produce one, and the
    W11-W12 rule stands: any verdict rests on the counter mechanism, never on
    an Mbps delta.
  * TX aggregation remains DEFAULT OFF in the driver; the lwip netif enables
    it and flushes every poll.  This run's three transmitted frames are DHCP
    and ARP, so the TX batching path is barely touched.

uacv — macOS as a UAC1 host, 2026-08-04
========================================
Second host personality, second class. MC200 reflashed by xrun to
1AMi2o2xxxxxx (UAC1, full speed); USB device port on the Mac; XTAG attached
for xscope. 300.5 s capture, 3.9 MB, 3006 blocks, zero missing marks.

The personality change is un-fakeable in the enumeration:
    PID 20b1:000f (was 000e)      Speed: Up to 12 Mb/s (was 480)
    CoreAudio: "XMOS xCORE-200 MC (UAC1.0)", 2 in / 2 out, 48000 Hz

macOS chose the format. It picked 48 kHz -- an INTEGER frames-per-packet rate,
where the fractional-sample law collapses to a single legal size -- and, more
interestingly, 24-bit in 3-BYTE subslots, not the 16-bit this config is
usually described as running.


The finding: an uninstrumented path forged a PASS, and the vacuity guard
caught it
-----------------------------------------------------------------------------
    or_acc 0x00000000    and_acc 0xFFFFFFFF    nonsilent_frames 0

The observer instrumented the 4-byte subslot path (_send_sample_4) and the
16-bit path (case 2). It did NOT instrument case 3, the 3-byte packed path --
which is the one macOS selected.

An uninstrumented path does not read as "no data". It reads as or_acc == 0,
which is precisely the signature of a silent stream. R3 tests
(or_acc & 0xFF) == 0 and would have reported

    PASS  low byte never non-zero: samples are left-justified

from code that never executed. A conformance verdict manufactured out of an
absence, about a host that was in fact sending 300,600 packets of real audio.

What stopped it was the non-silent-frame witness:

    SKIP  only 0 non-silent frames (need 10000); a silent stream would pass
          this check for the wrong reason

The design argued for that witness against SILENT AUDIO. The actual failure
was an uninstrumented code path -- a mode nobody anticipated -- and it
produces an identical signature, so the guard caught it regardless. That is
the strongest evidence so far that the "never let an absence read as a PASS"
rule is worth its cost.

Fixed in lib_xua b424b0e0; case 3 now accumulates like the other two.


The manifest-contradiction guard also did real work
----------------------------------------------------
The first run of this capture was judged with subslot_bytes=2, taken from the
config's usual description rather than from the device:

    INVALID  declares 2 channels x 2 B = 4 B per audio frame, but packet sizes
             [282] are not whole multiples of 4 B, and the device counted no
             non-multiple packets. The observed sizes imply a frame of 6 B.
             No verdict about the host can be trusted until the two agree

Exit 2, not exit 1: an operator error is not a host failure. The guard named
the right number (6 B) and the right reason. Corrected manifest -> valid run.

macOS honours the device's declared feedback rate in both classes
------------------------------------------------------------------
    UAC2/HS   bInterval 4 -> 1 ms     macOS polled 1000.0/s
    UAC1/FS   bRefresh  4 -> 16 ms    macOS polled   62.5/s

Two different declarations, two exactly matching poll rates. The RT1176 host
polls 62.5/s in both cases, which at high speed is sixteen times slower than
the device asks for.


W2 at an integer sample rate: honest, but it will always fire
--------------------------------------------------------------
At 48 kHz, frames-per-packet is exactly 48.0, so floor and ceiling coincide
and legal_packet_sizes is the single value {288}. macOS sent 282 B (47 frames)
552 times out of 300,600 -- 0.18% -- and W2 warned, with accurate arithmetic:
one frame of deviation.

But an asynchronous host MUST vary packet size to track feedback; that is what
the feedback endpoint is for. At an integer rate there is no second legal size
for it to vary INTO, so any conforming async host trips W2 there. The warning
is not wrong -- the variation is real and does consume FIFO headroom -- but it
is unavoidable rather than diagnostic, and a reader should know that before
treating it as a finding about macOS.

Not changing the rule on one capture. Recorded so the next person does not
mistake it for a defect.


class_req_bitmap 0x4 is correct here, not a gap
------------------------------------------------
Only bit 2 (SET_INTERFACE) is set; the clock bits are clear. UAC1 sets sample
rate through an endpoint control, not a Clock Source unit, and the observer's
hook is on the UAC2 clock unit. Reading this as a missing class request would
be wrong.

The RT1176 host does not claim the UAC1/FS device from cold, 2026-08-04
=======================================================================
Attempting the fourth cell of the matrix -- RT1176 host, UAC1 class -- produced
no capture at all, and the reason is a finding about the host rather than a
bench problem.

    UAC1 image (1AMi2o2xxxxxx) on J47/USB_OTG2:
        host heartbeat, continuously over ~110 s and three resets
        (two by hand at the board, one attempted over LinkServer):
            audio=none  uac2=0  alt=-1  ctrl=0/0/0
        capture: 1322 bytes -- header only, not one packet

    UAC2 image (2AMi8o8xxxxxx), same cable, same connector, same host
    binary, eight minutes later:
        capture: 2.7 MB, and the judge returns
            8 PASS, 0 FAIL, 1 SKIP     W1 +0.120 ppm

The control rules out the cabling, the connector, the host build, the observer
and the collector. The single variable is the device's class personality.

`ctrl=0/0/0` is the sharp part. That counter reports outstanding control
transfers, timeouts and queue failures. All three are zero, so the host never
issued a control request at all -- this is not the control-sequence wedge
documented earlier in this file, which showed a non-zero state stuck at
CTRL_SET_CLOCK. The host never began a claim.

Worth noting what the existing evidence did and did not establish. The
device-swap A/B in transcript_hw_evkb.txt shows the host handling the FS
personality after an HS -> FS swap, with `audio=ready uac2=0 alt=1
pkts/s=1000`. That is a RE-claim, from a driver that had already claimed the
HS device and rebuilt its descriptors. It was never evidence that the host
claims a UAC1 device from a cold start, and today it did not.

macOS claimed the identical device and image without difficulty (see above:
5 PASS, 300,600 packets), so the device presents a working UAC1 configuration.

The validator cannot report this defect, and that is not a gap in it. A host
that never claims sends no packets, so there is nothing to reduce and nothing
to judge; the judge says INVALID, "no validator state blocks found", exit 2 --
correctly refusing to describe a host it never observed. The evidence for this
finding is the host's own heartbeat next to a control capture, which is
exactly the pairing the two-gate rule asks for.

Not chased further tonight. Recorded as a candidate defect in USBHost_t36's
UAC1 claim path with a reproduction that takes eight minutes: load the UAC1
image, watch audio=none; load the UAC2 image, watch it stream.


RETRACTION: the section above is wrong. The host was right to decline.
=======================================================================
The finding recorded above -- "the RT1176 host never claims the UAC1/FS device
from cold", filed as a candidate defect in USBHost_t36 -- is WITHDRAWN. The
host behaved correctly and the fault was mine, in how I built the witness.

What actually happened. The example asks for an exact format:

    usb_audio_graph_test.cpp:148   audioOut.format(44100, 2, 16)

and uac1_find_alt() requires an exact match on channels, bit resolution and
rate support, returning -1 otherwise. claim() then returns false BEFORE
issuing any control transfer -- which is precisely the ctrl=0/0/0 I read as
suspicious. It was not a host that failed to start a claim; it was a host
correctly declining a device that did not offer the format it wanted.

My rebuild of 1AMi2o2xxxxxx omitted the 16-bit resolution override the
original witness was built with. Without it the image advertises 24-bit, which
is why macOS negotiated 3-byte subslots on it. The host asks for 16-bit, the
device offered none, so no alt matched.

Proven by rebuilding with the override and changing nothing else -- same host
binary, same cable, same connector, same collector:

    24-bit build:  audio=none, ctrl=0/0/0, 1322 bytes, no packets
    16-bit build:  streams immediately; 5 PASS, 0 FAIL, 2 WARN, 2 SKIP

The behaviour is not merely defensible, it is documented intent. claim() in
usb_audio.cpp carries the comment "P1 targets the witness's 24-bit alt
explicitly ... Broader alt negotiation is P2." Alt negotiation is deferred
scope, stated in the source I had already read.

Why the control experiment did not save me. Swapping to the UAC2 image proved
the cabling, connector, host build and collector were all fine, and I treated
that as isolating the fault to the host's UAC1 path. It did not: it isolated
the fault to the difference between the two IMAGES, and I had built one of
them wrong. A control rules out what it varies, not what it holds fixed, and
I held the witness build fixed in my thinking while it was the thing that had
changed.

This is the failure mode the whole tool exists to prevent, committed by hand
in prose: an absence of packets read as a defect in the party that was not at
fault. The judge itself never made the claim -- it returned INVALID, "no
validator state blocks found", exit 2, and refused to describe a host it had
not observed. The false accusation was entirely mine, in a commit message.

Required build flags for the UAC1 witness, so this does not recur:

    -DAUDIO_CLASS=1
    -DSTREAM_FORMAT_OUTPUT_1_RESOLUTION_BITS=16
    -DSTREAM_FORMAT_INPUT_1_RESOLUTION_BITS=16

(The sw_usb_audio checkout has been restored to pristine; these belong on the
build command, not as edits scattered through a third-party tree.)

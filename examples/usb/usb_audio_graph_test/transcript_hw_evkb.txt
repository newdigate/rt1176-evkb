usb_audio_graph_test — hardware evidence, MIMXRT1170-EVKB + XMOS xcore-200 MC
=============================================================================
Bench: EVKB host port J47 / USB_OTG2 (USBPHY2) -> XMOS MC200 (sw_usb_audio app_usb_aud_xk_216_mc,
config 1AMi2o2xxxxxx, UAC1 FS, stereo 16-bit, asynchronous, feedback EP 0x82
bRefresh=4), MC200 line out -> RME Fireface UFX ch1/2. Device instrumented
with xscope probes in lib_xua's decoupler (lib_xua-decouple-instrumentation
.patch beside this file): OUT-FIFO fill (bytes, 100 Hz), stream-reset
underflow count, overflow count, runtime dry-out count.

The periodic click: root cause, measured 2026-08-02
---------------------------------------------------
The device's converter runs on its own crystal. Un-fed-back, the host/device
rate difference accumulates in the device's OUT FIFO until lib_xua
block-corrects: under-feed -> the decoupler runs dry mid-stream (the
previously un-instrumented `outUnderflow = (rdptr == wrptr)` path in
handle_audio_request) and inserts OUT_BUFFER_PREFILL bytes of silence;
over-feed -> XUD stops being given buffers and packets are dropped until the
FIFO drains to half. Either correction is the audible click; period =
correction quantum / drift rate.

Locked-bias drift sweep (tools/driftrun.sh, 120 s per point, one flash per
point, open loop):

    bias(ppm)  drift(ppm)  runtime events            residual vs fit
       -250      -162.9    5 dry-outs                -0.08
       -150       -63.7    2 dry-outs                 0.03
        -83         2.7    none                       0.04
          0        85.0    none (climb phase)         0.09
        150       233.5    3 overflows                -0.04
        250       332.6    5 overflows                -0.03

    slope 0.9909 (ppm-equivalent scale; the broken probe this replaced
    measured 0.222), residual rms 0.06 ppm, zero crossing = device true
    rate = -85.7 ppm relative to host nominal. Fill drift is linear at
    r^2 0.95-0.99 in every segment of every point; consecutive drain
    segments within a point agree to 0.1%.

The earlier analogue A/B that seemed to rule rate mismatch out was measuring
its own capture chain: the chain's floor was ~17 events/s while the real
glitch rate at these offsets is 0.005-0.06/s. The device-side probes have no
floor: at bias -83 (2.7 ppm from true) 125 s ran with zero runtime events;
at every other point events appeared at quantum/drift cadence.

The fix: read the feedback endpoint
-----------------------------------
USBAudioOut now arms two iso-IN siTDs on the feedback endpoint (found via
bSynchAddress; the endpoint's own usage bits say "data" and cannot identify
it), 16 frames apart on the 32-slot periodic list = one read per 16 ms,
matching bRefresh=4. Each 3-byte 10.14 report is decoded to millihertz,
gated for plausibility (+-2% of nominal), EMA-averaged (1/8 per report --
the device dithers the raw report between adjacent values; slew-chasing the
raw value converges to a dither rail, measured as a +4.8 ppm sizing bias
before the EMA), and the packet-sizing accumulator slews toward the average
at ~90 ppm/s.

Closed-loop verification 2026-08-02 (25 min soak, device-side VCD):
    duration 1521.7 s, fill slope +0.025 B/s (+0.1 ppm equivalent)
    fill envelope 776..980 bytes (204 B total wander, +-2 packets of jitter)
    runtime corrections: ZERO (dry-out count froze at the t=0.05 s stream
    start transient; overflow never fired; underflow only the stream-start
    reset). Open loop at bias 0 the same interval predicts ~22 block
    corrections; the sweep measured one every ~25 s at the biases the click
    was originally reported against.
    heartbeat over the whole soak: err/s=0, pkts/s=1000, fbpkts 62.6/s
    sustained, fberr=0, fresh=1, sizing within ~1.5 ppm of the feedback EMA.

Analogue capture during the soak (12 min, MC200 line out -> RME ch1/2,
glitchdetect.py, selftest 9/9 first): 4.35 events/s, |mag| median 10.8
samples -- the same magnitude distribution as the 2026-08-02 loopback
control (2.23/s, median 10.9), i.e. the capture chain's own floor. No
same-session loopback control was possible (no re-cabling on an unattended
bench), so per this bench's measurement rules the analogue number is only
corroboration: nothing above the floor. The block-correction signature this
chain would need to resolve (0.04/s at the offsets in use) sits far below
its floor in both rate and magnitude, which is precisely why the device-side
probes were built.

Cross-checks:
  - Feedback EMA reads -83 ppm where the open-loop sweep intercept said
    -85.7 ppm (independent instruments, hours apart, temperature moves the
    crystal): the decoder is measuring the same physical quantity as the
    drift fit.
  - fbpkts climbs at 62/s (= 2 descriptors / 32 ms each), fberr=0.
  - fbrej counts a reproducible ~113-report burst at stream start (device's
    measurement engine not yet running -> zero/implausible reports, gated
    out by design), then stays static.

Historical note
---------------
An earlier swept-bias analogue measurement produced a convincing V at
-56 ppm; it did not survive a controlled A/B, and the sweep's sawtooth
confounded bias with time. The -85.7 ppm above comes from locked-bias
points with per-point provenance and 0.06 ppm residuals, and the feedback
endpoint independently reports the same rate. -56 was noise.

Device-swap re-arm, hardware A/B 2026-08-03
--------------------------------------------
The P3 review predicted statically that once any stream had started, a
re-claim needing the other transport would never re-arm (disconnect()
leaves is_streaming set; beginStreaming() opened by returning true on
it). Reproduced and fixed on silicon by swapping the MC200 between its
two personalities with xrun -- no host reset -- and watching pkts/s.
The personality change is un-fakeable in the log: the device's PID
changes, 20B1:000E (2AMi8o8, UAC2/HS) vs 20B1:000F (1AMi2o2, UAC1/FS).

    pre-fix host (build-prefix, driver at 090eadb~1), HS -> FS swap:
        before  audio=ready uac2=1 alt=1  pkts/s=1000
        after   audio=ready uac2=0 alt=1  pkts/s=0      <- wedged
    The claim and the whole control sequence SUCCEED (alt is valid, the
    transport flag is right); only the descriptors are never rebuilt, so
    the driver reports a healthy stream while transmitting nothing. That
    is the signature the fix had to remove, and it is why the bug
    survived P1 and P3: nothing in the API says anything is wrong.

    fixed host (090eadb), HS -> FS swap:
        after   audio=ready uac2=0 alt=1  pkts/s=1000 err/s=0
                underruns=0, sustained over minutes, and the FS feedback
                loop re-armed with it: fbpkts +62/s, fbrej=2, fberr=0,
                fresh=1, sizing tracking fb again.
    fixed host, FS -> HS swap (the reverse, also wedged pre-fix):
        "device ready, alt=1" then "streaming started" logged, and
        seq=47 audio=ready uac2=1 alt=1 err/s=0 fresh=1 -- one second
        after seq=22 audio=ready uac2=0 alt=1. service() dispatches on
        is_uac2, so a host walking the HS branch at 1000 pkts/s is proof
        the iTD ring was rebuilt; an un-rebuilt host reads pkts/s=0.

The reverse-direction window stayed short because the swap-back landed
in the separate re-enumeration wedge below; the rebuild itself is what
the heartbeat above records.

Control-sequence wedge: root cause found, 2026-08-03
-----------------------------------------------------
The re-enumeration wedge noted below was chased with the driver's
ctrl_state exposed in the heartbeat (ctrl=<state>/<timeouts>/<queue
fails>). Reproduced by xrun-ing the witness firmware while the host
streamed: the second claim sat at CTRL_SET_CLOCK for 71 consecutive
seconds, alt never valid.

Cause is in the core, not the device. A driver learns about a control
transfer ONLY when it completes cleanly: followup_Transfer (ehci.cpp)
calls the pipe callback for a qTD with neither active nor error bits,
while an errored transfer is routed to the pipe's
error_callback_function -- permanently the core's enumeration_error
(enumeration.cpp:135), which retries enumeration and never tells the
driver that issued the request. enumeration.cpp:220 is the only path to
driver->control() and it is on the clean side. A stalled request
therefore freezes a driver's sequence with nothing able to release it.

The Transfer_t-leak hypothesis was refuted twice: disconnect_Device ->
delete_Pipe already frees both the followup lists and the QH chain, and
on the bench the queue-fail counter stayed 0 while four attempts (12
allocations) passed through a ~9-entry pool -- which also proves the
transfers are freed between attempts rather than held.

Fixed by not depending on that callback: each step stamps a deadline and
a watchdog in service() reissues on expiry, bounded, then gives up with
counters showing why. ctrl_state now returns to idle instead of
freezing; normal operation unchanged (alt=1 ctrl=0/0/0, 1000 pkt/s).

What the fix does NOT do, now measurable rather than mysterious: after
this event the device stops answering control transfers at all. A fresh
attach gets a fresh budget and still fails four more times
(ctrl=0/8/0).

Followed up the same day; four candidate causes were each refuted by
measurement, and the answer is device-side, not host-side.

  - enumeration_error resuming enumeration on a live device: inert.
    enumeration_transmit has no case for the completed state (10), so it
    queues nothing. Read, not assumed.
  - Transfer_t pool leak on disconnect: refuted twice. delete_Pipe frees
    both the followup lists and the QH chain, and the queue-fail counter
    stays 0 through four attempts.
  - "Just retry longer": refuted, and harmful. Raised the budget to 40
    and the pool ran dry at attempt 5 (ctrl=0/5/1). A request that hangs
    holds its three Transfer_t entries until the pipe is deleted, so
    every retry permanently consumes entries from a pool shared with
    every other driver. Small and bounded is the only safe policy; the
    committed three is right.
  - The self-heal stream retargeting the new device: refuted as the
    cause. Gating the ring on a selected alternate setting took pkts/s
    from 1000 to 0 across the window and the wedge persisted unchanged.
    The gate was kept anyway (d370e80) because streaming to a device in
    alt 0 is wrong regardless.

What it actually is: a device-side startup race. xrun reloads the
firmware over JTAG while the device is enumerated; its USB stack answers
standard requests (enumeration completes, descriptors read, claim
succeeds) before the audio task is ready to answer CLASS requests, so
the clock SET_CUR is never answered. Every xrun recreates the race,
which is why repeated xruns never recover it. A host reset does recover
it because it re-enumerates a device that has by then settled -- proven
by resetting the host with the wedged device untouched: same device,
immediately audio=ready uac2=1 alt=1 ctrl=0/0/0, 1000 pkt/s, feedback
loop closed.

So this is a property of hot-reloading firmware onto a streaming device,
not a host driver defect, and no core change is warranted -- which
matters, because the core's control path is shared by every driver. The
driver's part (never freezing on a completion that cannot arrive) is
fixed and gated; the operational rule is that after an xrun reload the
host needs a reset, or the device a replug, once it has settled.

Two bench findings recorded for follow-up (tracked tasks, out of this
gate's scope): a device that attaches and re-enumerates within seconds
(xrun's load sequence does this) wedges the SECOND claim's control
sequence -- alt stays -1, the self-heal path zombie-streams the old
ring at nominal into the device's alt 0, and the unopened feedback EP's
zero-length reads are counted (fbrej at the 63/s poll rate) and never
applied, sizing pinned at nominal: the reject path proven live, twice,
by an enumeration bug (suspected Transfer_t pool leak from the aborted
in-flight control transfer). And JTAG-alive does not imply USB-alive:
the flash-booted witness survived the Mac power cycle with its USB
wedged; xrun restarting the same image brought it back.

THE FINDING THAT DEFINED THIS PHASE
-----------------------------------
The example is called usb_audio_graph_test. Until this gate its audio graph
was compiled out of every image ever built from it.

    usb_audio_graph_test.cpp:35     #define DRIVE_FROM_TONE 1

was a bare #define with no build override, and the sine node,
AudioOutputUSBHost and both AudioConnections all live under
`#if !DRIVE_FROM_TONE`. So every measurement in this directory -- the UAC1
sweep and soak above, the whole UAC2 P1 and P3 evidence, both A/B soaks --
was taken with USBAudioOut's INTERNAL tone generator. The graph adapter this
example exists to exercise was never in the binary. The console said so all
along, in the line nobody read as an accusation:

    GRAPH-TEST: MODE = driver tone generator (graph bypassed)

That is not a defect in any of those measurements: they measured transport,
descriptors and clocking, and they measured them correctly. It does mean P4
was the first time the graph -> FIFO -> packer path ran on hardware at all.

Now a CMake option, GRAPH_DRIVE, default OFF. The default build is unchanged
and that was verified rather than asserted: .text.itcm + .text.code + .data
extracted from before and after the edit are byte-identical, 37580 bytes,
sha 5021aa6843c0a359. (The first attempt to check this extracted `.text`,
which this linker script does not emit, compared two empty files and printed
IDENTICAL. A size guard now makes that failure mode impossible.)

---------------------------------------------------

Analogue, MC200 line out -> RME Fireface UFX, 3.4 s at 44.1 kHz, all 30
captured channels searched for a 440 Hz component rather than assuming a pair:

                        ch0         ch1
    peak                16612       14386
    rms                 11740       10070
    fundamental         440.085 Hz  440.085 Hz
    THD (h2..h7)        0.0478 %    0.1277 %
    h2                  -69.6 dB    -58.9 dB
    fundamental/noise   95.1 dB     95.0 dB
    crest factor        1.4151      1.4284

Crest 1.4151 against sqrt(2)=1.41421 is 0.06 % -- a real sine, through
graph -> FIFO -> uac_pack16(ch_live=2, ch_total=8, subslot=4) -> iso OUT ->
MC200 DAC -> RME.

The channel asymmetry is analogue, and that is provable rather than assumed:
the sketch fans ONE mono sine node to both graph inputs, so interleaved[i*2]
and interleaved[i*2+1] are bit-identical, and uac_pack16 writes them to device
channels 0 and 1 unchanged. Identical digital in, 10.7 dB more h2 out. The
difference can only live in the MC200's DAC channel 2, the cable or the RME's
input 2.

440.085 Hz is NOT a clock measurement and is not offered as one. It conflates
three clocks -- the MC200's DAC, the RME's ADC and the 44100 the FFT assumes
-- and the RME's own offset is uncalibrated here. Same discipline as the Stage
B loopback's 440.65 Hz, different reason (there it was bin width; here it is
an uncalibrated capture clock).

INSTRUMENT AND BENCH FINDINGS FROM THIS GATE
---------------------------------------------
* Print::printf truncates at PRINTF_BUF_SIZE (128) bytes PER CALL, silently.
  Adding port= to the heartbeat's first printf put it at exactly 128, and the
  field that got cut was spd= -- the one bit that separates a high-speed UAC2
  enumeration from a full-speed fallback, which was the entire reason for
  adding it. Now its own printf. Every other heartbeat field was already a
  separate call, which is why none of them had ever truncated.

* `LinkServer run` was misdiagnosed here as hanging, and driftrun.sh was
  briefly "fixed" to use `flash ... load` instead. It does not hang: it is
  asynchronous and silent, exactly as driftrun.sh's own comment has said since
  2026-08-02, and the board resets about 23 s in. `flash load` does program
  the part but leaves the core HALTED, so the first sweep point dwelled
  against a dead board and the console guard caught it. Reverted, with the
  trap written down in the script.

* The MC200 is loaded with `xrun`, which is RAM-resident. Unplugging it power
  cycles it, the image is gone, and it re-enumerates at FULL speed running
  whatever is in flash -- at which point the UAC2 driver correctly refuses it
  (dev->speed != 2) and the host reports audio=none with a perfectly healthy
  port. port=...(ccs=1 pe=1 pp=1 spd=0) is the signature; re-run xrun.

* vcdfill.py's ppm column assumed 4 B frames. This was NOT discovered here --
  the UAC2 P1 gate above records it and gives the manual 1.4112 divisor. What
  forced it to become a parameter (--frame-bytes) is that a manual division is
  fine for one number off one run but not when a five-point FIT consumes it:
  the slope came out 7.85 against a gate demanding 1.000, and that gate's own
  comment tells you to read that as "the probe or the analysis is broken".
  The zero crossing was never affected -- -icept/slope is invariant under a
  uniform scale error, which is why -85.8 ppm was right either way.

* driftrun.sh is now parameterised by DEV_CONFIG and GRAPH_DRIVE, with
  separate build trees per mode so a cached GRAPH_DRIVE cannot silently mix a
  tone-driven point into a graph-driven sweep. Defaults reproduce the UAC1
  tone-driven behaviour every earlier transcript was taken with.

UAC2 P2 gate, 2026-08-06 (parser and control breadth)
------------------------------------------------------
Spec: docs/superpowers/specs/2026-08-02-uac2-audio-out-design.md section 3 P2
-- "Full UAC2 walk, RANGE, IADs, rejection taxonomy; fixture corpus."
Gate: host suite green over the corpus, and the MC200 re-enumerating through
the full parser with results identical to P1's minimal one. Run last of the
four phases, because P1/P3/P4 all needed the bench and this needed none of it.

WHAT THE PARSER COULD NOT DO BEFORE
------------------------------------
* Say WHY it refused a device. Six distinct failures returned one `false`.
  That is the same defect usb_audio_capture_test's cfg= field had to work
  around at the sketch level -- "offered and rejected" and "nothing arrived"
  are different events and were indistinguishable. Now eight named reasons
  (uac2_parse_result), with the two that used to share a line deliberately
  split: NO_AC_HEADER ("not an audio function we recognise") is a different
  verdict from NOT_UAC2 ("an audio function we understand, declined by
  version").
* Follow a clock chain through a CLOCK_MULTIPLIER. The header documented this
  as out of scope and failing closed, so a device clocked
  source -> multiplier -> terminal did not parse at all.
* Tell two audio functions apart. Every interface was identified by CLASS, so
  a composite device -- separate playback and capture functions, the ordinary
  headset shape -- could have function A's AudioControl interface assembled
  with function B's AudioStreaming interface into a topology describing no
  real device, with the clock chain resolved across the seam.
* Ask what rates the device actually supports. UAC2 puts rates in a runtime
  RANGE conversation, and that conversation had never been had: the driver
  wrote CUR 44100 and assumed. A device not supporting 44100 would have been
  set to a rate it never advertised, first evidenced by wrong-pitch audio.

A WRONG ASSUMPTION THE CAPTURED FIXTURE CAUGHT
-----------------------------------------------
The IAD matcher was first written to require bFunctionSubClass == 0x01
(AUDIOCONTROL), which is the intuitive guess. The MC200's real IAD carries
0x00, and UAC2 4.6 agrees: an audio function's IAD uses
FUNCTION_SUBCLASS_UNDEFINED. So the matcher recognised no real audio function
at all, and the composite test failed with the whole topology empty.

It only surfaced because the tests run against a CAPTURED descriptor set. The
hand-written decoy function in the test had the same wrong assumption baked
into it, so a synthetic-only corpus would have agreed with the parser and both
would have been wrong together. That is the argument for building the
rejection and multiplier tests by MUTATING the real fixture rather than
inventing byte arrays: every byte except the one under test is known-good and
known-accepted, so a rejection can only be the field being tested.

A DESIGN CORRECTION MADE MID-TASK
----------------------------------
IAD scoping was first written as "the first audio function wins". That is
wrong in an ordinary case: a composite device declaring its capture function
before its playback function would be refused for having no output stream,
while the stream it needed sat in the next function along. The parser now
TRIES each audio function in declaration order and takes the first that yields
a usable topology, reporting the primary function's complaint if none do.

CORPUS (P2's first gate half)
------------------------------
Every captured fixture through the UAC2 parser, including the five UAC1 ones,
because what those prove is that the taxonomy answers informatively on real
devices rather than falling out early with something vague:

    dongle_uac1_duplex.bin           244 B  -> not-uac2
    generalplus_uac1_multirate.bin   244 B  -> not-uac2
    headset_uac1_config.bin          799 B  -> not-uac2
    jabra_uac1_multirate.bin         272 B  -> not-uac2
    xmos_uac1_async_feedback.bin     233 B  -> not-uac2
    xmos_uac2_2ami8o8.bin            372 B  -> ok, clock=0x29 alts=3 in_alts=2
                                              interfaces 0/1, input 2

Each UAC1 device reaches the version check and is declined BY VERSION -- the
most informative answer available. Before the taxonomy all six were `false`.

Host suite: 11838 checks, 0 failures (test_uac2_parse alone 112 -> 233). A
missing corpus fixture FAILS rather than skipping, verified by hiding one: a
corpus that quietly shrinks to nothing is green and worthless. Both new
features were vacuity-checked by disabling them and confirming the tests go
red -- the multiplier (3 checks fail, clock resolves to 0) and the RANGE step
arithmetic (44100 wrongly accepted inside an 8000..48000/4000 subrange).

SILICON (P2's second gate half)
--------------------------------
MC200 re-enumerated through the full parser, usb_audio_capture_test:

    CAPTURE-TEST: input ready, iface=2 alt=1 uac2=1
    CAPTURE-TEST: input ep=0x81 attr=0x05 mps=800 8ch x 4B (24 bit) clock=41
    CAPTURE-TEST: recording started

Byte for byte what P1's minimal parser and the Stage B run reported, clock=41
(0x29) included. Steady state: pkts/s=1000 the only value over 25 heartbeats,
over=0, fifo=0, cfg=372, spd=2, bytes/s alternating 1411072/1411088 -- the
same two modal values Stage B recorded -- derived=44096Hz.

Two console artefacts worth knowing, neither a fault:

* empty= and err= accumulate while the host's IN ring is armed and the device
  is ABSENT, then freeze. Flashing the host before loading the MC200 gave
  empty=333 err=333; resetting the host with the device already up gave
  empty=0 err=0 on the same firmware. They are independent counters
  (err = xact+babble+buffer, empty = zero-length microframes), so their being
  exactly equal is itself the diagnostic: every empty microframe also carried
  a transaction error, which is an absent device rather than a silent one.
* up= in this sketch is the RECORDING SESSION's age, not the board's:
  started_at is reset at "recording started" (line 237) while seq free-runs.
  A re-enumeration therefore shows up=1s with seq unbroken (75 -> 76), and one
  beat of absurd rates (pkts/s=82767) from dividing by a near-zero dt. Neither
  is a reset; seq never went backwards.

The MC200 is xrun-loaded, so it is RAM-resident and a power cycle loses it.
Re-running xrun with the console ATTACHED is safe and is how the one-shot
topology line above was captured without a LinkServer operation: xrun drives
the XTAG only and never touches the MCU-Link VCOM.

NOT DONE, AND DELIBERATELY
---------------------------
GET_RANGE is built and unit-tested but is NOT wired into the enumeration
control sequence. That sequence is a fixed chain (SET_CLOCK -> SET_INTERFACE
-> SET_RATE, then the input three) whose wedge cost a bench night and is
documented above; inserting a transfer into it risks precisely the "identical
results" half of this gate. The rate a device advertises should be consulted
before CUR is written, and the pieces to do it now exist.
